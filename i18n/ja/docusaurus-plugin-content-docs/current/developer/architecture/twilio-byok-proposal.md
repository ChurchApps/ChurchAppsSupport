# Twilio BYOK 連携の提案

:::caution 提案 — 利用可能な連携ではありません
これはメンテナーによるレビュー用の設計案で、2026年10月22日に確認した公開ソースと Twilio のドキュメントに基づいています。その後、基本的な Twilio プロバイダーが提供されています（`@churchapps/texting` 0.6.0 および B1 Admin の **Settings > Texting**）。教会は Account SID、Auth Token、送信元番号を入力します（プロバイダーは `MG` で始まる Messaging Service SID も受け付けますが、`fromNumber` 列はまだ `varchar(20)` のため、34文字の SID には短すぎます）。メッセージは受信者1人につき1リクエストずつ Twilio の Messages API を通じて送信され、STOP の返信は既存の受信 Webhook を通じて B1 に届きます。[教会設定：Texting](../../b1-admin/settings/church-settings.md#texting) を参照してください。以下の同意モデル、Advanced Opt-Out の処理、配信ステータス、セットアップ準備状況の確認は、まだ提案段階で、出荷された動作ではありません。[教会向けオンボーディング草案](./twilio-byok-onboarding-draft) には、提案されたセットアップ手順と教会固有の例が含まれています。
:::

## 推奨する方向性

B1 の既存のテキスト送信プロバイダー・システムに Twilio を追加します。方式は、**教会が所有する Twilio アカウント、API 認証情報、Messaging Service、SMS 対応の電話番号**を使うものです。教会は自身の法人を登録し、メッセージングのキャンペーンを登録し、Twilio に直接支払い、受信者の同意を維持し、Twilio Console で承認を管理します。ChurchApps は連携機能とドキュメントを提供します。

最初は、B1 の教会ごとに1つのメッセージング・プログラム、1つの Messaging Service、1つの米国ローカル 10DLC 送信元から始めます。既存の B1 画面を通じて、個別のテキスト、グループ向けテキスト、ワークフローによるテキスト、オプトインのリマインダーをサポートします。妥当な最初のプログラムは、その教会の同意内容と承認済みキャンペーンにおいて3つすべてが説明されている場合の、礼拝の変更、イベントのリマインダー、ボランティアのスケジュール連絡です。募金や販促のメッセージは、別途評価された範囲と同意が必要で、このプログラムに黙って追加してはいけません。

| 責任 | 教会 | B1 / ChurchApps |
|---|---|---|
| Twilio アカウント、請求、番号の所有 | 所有し、管理する | プラットフォーム用アカウントを用意せず、クレジットを再販売しない |
| ブランド、キャンペーン、番号登録 | 正確な教会情報を提出し、審査と修正に対応する | 必要条件を説明し、利用可能な準備状況の情報を読み取る |
| 登録ページ、ポリシー、メッセージの目的 | 公開し、維持する | 互換性のあるフォーム項目、例、同意の記録を提供する |
| 受信者の資格と STOP の処理 | 同意の証拠を確認し、SMS 以外で受け取った要求を確認する | 同意、抑止、権限、署名付き Webhook を適用する |
| 配信とサポート | Twilio のエラー、アカウントの状態、受信した返信を監視する | 提出と配信のステータスを表示し、承認を保証するような表示はしない |

以下は今回は対象外とします：ChurchApps が所有する Twilio の親アカウント、顧客用サブアカウント、番号の購入、Trust Hub への提出、請求、会話受信箱、MMS/WhatsApp、国際送信、フリーダイヤル（トールフリー）の導入。フリーダイヤルは登録の回避策ではなく、別途認証された送信元の経路です。これらの境界により、最初のリリースは B1 の既存の「持ち込みプロバイダー（bring-your-own-provider）」モデルと整合性を保ちます。

## 構成と認証情報の設計

`fromNumber` に多目的な役割を持たせたり、API キーの文字列に構造化データを格納したりするのではなく、明示的で追加型の構成項目を使用します：

| フィールド | 提案する目的 |
|---|---|
| `accountSid` | 教会が所有する Twilio のアカウント／プロジェクト識別子（`AC…`） |
| `apiKey`, `apiSecret` | 送信 API アクセス用の専用 Twilio API キー SID（`SK…`）とシークレット。暗号化・マスク表示される |
| `webhookAuthToken` | Twilio SDK が受信署名を検証するのに使うアカウントの Auth Token。別途暗号化・マスク表示される |
| `messagingServiceSid` | 教会の Messaging Service（`MG…`、34文字） |
| `fromNumber` | 選択された SMS 対応番号（E.164 形式）。そのアカウント／サービスで送信元として認証済みであること |
| プログラム構成 | 安定したプログラム ID、名前、許可される目的、登録／ポリシーの URL、開示バージョン |

Twilio は [REST 認証に API キーを推奨しています](https://www.twilio.com/docs/iam/api-keys)。送信と必要な読み取り専用のセットアップ確認をカバーする、テスト済みの最小権限のキー権限を使用してください。Webhook の [標準の Twilio 署名検証](https://www.twilio.com/docs/usage/security) には、依然としてアカウントの Auth Token が必要です。この違いを UI で説明してください。API シークレットは Webhook の Auth Token ではありません。認証情報は、サーバー側の設定ストアにのみ保持し、公開ページ、フォームの回答、ブラウザからの送信リクエスト、サポート issue には決して含めないでください。

教会は Console でこれらのリソースを作成・管理します。B1 の検証アクションは、構成済みのサービス、送信元、登録情報を読み取るだけにすること。番号の購入、キャンペーンの作成、Twilio 設定の変更、副作用としてのテスト送信を行ってはなりません。適格で同意済みの受信者に限定した、別途の明示的なテスト送信アクションを提供してください。

保存済みの同じプロバイダーを編集する場合にのみ、マスク済みの認証情報を保持してください。Twilio に切り替える場合は、専用の認証情報が必要で、古いプロバイダー固有の値は明確にクリアすること。マスク済みの Clearstream や Nalo のキーを Twilio の構成に持ち越してはなりません。

すべての読み込み・更新は、認証済みの B1 教会にスコープを限定してください。コールバックは保存済みの連携、想定される Twilio のアカウント／サービス／送信元に紐付け、教会をまたぐ競合する割り当ては拒否してください。認証情報のローテーションやプロバイダーの切断は、準備状況を無効にし、キュー内の送信を一時停止させる必要がありますが、同意記録や過去の配信記録は消去しないでください。

## 同意と抑止はリリースに必須の作業

Twilio プログラム用に電話番号に紐づく購読レコードを導入し、追記型の同意・抑止イベントを記録します。最低限の証拠として推奨されるのは、教会 ID、プログラム ID、正規化された電話番号、（任意の）検証済みの人物との関連付け、肯定的な操作、送信元のフォーム／送信 ID またはレビュー済みの外部証明、サーバーのタイムスタンプ、開示テキスト／バージョン、送信元 URL、ポリシーの URL、撤回／再開イベントです。アクセスと保持は、既存の教会データセキュリティ方針の下で制限してください。

`unknown`、`pending`、`active`、`suppressed` などの状態を使用します。既存の携帯番号、インポートされた連絡先、出席、寄付、グループ所属、`person.optedOut = false`、`allowSms` は、プログラムへの肯定的な同意ではありません。文書化された同意のインポートは、許可を得た監査可能な操作とし、取得元を記録してください。移行によって全員を登録してはなりません。

最初の Web の流れでは、B1 の標準の公開フォームモードを使用します。明示的に構成された SMS 同意の質問を追加します。質問は、チェックがされていない状態で始まり、任意項目のままとし、クリック可能なポリシーリンクを表示し、1つのプログラムと携帯電話のフィールドに対応づけます。その対応付けをサーバー側で検証し、肯定的な回答を保存する際には表示された開示内容のスナップショットを取得します。任意の質問ラベル、会話型 AI、ワークフローの所属から同意を導出してはなりません。会話型の同等の仕組みは、明示的な肯定的操作と証拠の記録がテストされた後にのみ有効化してください。

チェックされていない送信では購読を作成せず、他人の既存の同意を撤回してはなりません。同意は送信された電話番号に紐づけてください。スタッフは、世帯のレコードを統合することなく、曖昧な人物の関連付けを解決できるようにします。携帯番号が変わった場合は、新たに同意が必要です。匿名フォームでは、悪用対策を適用し、番号の所有確認やダブルオプトインの手順を明示的にしてください。チェックボックスをオンにしただけでは、その電話の持ち主が誰かは証明されません。確認手順を使う場合は、完了するまで購読を保留（pending）のままにし、その正確な流れを登録に関する資料に記載してください。

Twilio については、SMS の抑止とディレクトリの公開設定を分離してください。従来の配信停止は、抑止レコードに保守的に移行します。それ以外の従来の受信者は `unknown` のままにします。明示的で文書化された新規登録によって SMS の同意を確立することはできますが、その場合もディレクトリのプライバシー設定は変更されません。他のプロバイダーの動作は、その移行が別途レビューされるまで維持してください。

実際の送信のたびに、教会の連携が有効／準備完了であること、正確な電話番号に対する現在のプログラムの同意があること、電話番号レベルの抑止がないこと、既存の呼び出し元の権限を確認してください。リマインダーでは、さらに `allowSms`、カテゴリごとの設定、静穏時間（quiet hours）を尊重します。キューに入れた後に再確認し、差し込みフィールドを解決し、番号を正規化して検証し、電話番号で重複排除してください。STOP は、手動送信やワークフローを含め、そのサービス／プログラムのすべての送信を抑止します。また、その電話番号を共有するすべての人物も対象にしなければなりません。

共通の Twilio 送信経路で、教会の識別情報と STOP の案内を一貫して表示し、最終的な SMS／セグメント数をプレビューしてください。差し込みフィールドの展開や文字数の処理では、これらの要素を保持する必要があり、配信停止の案内を黙って切り詰めてはなりません。例と実際のリマインダー／ワークフローのテンプレートは整合させてください。

## Twilio の送信、返信、配信状態

`TwilioProvider.sendMessage` を、選択された Messaging Service と送信元を使って Messages API 経由で実装してください。Twilio の provider message SID と、「受け付け済み／送信済み」の結果を返します。HTTP の受け付けは、端末への配信ではありません。グループ送信では、入力順に受信者ごとの結果を返します。

`sendBulk` と個別送信の**両方**について、送信の並行数を制限してください。現在の差し込みフィールドの分岐は、`sendMessage` の呼び出しを一斉に展開しています。リクエストの予算内に収まらないグループについては、送信の意図と処理可能な作業を永続化してください。教会に別のサービスを動かすことを求めず、既存のデプロイの仕組みを再利用します。既知の一時的な障害やレート制限には、バックオフ付きで再試行してください。タイムアウトによる不確かな結果は、盲目的な再送（重複したテキストや課金のリスク）ではなく、照合すべき不明な結果として扱ってください。

教会ごとに、受信用と状態通知用のコールバック URL を構成してください。`X-Twilio-Signature` を、SDK、正確に構成された外部 URL、元のフォームパラメータ、一致するアカウントの Auth Token を使って検証します。秘密の URL だけでは不十分です。コールバックは、保存済みの教会／アカウント／メッセージのレコードに紐づけ、重複やメッセージの送信結果が確定する前に届くコールバックを扱い、古いイベントが最終状態を上書きしないようにしてください。受信確認には空の TwiML を返し、状態イベントには適切な成功レスポンスを返してください。[Twilio のセキュリティ](https://www.twilio.com/docs/usage/security)、[ステータスのコールバック](https://www.twilio.com/docs/messaging/guides/track-outbound-message-status)

Messaging Service の **Advanced Opt-Out** の利用を推奨します。STOP／START／HELP の確認応答は Twilio が担当し、B1 は認証済みの `OptOutType` イベントを受け取り、重複した確認を送信しません。STOP は直ちに抑止を記録します。START は、既知の購読を、同じ開示済みプログラムに限って復元し、新しい再開イベントを記録します。無関係なメッセージを新しい電話番号に許可したり、リマインダーの設定を有効にしたりしてはなりません。HELP では誰も登録されません。その他の受信返信は B1 の受信箱の範囲外とし、教会が Twilio でそれらを監視するための文書化された方法が必要です。[Advanced Opt-Out](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out)

Twilio のメッセージ SID、アカウント／サービスの紐付け、送信日時、最終的なステータス／エラーコード、コールバックの時刻を、配信ログと一緒に保存してください。キュー済み／受け付け済み、配信済み、失敗、未配信、不明を正確に表示します。他のプロバイダー向けの既存のレスポンス仕様を維持し、集計された成功件数が送信を表すのか配信を表すのかを定義してください。

## セットアップの準備状況と承認の検証

認証情報、サービス／送信元の所有、キャンペーンの認証、番号の登録、Webhook の確認、配信が確認されたテスト送信について、それぞれ個別のチェックポイントを表示してください。認証情報が機能しているだけで、単一の緑色の「承認済み」バッジを表示してはなりません。

米国のローカル番号については、サービスの [Usa2p キャンペーンリソース](https://www.twilio.com/docs/messaging/api/usapptoperson-resource) を読み取り、関連するキャンペーンが `VERIFIED` であることを必須としてください。さらに、選択された電話番号がそのサービスに関連付けられており、番号の登録が完了していることを別途検証します。承認済みのキャンペーンでも、番号は保留中のことがあります。サポートされている読み取り API で必要なシグナルが公開されていない場合は、**Console での手動確認が必要**と表示し、教会の管理者による日付付きの確認を、そのように記録してください。API で検証済みとラベル付けしてはなりません。番号登録のイベントの自動化は、後続の課題にできます。[番号登録のエラー](https://www.twilio.com/docs/api/errors/30035)、[A2P 登録イベント](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/event-streams-setup)

送信を有効にする前に、最新の確認を必須としてください。確認が行われた日時と方法を記録し、古い確認は期限切れにし、認証情報の失効、送信元の変更、登録の失敗、継続的なアカウントエラーがあれば一時停止してください。テスト送信の配信が成功したことは、テストした経路の確認にすぎず、キャリアによる全体的な承認や受信者の同意を証明するものではありません。付随の草案には、教会の送信前、公開前、および運用中の確認項目が定められています。

## リポジトリとリリース計画

[組織の貢献ガイド](https://github.com/ChurchApps/.github/blob/main/CONTRIBUTING.md) では、B1 の機能要望は ChurchAppsSupport に、実装の PR は所有するリポジトリに送るよう定められています。単一の中央の機能要望を作成し、それに焦点を絞った実装 PR をリンクしてください。

1. **ChurchAppsSupport:** Twilio をユーザー向けの利用可能な機能として提示する前に、この設計と、そのオンボーディング草案をレビューする。
2. **Packages:** Twilio アダプター、明示的な共有の構成／インターフェース、そして B1Admin／B1App で共有される SMS 同意フォームの描画を追加する。changeset を含め、利用側を更新する前に既存のリリースワークフローで公開する。
3. **Api:** 連携メタデータ、同意／抑止、配信状態のための追加型マイグレーションを追加する。構成の検証、共通の送信ゲート、フォームの証拠取得、Webhook の処理、ディスパッチの永続化を実装する。
4. **B1Admin:** Twilio の構成／準備状況の UI、プログラムと同意の管理、プロバイダーを考慮した送信元の保存、正確な配信レポートを追加する。通常の人物編集を通じて、SMS 同意の上書きを一切公開しない。
5. **B1App:** 公開フォームとページ、ポリシーリンクの体験を、共有コントロールに対して検証する。匿名の訪問者とモバイルの訪問者を含める。別途の Twilio ブラウザークライアントは不要。
6. **ChurchAppsSupport:** リリース後、オンボーディング草案を正式なセットアップ／ヘルプページに変換し、実際のスクリーンショットを追加し、テキスト設定からリンクし、翻訳を手配する。

利用側より前に、スキーマと共有パッケージをデプロイしてください。Twilio は小規模なオプトインのパイロット向けに機能フラグで制御し、既存のプロバイダーは引き続き動作させます。ロールバックでは、Twilio の送信を無効にし、未送信のジョブをキャンセルしますが、オプトアウトと証拠は保持します。受信者を別のプロバイダーや送信元に自動的に切り替えてはなりません。

## 工数の見積もり

エコシステムに精通した貢献者を想定した計画上の見積もりです。この評価では、本番の認証情報や実際の SMS は使用していません：

| 作業 | 開発者日数 |
|---|---|
| アダプター、構成／スキーマの拡張、設定 UI | 2〜3 |
| 電話番号／プログラムの同意、独立した抑止、共通の送信ゲート、公開フォームの統合 | 3〜5 |
| 署名付きコールバック、配信の永続化、上限付きで耐久性のあるディスパッチ | 2〜3 |
| 準備状況 UI、教会向けガイド、統合・回帰テスト、パイロットの修正 | 3〜4 |
| **推奨するローンチの範囲** | **合計 10〜15** |

基本的なアダプター／設定の概念実証は、およそ1〜2日です。送信元のみの見積もりには、この提案に必要な同意とオンボーディングの作業は含まれていません。Twilio やキャリアによる外部のレビュー時間は別途かかり、変動します。プロジェクトは承認の日付や承認の結果を約束すべきではありません。

## 受け入れ基準

- [ ] 教会がアカウント、サービス、登録済みの送信元、キャンペーンを所有し、その費用を負担する。ChurchApps が管理する Twilio アカウントは不要。
- [ ] 認証情報は暗号化・マスク表示され、テナントに紐づけられ、ローテーション可能で、ログや公開コンテンツには含まれない。検証は読み取り専用である。
- [ ] 任意でチェックされていない同意は、実際のポリシーリンクを表示し、プログラム／電話番号／開示内容の証拠をサーバー側に保存する。同意を拒否しても、フォームの主要な操作は引き続き可能。
- [ ] 手動、グループ、差し込みフィールド、ワークフロー、リマインダーのすべての経路で、同じ Twilio の資格ゲートを適用する。不明、未同意、電話番号が変更された、または抑止された受信者は、有用な理由とともにスキップされる。展開と文字数処理の後も、教会の識別情報と STOP の案内を保持して描画する。
- [ ] 従来のディレクトリのプライバシー設定では、受信者を登録しない。STOP／START はディレクトリの公開状態や無関係な設定を変更しない。電話番号の共有や教会をまたぐケースをテストする。
- [ ] 署名付きの STOP／START／HELP、無効な署名、誤ったアカウント／サービス、重複イベント、フォームの再送、偽造された同意の対応付けを網羅する。
- [ ] グループのサイズとタイムアウト、レート制限、部分的な失敗、不確かな結果、コールバックの競合、順序の狂ったイベントを、重複送信なしでテストする。
- [ ] キャンペーンの承認と番号登録の完了は、認証情報の検証とは別に扱う。手動の証拠は明確にラベル付けする。古い、または失効した準備状況では送信をブロックする。
- [ ] パイロットの教会が、登録ページ、拒否と承諾の両方のフォームの流れ、正確なポリシーの URL、同意済みのテスト受信者について、送信、配信、STOP による抑止、許可された再登録まで確認する。
- [ ] 既存の Clearstream、Text In Church、Nalo の設定と送信動作が回帰テストに合格する。ヘルプの文面で、提案と提供済みの機能を区別する。
