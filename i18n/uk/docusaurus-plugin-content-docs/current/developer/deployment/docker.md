# Самохостинг за допомогою Docker

<div class="article-intro">

Запустіть власний приватний екземпляр B1 Admin, порталу для членів громади та вебсайту B1, API і бази даних MySQL на будь-якій машині з Docker: домашньому сервері, невеликому VPS або локальному пристрої. Одна команда встановлює систему, одна команда оновлює її, і кожне оновлення спочатку створює резервну копію. Якщо ви не хочете самостійно керувати сервером, перегляньте [Самохостинг на Railway](./railway-template) як керований альтернативний варіант.

</div>

## Швидкий старт

<div class="prereqs">
<h4>Що вам потрібно</h4>

- Машина з Linux (або macOS / Windows із WSL чи Git Bash, оскільки допоміжна програма `b1` є скриптом bash) з [Docker Engine](https://docs.docker.com/engine/install/) та Compose v2 (входить до складу Docker Desktop)
- Близько 2 ГБ оперативної пам'яті та 5 ГБ дискового простору
- Для публічного сайту: доменне ім'я, спрямоване на цю машину, з доступними портами 80 і 443

</div>

```bash
curl -fsSL https://raw.githubusercontent.com/ChurchApps/B1Admin/main/deploy/install.sh | bash -s -- --domain church.example.org
```

Якщо не вказувати `--domain`, система працюватиме на `http://localhost`. Установлювач створює папку `b1church`, записує файл `.env` зі щойно згенерованими секретними ключами, завантажує готові образи з GitHub Container Registry і чекає, доки API не повідомить про нормальний стан. Нічого не збирається на вашій машині, тому перший запуск займає хвилину або дві.

Після завершення:

1. Відкрийте **https://church.example.org/admin** (або http://localhost/admin) і натисніть **Register**. Перший обліковий запис автоматично стає адміністратором сервера.
2. Дотримуйтеся підказок у застосунку, щоб створити першу церкву. Її вебсайт і портал для членів одразу стануть доступними за адресою **https://church.example.org/**.

Усе працює за одним доменом:

| Шлях | Сервіс |
|------|---------|
| `/` | B1App — вебсайт церкви та портал для членів |
| `/admin` | B1Admin — панель персоналу |
| `/api` | API, завантажені файли та websocket для оновлень у реальному часі |

HTTPS налаштовується автоматично: вбудований проксі [Caddy](https://caddyserver.com/) отримує та поновлює сертифікат Let's Encrypt для домену, вказаного в `.env`. Назовні відкриті лише порти 80 і 443; до бази даних можна звернутися лише зсередини мережі Docker.

## Команда `b1`

Установлювач залишає скрипт `deploy/b1` поруч із `docker-compose.yml`. Щоденно потрібна лише ця програма:

| Команда | Що робить |
|---------|--------------|
| `./deploy/b1 upgrade` | Завантажує поточний випуск, створює резервну копію, перезапускає систему й перевіряє, що API працює справно |
| `./deploy/b1 upgrade 2026.10.1` | Те саме, але з прив'язкою до конкретного випуску |
| `./deploy/b1 backup` | Зберігає знімок бази даних, завантажених файлів і `.env` у `backups/<timestamp>/` |
| `./deploy/b1 restore backups/<timestamp>` | Відновлює знімок (API зупиняється на час виконання) |
| `./deploy/b1 rollback` | Відновлює останню резервну копію разом із випуском, для якого її було створено |
| `./deploy/b1 status` | Установлена версія та стан контейнерів |
| `./deploy/b1 logs api` | Переглядає журнали сервісу в реальному часі |

Випуски публікуються як один версійований пакет, тож три образи завжди відповідають одне одному. `B1_VERSION=stable` у `.env` відстежує останній випуск; щоб зафіксувати конкретну версію, вкажіть її. Примітки до випусків розміщено в розділі [Випуски B1Admin](https://github.com/ChurchApps/B1Admin/releases).

## Налаштування

Усі параметри зберігаються в `.env` поруч із `docker-compose.yml`. Установлювач заповнює обов'язкові:

```bash
B1_VERSION=stable
DOMAIN=church.example.org
SITE_ADDRESS=church.example.org          # що обслуговує Caddy; http://localhost для локального встановлення
PUBLIC_URL=https://church.example.org    # як браузери та електронні листи дістаються до сайту
MYSQL_ROOT_PASSWORD=…                    # згенеровано
JWT_SECRET=…                             # згенеровано
ENCRYPTION_KEY=…                         # згенеровано, рівно 32 символи — ніколи не змінюйте після збереження облікових даних

# Електронна пошта — настійно рекомендовано; без неї учасники не зможуть скинути власні паролі
MAIL_SYSTEM=SMTP
SMTP_HOST=smtp.resend.com
SMTP_USER=resend
SMTP_PASS=re_xxxxxxxxx
SMTP_SECURE=false
SUPPORT_EMAIL=noreply@church.example.org
```

Після редагування `.env` застосуйте зміни командою `docker compose up -d`. Вебзастосунки самі визначають, до якого API звертатися, за адресою в браузері, тому для зміни домену достатньо оновити `SITE_ADDRESS` і `PUBLIC_URL` та перезапустити систему — перебудова не потрібна.

:::warning
Берігайте `.env` у безпеці. `ENCRYPTION_KEY` захищає збережені облікові дані платіжних шлюзів і сховища; резервна копія без нього не зможе їх розшифрувати. `./deploy/b1 backup` із цієї причини включає копію ключа.
:::

### Перехід на домен пізніше

Якщо ви встановили систему на `localhost` і згодом хочете зробити її публічною: спрямуйте DNS на цю машину, укажіть у `.env` значення `DOMAIN`, `SITE_ADDRESS` (голий домен) і `PUBLIC_URL` (`https://` + домен), а потім виконайте `docker compose up -d`. Caddy отримає сертифікат із першим запитом.

## Електронна пошта, пожертви, кілька сайтів та інтеграції

Ці функції працюють так само, як на Railway: ті самі змінні середовища, але задані в `.env`, а не на панелі Railway:

- **[Електронна пошта / SMTP](./railway-template#1-email-highly-recommended)** — покрокові інструкції для Resend, Brevo та Gmail
- **[Кілька сайтів](./railway-template#3-multi-site-multiple-churches-on-one-instance)** — необмежена кількість церков в одному екземплярі. `/` обслуговує церкву, чий slug дорівнює `DEFAULT_CHURCH_SLUG` (перша церква має slug `church`); спрямуйте додаткові домени на цю машину й прив'яжіть їх у **Settings → Domains** у B1Admin
- **[Онлайн-пожертви](./railway-template#4-online-giving-stripe--paypal)** — налаштовуються для кожної церкви в адміністративному інтерфейсі
- **[Додаткові інтеграції](./railway-template#6-optional-feature-integrations)** — `OPENAI_API_KEY`, `YOUTUBE_API_KEY`, `PEXELS_KEY`, `VIMEO_TOKEN`, `API_BIBLE_KEY`, `GOOGLE_RECAPTCHA_SECRET_KEY`
- **[Push-сповіщення](#push-notifications)** — `WEB_PUSH_*`; установлювач залишає ці поля порожніми, тому push-сповіщення вимкнені, доки ви їх не додасте

Запрошення та інші електронні листи, які надсилає церква, на самохостингу вмикаються автоматично (хостингова служба вмикає їх лише після ручної перевірки, щоб захистити репутацію відправника).

## Push-сповіщення

Push-сповіщення у браузері та мобільному вебзастосунку залишаються вимкненими, доки на сервері немає пари ключів VAPID. Установлювач її не створює. Поки ви її не додасте, сторінка сповіщень мобільного вебзастосунку повідомлятиме, що push-сповіщення для сайту не увімкнено.

1. Згенеруйте пару ключів. Для цього потрібен лише Docker:

   ```bash
   docker run --rm node:lts-alpine npx --yes web-push generate-vapid-keys
   ```

2. Додайте два значення в `.env`. `WEB_PUSH_SUBJECT` необов'язковий і містить контактну адресу, яку бачать служби push-сповіщень:

   ```bash
   WEB_PUSH_PUBLIC_KEY=…
   WEB_PUSH_PRIVATE_KEY=…
   WEB_PUSH_SUBJECT=mailto:admin@example.org
   ```

3. Застосуйте зміни:

   ```bash
   docker compose up -d
   ```

4. Щоб перевірити, відкрийте **Server Admin → Server Health** у B1Admin. Обидва ключі Web Push мають відображатися як налаштовані. Після цього учасники зможуть увімкнути сповіщення в мобільному вебзастосунку.

:::warning
Після того як учасники підключилися, не змінюйте ключі. Їх зміна робить недійсними всі наявні підписки, і кожному пристрою доведеться зареєструватися знову.
:::

## Дані, резервні копії та зберігання файлів

Три іменовані томи Docker зберігають усі дані:

| Том | Вміст |
|--------|----------|
| `b1church_mysql-data` | Усі схеми бази даних |
| `b1church_api-content` | Завантажені файли — фотографії, документи, зображення для вебсайту |
| `b1church_caddy-data` | Сертифікати TLS |

`./deploy/b1 backup` створює узгоджений знімок перших двох томів разом із `.env` у `backups/<timestamp>/`. Налаштуйте його запуск через cron і копіюйте папку на іншу машину:

```
0 3 * * * cd /opt/b1church && ./deploy/b1 backup >> backups/backup.log 2>&1
```

Для великих медіатек можна перевести зберігання файлів на S3 — установіть `FILE_STORE=S3` і змінні `AWS_*`, описані в розділі [Зберігання файлів](./railway-template#5-file-storage) посібника для Railway. Резервні копії бази даних не включають об'єкти S3; увімкніть версіонування для бакета.

## Оновлення

```bash
./deploy/b1 upgrade
```

Команда виконує такі кроки: завантажує випуск, створює резервну копію, перестворює контейнери, запускає будь-які очікувані міграції бази даних під час запуску API і чекає на перевірку його стану. Якщо щось іде не так, команда зупиняється і пропонує виконати `./deploy/b1 rollback`, яка відновлює цю резервну копію та попередній випуск. Міграції працюють лише в один бік; відкат завжди означає відновлення знімка.

Оновлення з бета-версії файлу compose (того, що збирав образи з вихідного коду) працює так само, щойно у вас є `.env`: раніше за замовчуванням використовувався `MYSQL_ROOT_PASSWORD=churchapps`, тож додайте це значення в `.env` разом із `PUBLIC_URL` і `SITE_ADDRESS`, замініть `docker-compose.yml` і `deploy/` поточними файлами та виконайте `./deploy/b1 upgrade`.

## Збирання із вихідного коду

Розробники можуть збирати образи локально замість їх завантаження:

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

`API_CONTEXT` і `B1APP_CONTEXT` у `.env` вказують збиркам на локальні копії репозиторіїв (наприклад, `../Api`) або на git-посилання.

## Усунення несправностей

| Симптом | Імовірна причина | Рішення |
|---------|--------------|-----|
| Контейнер `api` постійно перезапускається | помилка міграції або неправильний пароль до бази даних | `./deploy/b1 logs api` — міграція виводить, який модуль не вдався |
| `api` у журналі: "ENCRYPTION_KEY must be exactly 32 characters" | ключ у `.env` змінено вручну або обрізано | відновіть оригінальний 32-символьний ключ (створюйте новий, лише якщо облікових даних ще не збережено) |
| Браузер показує попередження про сертифікат | DNS ще не вказує сюди або порти 80/443 заблоковано | виправте DNS або брандмауер; Caddy повторює спробу автоматично |
| `/` показує панель керування замість вебсайту | церкву ще не створено або `DEFAULT_CHURCH_SLUG` не збігається | створіть церкву або встановіть slug у **Settings → Church** |
| Повідомлення "Check your email", але лист не надходить | `MAIL_SYSTEM=SMTP` з неправильними обліковими даними | виправте облікові дані або видаліть `MAIL_SYSTEM`, щоб вимкнути електронну пошту |
| Мобільний вебзастосунок повідомляє, що push-сповіщення не увімкнено | на сервері немає ключів VAPID | додайте їх, як описано в розділі [Push-сповіщення](#push-notifications) |
| Чат і функції реального часу не працюють | websocket блокується іншим проксі перед системою | сокет працює за шляхом `/api/` на тому самому порту; дозвольте заголовки `Upgrade` |
| `install` відмовляється: "database volume already exists" | залишки від попереднього встановлення | виконайте `docker compose down -v`, щоб видалити дані, або створіть `.env` і використовуйте `upgrade` |

Усе ще не вдається розв'язати проблему? Створіть issue на [github.com/ChurchApps/ChurchAppsSupport/issues](https://github.com/ChurchApps/ChurchAppsSupport/issues) і додайте результат команди `./deploy/b1 logs`.
