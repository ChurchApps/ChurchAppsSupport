# Пропозиція щодо інтеграції Twilio BYOK

:::caution Пропозиція — інтеграція, яка наразі недоступна
Це проєкт для розгляду мейнтейнерами, підготовлений на основі публічного коду та документації Twilio, переглянутих 22 жовтня 2026 року. Відтоді було випущено базового провайдера Twilio (`@churchapps/texting` 0.6.0 та **Settings > Texting** у B1 Admin): церква вводить свій Account SID, Auth Token і номер відправника (From). Провайдер також приймає Messaging Service SID, що починається з `MG`, але стовпець `fromNumber` досі має тип `varchar(20)`, що закороткий для 34-символьного SID. Повідомлення надсилаються окремим запитом для кожного одержувача через Messages API Twilio, а відповіді STOP потрапляють до B1 через наявний вхідний webhook. Див. [Налаштування церкви: Texting](../../b1-admin/settings/church-settings.md#texting). Модель згоди, обробка розширеного відмовлення (Advanced Opt-Out), статус доставки та перевірки готовності налаштування, описані нижче, усе ще є пропозиціями, а не реалізованою поведінкою. Супровідний [проєкт налаштування для церков](./twilio-byok-onboarding-draft) містить запропоновані інструкції з налаштування та приклади для церков.
:::

## Рекомендований шлях

Додайте Twilio до наявної системи провайдерів текстових повідомлень B1, використовуючи **обліковий запис Twilio, що належить церкві, облікові дані API, Messaging Service і номер телефону з підтримкою SMS**. Церква реєструє свою юридичну особу та кампанію розсилки, сплачує Twilio напряму, веде облік згоди одержувачів і керує схваленням у Twilio Console. ChurchApps надає інтеграцію та документацію.

Почніть з однієї програми повідомлень, однієї Messaging Service і одного місцевого американського відправника 10DLC на кожну церкву B1. Підтримуйте індивідуальні повідомлення, групові повідомлення, повідомлення робочих процесів і нагадування про підписку через наявні екрани B1. Розумна перша програма охоплює зміни в богослужіннях, нагадування про заходи та планування волонтерів, за умови що всі три описані в згоді цієї церкви та схваленій кампанії. Фандрейзинг або рекламні повідомлення потребують окремо оціненого обсягу та окремої згоди; не додавайте їх до цієї програми без попередження.

| Обов'язок | Церква | B1 / ChurchApps |
|---|---|---|
| Обліковий запис Twilio, оплата, володіння номерами | Володіє та адмініструє їх | Не надає платформний обліковий запис і не перепродає кредити |
| Реєстрація бренду, кампанії, номера | Подає точну інформацію про церкву; опрацьовує перевірку та виправлення | Пояснює передумови та показує наявну інформацію про готовність |
| Сторінка підписки, політики, призначення повідомлень | Публікує та підтримує їх | Надає сумісні елементи форм, приклади та записи про згоду |
| Відповідність одержувачів і обробка STOP | Перевіряє докази згоди та запитує відгуки, отримані поза SMS | Забезпечує дотримання згоди, блокування, дозволів і підписаних webhook |
| Доставка та підтримка | Стежить за помилками Twilio, станом облікового запису та вхідними відповідями | Показує статус подання та доставки, не обіцяючи гарантій схвалення |

Відкладіть: ChurchApps-керований батьківський обліковий запис Twilio, субакаунти клієнтів, придбання номерів, подання до Trust Hub, оплату, інбокс розмов, MMS/WhatsApp, міжнародну відправку та онбординг toll-free. Toll-free — це окремий шлях перевіреного відправника, а не обхід реєстрації. Ці межі узгоджують перший випуск із наявною моделлю B1 «власний провайдер».

## Конфігурація та дизайн облікових даних

Використовуйте явні додаткові поля конфігурації, а не перевантажуйте `fromNumber` і не зберігайте структуровані дані в рядку ключа API:

| Поле | Запропоноване призначення |
|---|---|
| `accountSid` | Ідентифікатор облікового запису або проєкту Twilio, що належить церкві (`AC…`) |
| `apiKey`, `apiSecret` | Ідентифікатор ключа API Twilio (`SK…`) і секрет для вихідного доступу до API; зашифровані та замасковані |
| `webhookAuthToken` | Auth Token облікового запису, який SDK Twilio використовує для перевірки вхідних підписів; окремо зашифрований і замаскований |
| `messagingServiceSid` | Messaging Service церкви (`MG…`, 34 символи) |
| `fromNumber` | Вибраний номер з підтримкою SMS у форматі E.164, перевірений як відправник в цьому обліковому записі або сервісі |
| Конфігурація програми | Стабільний ID програми, назва, дозволені призначення, URL підписки та політик, версія розкриття |

Twilio [надає перевагу ключам API для автентифікації REST](https://www.twilio.com/docs/iam/api-keys). Використовуйте найвужчі протестовані дозволи ключа, які покривають відправку та потрібні для читання перевірки налаштування. Auth Token облікового запису все ще потрібен для [стандартної перевірки підпису webhook Twilio](https://www.twilio.com/docs/usage/security). Поясніть цю різницю в інтерфейсі: секрет API не є Auth Token для webhook. Зберігайте облікові дані виключно в серверному сховищі налаштувань, ніколи на публічних сторінках, у відповідях форм, запитах відправки з браузера чи у зверненнях до підтримки.

Церква створює й керує цими ресурсами в Console. Кнопка перевірки B1 має лише читати налаштований сервіс, відправників і реєстраційні дані. Вона не повинна купувати номери, створювати кампанії, змінювати налаштування Twilio або надсилати тестове повідомлення як побічний ефект. Окрема явна дія тестової відправки має бути обмежена одним придатним одержувачем, який дав згоду.

Зберігайте замасковані облікові дані лише під час редагування того самого збереженого провайдера. Перехід на Twilio має вимагати власних облікових даних і очищати застарілі значення, специфічні для провайдера. Не переносьте замаskovany ключ Clearstream або Nalo в конфігурацію Twilio.

Обмежуйте кожне завантаження та оновлення автентифікованою церквою B1. Прив'язуйте callback-и до збереженої інтеграції та очікуваних облікового запису, сервісу чи відправника Twilio, і відхиляйте конфліктні міжцерковні призначення. Ротація облікових даних і відключення провайдера мають анулювати готовність і призупиняти черговані відправки, не стираючи записів згоди та історії доставки.

## Згода та блокування: обов'язкова робота для випуску

Запровадьте записи підписки, прив'язані до телефону, для програми Twilio, а також append-only події згоди та блокування. Запропонований мінімум доказів: ID церкви, ID програми, нормалізований телефон, необов'язковий перевірений зв'язок з особою, явна дія, ID форми або подання чи перевірений зовнішній доказ, серверна мітка часу, текст і версія розкриття, URL джерела, URL політик і події відкликання або відновлення. Обмежуйте доступ і строк зберігання відповідно до наявної політики безпеки даних церкви.

Використовуйте стани `unknown`, `pending`, `active` і `suppressed`. Наявні мобільні номери, імпортовані контакти, відвідуваність, пожертви, членство в групах, `person.optedOut = false` і `allowSms` не є явною згодою на програму. Імпорт задокументованої згоди має бути дозволеною та аудитованою дією із записаним джерелом; міграція не повинна зараховувати всіх.

Для початкового веб-процесу використовуйте стандартний режим публічної форми B1. Додайте явно налаштоване питання про згоду на SMS, яке починається непозначеним, залишається необов'язковим, відображає посилання на політики, що клікаються, і відповідає одній програмі та одному полю мобільного телефону. Перевіряйте це зіставлення на сервері та зберігайте знімок показаного розкриття під час збереження ствердної відповіді. Ніколи не виводьте згоду з довільних міток питань, розмовного ШІ чи членства в робочому процесі. Розмовний еквівалент вмикайте лише після тестування його явної ствердної взаємодії та запису доказів.

Непозначене подання не створює підписки і не має відкликати чужу наявну згоду. Прив'язуйте згоду до поданого телефону; персонал може вирішувати неоднозначні зв'язки з особами без об'єднання домогосподарств. Змінений мобільний номер потребує власної згоди. Для анонімних форм застосовуйте засоби захисту від зловживань і явно вказуйте будь-яку перевірку володіння номером або кроки подвійного підтвердження. Самого позначеного прапорця недостатньо, щоб довести, хто володіє телефоном. Якщо використовується підтвердження, залишайте підписку у стані очікування до його завершення і точно описуйте цей процес у реєстраційних матеріалах.

Для Twilio відокремте блокування SMS від видимості в каталозі. Консервативно перенесіть будь-яку застарілу відмову в запис блокування; інших застарілих одержувачів залишайте `unknown`. Явна, задокументована нова підписка може встановлювати згоду на SMS, тоді як приватність каталогу залишається незмінною. Поведінку інших провайдерів зберігайте, доки їхні міграції не будуть окремо переглянуті.

При кожній фактичній відправці вимагайте, щоб інтеграція церкви була увімкнена та готова, щоб була чинна згода на програму для точного телефону, не було блокування на рівні телефону і діяв наявний дозвіл викликаючого. Нагадування додатково враховують `allowSms`, налаштування категорій і тихі години. Повторно перевіряйте після постановки в чергу, розв'язуйте поля підстановки, нормалізуйте та перевіряйте номери та видаляйте дублікати за телефоном. STOP блокує всі відправки для сервісу або програми, включно з ручними відправками та робочими процесами; це також має охоплювати кожну особу, що має той самий телефон.

Відображайте ідентичність церкви та інструкцію STOP послідовно в спільному шляху відправки Twilio і показуйте попередній перегляд остаточної кількості SMS та сегментів. Розкриття полів підстановки та обробка довжини мають зберігати ці елементи; не обрізайте мовчки інструкцію про відмову. Тримайте приклади та фактичні шаблони нагадувань і робочих процесів узгодженими.

## Відправки Twilio, відповіді та стан доставки

Реалізуйте `TwilioProvider.sendMessage` через Messages API з вибраним Messaging Service і відправником. Поверніть SID повідомлення провайдера та результат «прийнято або подано»; прийняття HTTP не означає доставку на телефон. Групова відправка використовує результати для кожного одержувача в порядку вхідних даних.

Обмежуйте паралельність вихідних повідомлень для **і** `sendBulk`, і окремих відправок: поточна гілка злиття полів розгалужує виклики `sendMessage`. Зберігайте намір відправки та заявки на роботу для груп, які не вміщаються в бюджет одного запиту. Повторно використовуйте наявну модель розгортання, а не вимагайте від церков запускати ще один сервіс. Повторюйте спроби при відомих тимчасових помилках або обмеженнях частоти з відстроченням. Тайм-аути з невизначеним результатом вважайте невідомими результатами для звірки, а не вказівкою сліпо повторно надсилати та ризикувати дублікатами повідомлень і стягнень.

Налаштуйте URL вхідних callback-ів і callback-ів статусу для конкретної церкви. Перевіряйте `X-Twilio-Signature` за допомогою SDK, точного налаштованого зовнішнього URL, оригінальних параметрів форми та відповідного Auth Token облікового запису. Самого секретного URL недостатньо. Зіставляйте callback-и зі збереженими записами церкви, облікового запису чи повідомлення, обробляйте дублікати та callback-и, що приходять до фіксації результату відправки, і не дозволяйте старішим подіям перезаписувати кінцевий статус. Для вхідного підтвердження повертайте порожній TwiML, а для подій статусу відповідну успішну відповідь. [Безпека Twilio](https://www.twilio.com/docs/usage/security), [callback-и статусу](https://www.twilio.com/docs/messaging/guides/track-outbound-message-status)

Рекомендуйте **Advanced Opt-Out** для Messaging Service. Twilio відповідає за підтвердження STOP, START і HELP; B1 обробляє автентифіковані події `OptOutType` і не надсилає дубльованих підтверджень. STOP одразу записує блокування. START відновлює лише відому підписку на цю саму задекларовану програму з новою подією відновлення; він не має підписувати новий телефон на непов'язані повідомлення або вмикати параметри нагадувань. HELP нікого не підписує. Інші вхідні відповіді залишаються поза межами інбоксу B1; церквам потрібен задокументований спосіб відстежувати їх у Twilio. [Advanced Opt-Out](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out)

Зберігайте SID повідомлення Twilio, прив'язку облікового запису або сервісу, час подання, кінцевий статус і код помилки, а також час callback-у разом з журналом доставки. Точно відображайте стани «у черзі або прийнято», «доставлено», «помилка», «не доставлено» або «невідомо». Зберігайте наявний контракт відповіді для інших провайдерів і визначте, чи сукупні показники успіху означають подання чи доставку.

## Готовність налаштування та перевірка схвалення

Показуйте окремі контрольні пункти для облікових даних, володіння сервісом і відправником, перевірки кампанії, реєстрації номера, перевірок webhook та успішного пробного тесту доставки. Ніколи не показуйте єдиний зелений значок «схвалено» лише тому, що облікові дані працюють.

Для місцевих американських номерів прочитайте [ресурс кампанії Usa2p](https://www.twilio.com/docs/messaging/api/usapptoperson-resource) сервісу та вимагайте, щоб відповідна кампанія мала статус `VERIFIED`. Окремо перевірте, що вибраний телефон пов'язаний із цим сервісом і завершив реєстрацію номера: схвалена кампанія може мати номер в очікуванні. Якщо підтримуваний API читання не показує потрібного сигналу, позначайте **потрібна ручна перевірка в Console** і записуйте датоване підтвердження адміністратора церкви як таке. Не позначайте це як перевірене через API. Автоматичні події реєстрації номерів можна додати пізніше. [Помилки реєстрації номерів](https://www.twilio.com/docs/api/errors/30035), [події реєстрації A2P](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/event-streams-setup)

Вимагайте актуальних перевірок перед увімкненням відправок. Фіксуйте, коли і як перевірялася готовність, перестаньте вважати застарілі перевірки дійсними та призупиняйте відправки при відкликаних облікових даних, змінених відправниках, помилках реєстрації або стійких помилках облікового запису. Успішна доставка пробного повідомлення підтверджує лише протестований шлях, а не загальне схвалення оператором зв'язку чи згоду одержувача. Супровідний проєкт визначає перевірки церкви перед поданням, перед запуском і під час постійної експлуатації.

## План сховища та випуску

[Настанови щодо внесків в організацію](https://github.com/ChurchApps/.github/blob/main/CONTRIBUTING.md) спрямовують запити на функції B1 до ChurchAppsSupport, а реалізаційні PR до відповідних репозиторіїв. Використовуйте один центральний запит на функцію та пов'язуйте сфокусовані реалізаційні PR із ним:

1. **ChurchAppsSupport:** перегляньте цей проєкт і його проєкт онбордингу, перш ніж представляти Twilio як доступну функцію для користувачів.
2. **Packages:** додайте адаптер Twilio, явні спільні конфігурацію та інтерфейси, а також відображення форми згоди на SMS там, де це спільно використовують B1Admin і B1App. Додайте changeset і публікуйте через наявний робочий процес випуску перед оновленням споживачів.
3. **Api:** додайте адитивні міграції для метаданих інтеграції, згоди та блокування, а також станів доставки. Реалізуйте перевірку конфігурації, спільні гейти відправки, збір доказів з форм, обробку webhook і збереження диспетчеризації.
4. **B1Admin:** додайте UI налаштування та готовності Twilio, керування програмами та згодою, збереження відправника з урахуванням провайдера та точну звітність про доставку. Не надавайте перевизначення згоди на SMS через звичайне редагування особи.
5. **B1App:** перевірте досвід публічної форми, сторінки та посилань на політики відповідно до спільних елементів керування, включно з анонімними відвідувачами та мобільними користувачами. Окремий браузерний клієнт Twilio не потрібен.
6. **ChurchAppsSupport:** після випуску перетворіть проєкт онбордингу на підтримувані сторінки налаштувань і довідки, додайте фактичні скріншоти, посилайтеся на них з налаштувань текстових повідомлень і організуйте переклади.

Розгортайте схему та спільні пакети до споживачів. Тримайте Twilio під функціональним прапорцем для невеликого пілотного запуску з добровільною участю; наявні провайдери мають продовжувати працювати. Відкат вимикає відправку через Twilio і скасовує невідправлені завдання, зберігаючи відмови та докази. Він не повинен автоматично переводити одержувачів до іншого провайдера або відправника.

## Оцінка зусиль

Планова оцінка для учасника, знайомого з екосистемою. Жодних виробничих облікових даних або живих SMS в оцінці не використовувалося:

| Робота | Робочі дні розробника |
|---|---|
| Адаптер, розширення конфігурації та схеми, UI налаштувань | 2–3 |
| Згода на телефон і програму, незалежне блокування, спільні гейти відправки, інтеграція публічної форми | 3–5 |
| Підписані callback-и, збереження доставки, обмежена та довготривала диспетчеризація | 2–3 |
| UI готовності, церковний посібник, інтеграційне та регресійне тестування, виправлення пілоту | 3–4 |
| **Рекомендований обсяг запуску** | **10–15 загалом** |

Базовий проєкт адаптера та налаштувань займає приблизно 1–2 дні. Оцінка лише відправника не включає роботу зі згодою та онбордингом, необхідну для цієї рекомендації. Час зовнішньої перевірки Twilio або оператором зв'язку окремий і змінний. Проєкт не повинен обіцяти дату схвалення або результат схвалення.

## Критерії приймання

- [ ] Церква володіє обліковим записом, сервісом, зареєстрованим відправником і кампанією та оплачує їх. Обліковий запис Twilio, керований ChurchApps, не потрібен.
- [ ] Облікові дані зашифровані та замасковані, обмежені межами церкви, підлягають ротації та відсутні в журналах і публічному вмісті. Перевірка лише читає.
- [ ] Необов'язкова непозначена згода відображає справжні посилання на політики та зберігає на сервері дані про програму, телефон і розкриття. Відмова все одно дозволяє основну дію форми.
- [ ] Усі ручні, групові, підстановки полів, робочі процеси та шляхи нагадувань застосовують однаковий гейт придатності Twilio. Невідомі, без згоди, зі зміненим телефоном або заблоковані одержувачі пропускаються з корисною причиною. Відображення зберігає ідентичність церкви та інструкцію STOP після розкриття та обробки довжини.
- [ ] Застаріла приватність каталогу не підписує одержувачів. STOP і START ніколи не змінюють видимість у каталозі чи непов'язані параметри. Випадки спільного телефону та міжцерковні випадки протестовано.
- [ ] Підписані STOP, START і HELP, недійсні підписи, неправильні облікові записи або сервіси, дубльовані події, повторно надіслані подання форм і підроблені зіставлення згоди охоплені тестами.
- [ ] Розмір групи, тайм-аути, обмеження частоти, часткові збої, неоднозначні результати, гонки callback-ів і події доставки не за порядком протестовано без дублікатів відправок.
- [ ] Схвалення кампанії та завершена реєстрація номера відрізняються від перевірки облікових даних. Ручні докази чітко позначено. Застаріла або відкликана готовність блокує відправки.
- [ ] Пілотна церква перевіряє сторінку підписки, шляхи прийнятої та відхиленої форми, точні URL політик і згоджуючого тестового одержувача через подання, доставку, блокування через STOP і дозволене повторне підписання.
- [ ] Наявні налаштування та поведінка відправки Clearstream, Text In Church і Nalo проходять регресійні перевірки. Текст довідки чітко відрізняє пропозиції від випущених функцій.
