# Маршрутизація вебсайтів і кілька сайтів

<div class="article-intro">

Одна церква тепер може мати кілька окремих вебсайтів, і кожен із них може розміщуватися на піддомені `*.b1.church` або на повністю власному домені церкви. Ця сторінка описує рівень маршрутизації, який працює *під* конструктором: як вхідний запит визначає церкву **і** конкретний сайт, модель даних для кількох сайтів (значення-маркер `siteId`, яке зберігає всі раніше створені сайти без змін) і edge-рівень для власних доменів, тобто самокерований проксі Caddy на EC2, що завершує TLS і перенаправляє кожен домен церкви на відповідний upstream `*.b1.church`. Про те, що відображається після того, як запит визначено, тобто про дерево сторінок, секцій і елементів, читайте [Конструктор вебсайтів](./website-builder.md).

</div>

## Огляд

```
   grace.b1.church              www.gracechurch.org  (власний домен)
   (піддомен b1.church)                   │
          │                               ▼
          │             ┌──────────────────────────────────────────┐
          │             │ Caddy edge — EC2 3.23.251.61              │
          │             │             (proxy.b1.church)             │
          │             │  • завершує TLS (сертифікат LE для домену)│
          │             │  • переписує Host → {sub}.b1.church       │
          │             │  • проксіює запити до B1App               │
          │             └────────────────────┬─────────────────────┘
          │                  Host = {sub}.b1.church
          ▼                                  ▼
   ┌────────────────────────────────────────────────────────────┐
   │ B1App src/middleware.ts                                     │
   │  • завжди: видаляє будь-який x-site від клієнта (анти-підміна)│
   │  • внутрішній Host *.b1.church ⇒ пошук у domains залишається неактивним│
   │  • сирий власний Host (повз Caddy) ⇒ пошук → встановлює x-site│
   └───────────────────────────┬────────────────────────────────┘
                               ▼  next.config.mjs → першa мітка host → /[sdSlug]/…
              ┌─────────────────────────────────────────────────┐
              │ [sdSlug] · ConfigHelper.load(sdSlug)             │
              │   GET /membership/churches/lookup/?subDomain=…   │
              │   → { id, name, subDomain, siteId? }             │
              │   передає ?siteId= в кожен виклик контенту:      │
              │   /content/pages/:id/tree · /globalStyles ·      │
              │   /blocks/public/footer · /links · sitemap       │
              └─────────────────────────────────────────────────┘

  збереження/видалення домену (B1Admin Settings→Domains → POST /membership/domains)
        └─ best-effort CaddyHelper.updateCaddy()  (обгорнуто, некритично, тайм-аут 10 с)
  Caddy сам читає таблицю domains через два анонімні endpoint-и:
        GET /membership/domains/authorize  — `ask` для on-demand TLS (200 відомий / 404 невідомий)
        GET /membership/domains/hostmap    — мапа host→{sub}.b1.church (оновлення кожні 5 хв)
```

Цей рівень тримається на трьох правилах:

1. **Маркер зберігає зворотну сумісність.** `siteId = ''` означає основний сайт. Кожна сторінка, блок, посилання, глобальний стиль і рядок домену, які існували до цієї функції, мають `''` і відображаються так само, як раніше. *Другий* вебсайт — це просто набір рядків з непорожнім `siteId`, а будь-який endpoint контенту, викликаний без `?siteId=`, повертає основний сайт, тобто саме той самий старий запит байт у байт.
2. **Визначення базується на мітці хоста і сходиться до одного результату.** Піддомен `*.b1.church` маршрутизується напряму за своєю міткою хоста. Власний домен переписується на мітку `{sub}.b1.church` на рівні Caddy, ще до того, як B1App його побачить (а middleware з пошуком у БД встановлює заголовок `x-site` як резерв для будь-якого сирого власного `Host`). Обидва шляхи потрапляють в один і той самий маршрут `[sdSlug]` і в один і той самий виклик `churches/lookup`, тож подальше відображення однакове.
3. **Edge-рівень Caddy не зберігає стан і спирається на одне джерело істини.** Власні домени завершуються на самокерованому проксі Caddy на EC2, який переписує кожен домен на upstream `{sub}.b1.church`. Збереження домену викликає один best-effort `CaddyHelper.updateCaddy()`, а Caddy також читає таблицю `domains` напряму (endpoint-и `authorize` і `hostmap` нижче). Таблиця є авторитетною, тож недоступний Caddy ніколи не може призвести до помилки збереження.

## Визначення сайту

### Піддомени `*.b1.church`

`B1App/next.config.mjs` переписує вхідні запити за хостом. Правило хоста з шаблоном `(?<subdomain>.*?)\..*` захоплює **першу мітку** хоста і переписує `/` та `/:path*` на `/{subdomain}`, тобто на сегмент App Router `[sdSlug]`. Отже, `grace.b1.church/about` перетворюється на `/grace/about`.

Всередині `src/app/[sdSlug]/` функція `ConfigHelper.load(sdSlug)` (`src/helpers/ConfigHelper.ts`) викликає `GET /membership/churches/lookup/?subDomain={sdSlug}`. Відповідь `ChurchController.getBySubDomain` тепер має дві гілки:

| Slug збігається з | Відповідь | Значення |
|-------------------|-----------|----------|
| `churches.subDomain` | `{ id, name, subDomain }` | Основний сайт цієї церкви |
| `sites.subDomain` | `{ id, name, subDomain, siteId }` | **Додатковий сайт**: контролер переходить до `sites`, визначає церкву-власника і повертає запитаний slug разом із додатковим `siteId` |

Саме додатковий `siteId` відрізняє запит до додаткового сайту від запиту до основного; решта конвеєра спільна.

Slug, якого немає ні в одній таблиці, повертається як `{}` зі статусом `200`. `ConfigHelper.load` трактує відповідь без `id` як невідомий сайт і викликає `notFound()` із Next, тож невідомий піддомен отримує справжню 404, а не щоразу викликає `/…/undefined`. Маршрут сторінки конструктора будує шлях дерева через `pageTreePath()` (`src/helpers/pageTreePath.ts`), який кодує slug у URL. Завдяки цьому некоректний slug (зворотні слеші, пробіли) дає 404, а не `400` від API, що перетворювалося б на 500.

### Власні домени

Власний домен церкви завершується на **edge-рівні Caddy** (детально описано нижче), який переписує заголовок `Host` на `{sub}.b1.church` сайту перед проксіюванням до B1App. Тож на звичайному шляху B1App отримує *внутрішній* хост `*.b1.church` і визначає його за міткою хоста так само, як рідний піддомен. Пошук у БД middleware не спрацьовує. Файл `src/middleware.ts` все одно виконується на кожному запиті, але з одним постійним завданням і одним резервним:

1. **Завжди** він **видаляє будь-який заголовок `x-site` від клієнта**. Цей заголовок можна підробити як вхідні дані для переписування, і довіряють йому лише тоді, коли його встановлює сам middleware. Саме видалення є справжньою роботою middleware за Caddy.
2. **Резерв, лише для не внутрішнього `Host`**: для сирого власного `Host`, який доходить до B1App *без* переписування Caddy, він викликає `GET /membership/domains/public/lookup/{host}`. Якщо у відповіді є `subDomain`, встановлюється `x-site: {subDomain}.b1.church`. За Caddy ця гілка неактивна, бо `Host` уже має вигляд `*.b1.church`.

Внутрішні хости, а саме `localhost`, `b1.church` і суфікси `.b1.church`, `.localtest.me`, `.localhost`, `.up.railway.app`, `.vercel.app`, повністю пропускають пошук. Вони вже визначені переписуванням за міткою хоста або є хостами попереднього перегляду чи розгортання.

Сам пошук (`DomainRepo.loadByName`) виконує `LEFT JOIN` таблиць `domains → churches` і `domains → sites` та повертає `COALESCE(NULLIF(sites.subDomain,''), churches.subDomain)`, тобто піддомен призначеного додаткового сайту, якщо домен вказує на нього, інакше піддомен церкви. Спочатку шукається точний хост. Якщо він починався з `www.` і нічого не знайдено, пошук виконується **один раз** повторно для голого апекса.

У `next.config.mjs` правила переписування `x-site` розміщені **перед** загальними правилами хоста, тож вони мають пріоритет. `x-site: grace.b1.church` → перша мітка `grace` → `[sdSlug] = grace`, а далі визначення повністю збігається зі шляхом піддомену (той самий `churches/lookup`, той самий `siteId`).

:::info
Заголовок `x-site` ззовні не довіряється. Middleware безумовно видаляє будь-який вхідний `x-site`, перш ніж за потреби встановити власний, а правила переписування бачать лише значення, встановлене middleware. Клієнт не може примусово потрапити до контенту іншої церкви, надіславши заголовок.
:::

Дві операційні деталі middleware:

- **Кеш.** Результат для кожного хоста (знайдено *або* підтверджено відсутність, але ніколи мережева помилка) кешується на **10 хвилин** у пам'яті, в `Map`, для кожного ізольованого екземпляра serverless.
- **Matcher.** Matcher навмисно знову включає `/sitemap.xml`, `/robots.txt` і `/manifest.webmanifest`. Його перший шаблон виключає шляхи з крапкою, які інакше відкинули б ці файли. Їх повертають назад, щоб власний домен церкви також отримував заголовок `x-site` для своїх SEO- та PWA-файлів.
- **Канонічний заголовок.** Для сторінок церкви middleware додає до відповіді заголовок `Link: <{proto}://{host}{path}>; rel="canonical"`, який вказує хост, з якого фактично віддано сторінку: піддомен або власний домен (`helpers/canonicalLink.ts`). Коли власний домен доходить до B1App через [проксі Caddy](../deployment/caddy-proxy.md), хост запиту є піддоменом `{sub}.b1.church`, тому middleware бере домен відвідувача з `X-Church-Host`. Однак це робиться лише після того, як `/domains/public/lookup/{host}` підтвердить, що домен відповідає тому самому піддомену (`ownsSubdomain()`). Тоді канонічне посилання, `robots.txt` і `sitemap.xml` вказують на власний домен, а не на піддомен `b1.church`. На нерелевантних хостах (`b1.church`, `localhost`, `*.vercel.app`, `*.up.railway.app`), а також для `/mobile`, `/login`, `/logout` і згенерованих файлів robots/sitemap/manifest це не виконується.

### Вимкнений публічний вебсайт

Церква може увімкнути **Disable Public Website** у B1Admin (налаштування контенту на рівні церкви `hidePublicSite = "true"`). Тоді сайт показує лише маршрути для членів:

- **Middleware B1App** шукає піддомен (спочатку `/membership/churches/lookup`, потім `/content/settings/public/:churchId`) і перенаправляє анонімні запити до будь-якого шляху поза дозволеним списком на `/login?returnUrl={path}{query}`. Дозволений список (`helpers/publicSite.ts`) включає `/login`, `/logout`, `/mobile/*`, `/register/*`, `/guest-register`, а також файли manifest/robots/sitemap. Кешуються лише підтверджені відповіді: 60 секунд у production, оскільки виклик revalidate з адмінки не може очистити цю мапу для окремого екземпляра; у dev/test кешування немає. Помилка API призводить до показу сайту, а не до блокування всіх відвідувачів.
- **Авторизовані члени бачать повний сайт.** Запит із чинним cookie `jwt` (функція `hasSession()` middleware декодує поле `exp` корисного навантаження без перевірки підпису, тож це м'який бар'єр, а не контроль доступу) пропускає перенаправлення. Після входу член повертається на сторінку, яку запитував, і бачить звичайні сторінки, вбудовані сторінки (Groups, Sermons тощо) та навігацію в заголовку. Компоненти сторінок і `Header` більше самі не перевіряють `hidePublicSite`.
- **`robots.txt`** забороняє все, як і на хостах з noindex.
- **API.** `GET /content/pages/public/:churchId` (список сторінок для sitemap) повертає `[]`, тож анонімні клієнти не можуть отримати список сторінок.

### Передача `siteId`

`ConfigHelper` зберігає визначений `siteId` у своєму `ConfigurationInterface` для кожного запиту (мемоізовано через `cache()` з React) і додає `?siteId=` до викликів контенту, які він робить, та до викликів, які роблять компоненти сторінок. Це **умовно**: порожній `siteId` (піддомен основної церкви) взагалі не додає параметр. Endpoint-и, які отримують цей параметр: дерево сторінок (`/content/pages/:id/tree`), публічний список сторінок для sitemap (`/content/pages/public/:id`), глобальні стилі (`/content/globalStyles/church/:id`), посилання навігації (`/content/links/church/:id`) і окремий блок футера (`/content/blocks/public/footer/:id`). На звичайному шляху відображення футер приходить всередині дерева сторінок (секції з позначкою `zone: "siteFooter"`), уже отриманий з `siteId`, тож прогалини без області видимості немає.

Портал для членів (B1App `mobile`) навмисно залишається поза цим механізмом: `loadChurchAppearance.ts` визначає церкву через `churches/lookup`, але читає налаштування на рівні церкви з `/settings/public/{id}` і ніколи не передає `siteId`. У версії 1 портал охоплює всю церкву (див. нижче).

## Кілька вебсайтів для однієї церкви

### Модель даних

Нова таблиця `membership.sites` навмисно мінімальна:

| Колонка | Тип | Примітки |
|---------|-----|----------|
| `id` | `char(11)` PK | |
| `churchId` | `char(11)` | Церква-власник |
| `name` | `varchar(255)` | Назва для відображення (наприклад, «Español», «Youth») |
| `subDomain` | `varchar(45)` | **Унікальний індекс**: глобальний простір імен (нижче) |

Прив'язка до сайту визначається одним доданим колонкою у таблицях контенту та доменів, яка не є nullable:

| Таблиця (модуль) | Колонка | Що означає `''` |
|------------------|---------|-----------------|
| `domains` (membership) | `siteId char(11) NOT NULL DEFAULT ''` | Домен обслуговує основний сайт |
| `pages`, `links`, `globalStyles`, `blocks` (content) | `siteId char(11) NOT NULL DEFAULT ''` | Основний сайт. Для **`blocks`** `''` додатково означає *спільний для всіх сайтів* |

Ці зміни додають дві міграції (`tools/migrations/membership/2026-07-02_sites.ts`, `tools/migrations/content/2026-07-02_site_id.ts`). Оскільки колонка за замовчуванням має `''`, кожен наявний рядок зберігає поточну поведінку без заповнення даних.

**Глобальний простір імен піддоменів.** `sites.subDomain` використовує *той самий* простір імен, що й `churches.subDomain`. Піддомен сайту ніколи не може збігтися з піддоменом церкви або з піддоменом іншого сайту. Це перевіряється на **обох** шляхах збереження: `SiteController.save` відхиляє slug, який є в `churches` або `sites`, а `ChurchController.validateSave` робить те саме у зворотному напрямку. Унікальний індекс на `sites.subDomain` забезпечує це на рівні бази даних.

**Унікальність сторінок** розширено з `(churchId, url)` до `(churchId, siteId, url)`, тож два сайти однієї церкви можуть мати кожен власний `/about`.

### Контент для кожного сайту з резервними варіантами

Кожен endpoint списку або дерева, прив'язаний до сайту, приймає необов'язковий `?siteId=` (якщо його немає, береться `''`, тобто основний сайт): дерево сторінок, список і публічні сторінки, списки блоків, блоки за типом і футер, посилання (анонімні, відфільтровані та всі), а також глобальні стилі. Секції та елементи безпосередньо до сайту не прив'язані, вони успадковують його через батьківську сторінку або блок.

Два ланцюжки визначення роблять основну роботу:

- **Глобальні стилі: `сайт → основний → типовий`.** `GlobalStyleRepo.loadForChurch(churchId, siteId)` повертає власний рядок сайту. Якщо у додаткового сайту його немає, повертається **рядок основного сайту (`''`) як є** (зберігаючи його `id`/`siteId`, за якими клієнт виконує копіювання при записі). Якщо немає й основного, `GlobalStyleController` повертає жорстко закодовану типову палітру та шрифти.
- **Блок футера: перевага у сайту, спільний як резерв.** `BlockRepo.loadByBlockType(churchId, "footerBlock", siteId)` повертає спільні рядки (`''`) *і* рядки конкретного сайту. Визначник обирає футер самого сайту, якщо він є, інакше спільний. Та сама логіка виконується і в `TreeHelper.insertBlocks` (дерево сторінки), і в окремому endpoint-і `/content/blocks/public/footer/:churchId`.

### Каскадне видалення сайту

`SiteController.delete` (доступний за дозволом Settings→Edit у membership) видаляє додатковий сайт у три кроки:

1. `ContentModuleGateway.deleteSiteContent(churchId, siteId)` каскадно видаляє весь контент сайту: його **сторінки** разом із секціями, елементами, `pageHistory` і `posts`; його власні **блоки** разом із секціями, елементами і `pageHistory`; його **посилання** та **globalStyles**. Захист не дозволяє виконувати це для `''`: основний або спільний маркер ніколи не видаляється каскадно.
2. `DomainRepo.clearSiteId` **переприв'язує** домени сайту назад до основного (`siteId → ''`), а не видаляє їх, тож власний домен переживає видалення сайту.
3. Рядок `sites` видаляється, а маршрути Caddy повторно синхронізуються (best-effort).

### Інтерфейс B1Admin

| Можливість | Де | Механізм |
|------------|----|----------|
| Перемикач сайтів | `useSiteSelection` + `SiteSwitcher` (порожнє значення = «Main Website») | Читає параметр URL `?site=` і передає його як `?siteId=` у виклики ContentApi. Доступний у трьох розділах **списків** сайтів: **Pages**, **Blocks**, **Appearance**, але *не* в редакторах сторінок і блоків, які зберігають `siteId` у самому записі |
| Створення та видалення сайтів | `SitesDialog`, відкривається з пункту «Manage websites…» у перемикачі | `POST /membership/sites` / `DELETE /membership/sites/:id` (назва і subDomain). Доступ за дозволом Settings→Edit у membership (`Permissions.settings.edit` на сервері; `Permissions.membershipApi.settings.edit` у B1Admin). **Лише створення та видалення: перейменування у версії 1 немає** |
| Призначення сайту для домену | `DomainSettingsEdit` у Settings→Domains | Випадаючий список сайту для кожного рядка надсилає `siteId` для кожного домену до `/membership/domains`. Стовпець приховується, якщо API не повертає сайтів (старіша версія бекенду) |
| Копіювання при записі для стилів | `StylesManager.prepareForSave` | Якщо `siteId` завантаженого рядка глобальних стилів не збігається з вибраним сайтом (тобто API повернув успадкований основний як резерв), він видаляє `id` основного і ставить поточний `siteId`. Це примушує **додати** новий рядок для конкретного сайту замість перезапису основного. Така сама логіка розгалуження при невідповідності застосовується й до блоку футера сайту |

:::info
**Що у версії 1 залишається для всієї церкви (свідомий вибір області, а не обмеження моделі даних):** **блог** (`BlogPage` не має перемикача і завантажує `/posts` без `siteId`), **віджети сайту** (банер оголошень і кнопка запуску), **переадресації**, **логотип, GA4 і налаштування церкви** та **портал для членів** (мобільний B1App). Це *не* означає «весь Appearance»: глобальні стилі додаткового сайту (палітра, шрифти, типографіка, відступи, навігація, власний CSS) **є** окремими для кожного сайту через описаний вище механізм копіювання при записі. Лише підрозділи банера, кнопки запуску, переадресацій і логотипу на сторінці Appearance залишаються для всієї церкви.
:::

## Власні домени: edge Caddy (план статичної конфігурації)

:::info
**Напрям переглянуто 2026-07-02.** Раніше планували перенести хостинг власних доменів на домени, керовані Vercel. Цей план **скасовано**, а весь код реєстрації доменів у Vercel (`VercelHelper`, його змінні середовища `vercelToken`/`vercelProjectId`/`vercelTeamId`, параметри SSM і записи перевірки стану) було видалено з Api. Самокерований **проксі Caddy на EC2 залишається** постійним edge-рівнем для власних доменів. Залишилася лише внутрішня робота: замінити *динамічну* конфігурацію Caddy через admin API на *статичну*, яка переживає перезапуски.
:::

### Edge

Кожен власний домен церкви спрямовує DNS на одну машину EC2: `3.23.251.61`, яка також доступна як `proxy.b1.church`. Екран Settings→Domains в B1Admin підказує церквам додати апекс `A → 3.23.251.61` або `CNAME → proxy.b1.church`. Caddy завершує TLS за допомогою сертифіката Let's Encrypt для кожного домену, переписує заголовок `Host` на upstream `{sub}.b1.church` домену та проксіює запити до B1App. B1App далі маршрутизує їх за міткою хоста, як і будь-який рідний піддомен (див. [Власні домени](#custom-domains) вище).

Відповідність upstream береться з `DomainRepo.loadPairs`. Його вираз dial **об'єднує (COALESCE) піддомен призначеного сайту**, тож домен проксіюється на правильний *додатковий* сайт, а якщо його немає, на основний сайт церкви:

```sql
CONCAT(COALESCE(NULLIF(s.subDomain,''), c.subDomain), '.b1.church:443')  AS dial
WHERE d.domainName NOT LIKE '%www.%'
```

Рядки `www.*` виключено з мапи. Caddy обслуговує `www.{host}` через перенаправлення `302` на апекс.

### Два анонімні endpoint-и для edge

`DomainController` надає два неавтентифіковані endpoint-и лише для читання, які безпосередньо використовує машина: вони анонімні, бо edge звертається до них до того, як з'явиться будь-який контекст церкви:

| Endpoint | Повертає | Роль |
|----------|----------|------|
| `GET /membership/domains/authorize?domain=` | `200`, якщо домен (або, у разі промаху для `www.`, його голий апекс) існує в `domains`; інакше `404` (включно з порожнім `domain`) | `ask` для on-demand TLS у Caddy: механізм захисту від зловживань, який вирішує, чи видавати сертифікат для вхідного SNI |
| `GET /membership/domains/hostmap` | `text/plain`, по одному відсортованому рядку `{domain} {sub}.b1.church` для кожного домену, який можна маршрутизувати | Файл мапи host→upstream, який машина оновлює за таймером |

`authorize` повторно використовує `DomainRepo.loadByName` (точний хост, потім одна повторна спроба для `www.`→апекс). `hostmap` повторно використовує `loadPairs`, тож він враховує сайти, виключає `www.*` і цілком збігається з маршрутами проксі. Далі він просто відкидає суфікс `:443`.

### Збереження та видалення домену: один best-effort запит

`DomainController.save` записує рядки `domains`, а потім виконує **один best-effort** виклик `CaddyHelper.updateCaddy()`, обгорнутий у `try/catch`, який записує помилку (`console.error`) і ігнорує її. `delete` робить те саме (це також усунуло попередню помилку застарілого маршруту при видаленні), як і видалення додаткового сайту (`SiteController.delete`). Сам `updateCaddy` обмежений тайм-аутом Axios **10 с**, тож недоступний або зупинений Caddy ніколи не може призвести до помилки `500` при збереженні домену. Авторитетним джерелом є таблиця `domains`.

### Поточний стан: статична конфігурація, без стану під час роботи

Машина (EC2 під Windows з постійною Elastic IP) запускає Caddy зі **статичного Caddyfile**: on-demand TLS, чий `ask` вказує на `/membership/domains/authorize`, а також файл мапи host→upstream, який оновлюється кожні 5 хвилин з `/membership/domains/hostmap` запланованим завданням, що завершується коректним `caddy reload`. Конфігурація переживає перезапуски без жодного стану під час роботи, без процедури повторного «прогріву». Невідомий SNI **відхиляється на рівні TLS** (сертифікат для хоста, який відхилив `authorize`, не створюється), а авторизований, але ще не доданий до мапи хост (новий домен у вікні синхронізації) отримує чисту 404. Нові домени стають доступними протягом приблизно 5 хвилин після збереження, а їхні сертифікати створюються під час першого звернення. Встановлення та налаштування, експлуатація і перевірені на практиці пастки: [Проксі Caddy для власних доменів](../deployment/caddy-proxy.md).

### Застарілий динамічний push: шлях відкату, очікує видалення

`CaddyHelper` (модуль membership) досі може керувати Caddy через його **admin API** за адресою `caddyHost:caddyPort` (SSM `caddyHost`/`caddyPort`; нічого не робить, якщо їх не задано; виводиться в групі Integrations `ServerHealthController`). `updateCaddy()` виконує PATCH повного масиву маршрутів, а `initializeCaddy()` разом з endpoint-ами `GET /membership/domains/caddy/init` і `GET /membership/domains/caddy` відбудовують сервер з динамічною конфігурацією з нуля. У цьому режимі конфігурація існувала лише в пам'яті Caddy, тобто саме та «втрата пам'яті під час перезапуску», яку замінила ця архітектура. Механізм залишено лише як шлях відкату, і його заплановано видалити після того, як статична машина стабільно працюватиме. Best-effort push `updateCaddy()` під час збереження чи видалення домену нешкідливо нічого не робить зі статичною машиною, бо її admin API доступний лише з localhost.
