# Автентифікація та дозволи

<div class="article-intro">

API ChurchApps використовує автентифікацію на основі JWT. Користувачі входять у систему й отримують токен, який містить їхню ідентичність, членство в церкві та дозволи. Ця сторінка описує процес автентифікації, модель дозволів і підтримку OAuth.

</div>

## Процес входу

### Стандартний вхід

```
POST /membership/users/login
```

**Автентифікація:** Публічний

Приймає один із трьох типів облікових даних:

| Поле | Опис |
|------|------|
| `email` + `password` | Стандартний вхід за електронною поштою та паролем |
| `jwt` | Повторна автентифікація з наявним JWT |
| `authGuid` | Одноразове посилання для автентифікації (використовується в листах із привітанням і скиданням пароля) |

**Відповідь:**

```json
{
  "user": {
    "id": "abc-123",
    "firstName": "Jane",
    "lastName": "Doe",
    "email": "jane@example.com"
  },
  "churches": [
    {
      "church": { "id": "church-1", "name": "First Church", "subDomain": "firstchurch" },
      "person": { "id": "person-1", "membershipStatus": "Member" },
      "groups": [{ "id": "group-1", "name": "Choir", "leader": false }],
      "apis": [
        {
          "keyName": "MembershipApi",
          "permissions": [
            { "contentType": "People", "action": "View" },
            { "contentType": "People", "action": "Edit" }
          ]
        }
      ]
    }
  ],
  "token": "<jwt-token>"
}
```

Поле `token` є JWT, який слід надсилати як `Authorization: Bearer <token>` у наступних запитах.

### Двоетапна перевірка під час входу

Користувачі можуть увімкнути двоетапну перевірку входу через застосунок-автентифікатор (TOTP). Для таких користувачів вхід через `email` + `password`, `authGuid` або SSO не повертає токен. Натомість сервер відповідає запитом на підтвердження:

```json
{ "mfaRequired": true, "mfaToken": "<challenge-token>" }
```

Токен запиту дійсний 5 хвилин. Надішліть його назад на той самий ендпоінт разом із кодом:

```json
{ "mfaToken": "<challenge-token>", "mfaCode": "123456" }
```

`mfaCode` може бути поточним 6-значним кодом автентифікатора або одним із десяти одноразових резервних кодів користувача. Неправильний код повертає `Invalid code`, а повторні невдалі спроби обмежуються за кількістю для кожного облікового запису. Повторний вхід через `jwt` ніколи не вимагає підтвердження, тож наявні сесії продовжують оновлюватися. Об'єкт `user` у відповіді на вхід містить `mfaEnabled`.

Ендпоінти самообслуговування (лише для авторизованого користувача, у межах `/membership/users/mfa`):

| Ендпоінт | Опис |
|----------|------|
| `GET /status` | `{ enabled, backupCodesLeft }` |
| `POST /setup` | Починає налаштування; повертає `{ secret, otpauthUrl }` для QR-коду |
| `POST /enable` | Тіло `{ code }`; вмикає перевірку і один раз повертає `{ backupCodes }` |
| `POST /disable` | Тіло `{ code }` (код автентифікатора або резервний код); вимикає перевірку |
| `POST /reset/:userId` | Лише Server.Admin; вимикає перевірку для іншого користувача |

Секрети зберігаються у зашифрованому вигляді, а резервні коди зберігаються у вигляді хешів. Увімкнення, вимкнення та скидання записуються в журнал аудиту.

### Вміст токена

JWT містить:
- `id` — ідентифікатор користувача
- `churchId` — поточно вибрана церква
- `personId` — запис особи для вибраної церкви
- масиви дозволів для кожного API

### Вибір церкви

Користувачі можуть належати до кількох церков. Відповідь на вхід містить усі церкви з їхніми дозволами. Щоб перемкнути церкву, клієнт створює новий JWT, обмежений іншою церквою, на основі даних відповіді на вхід.

## Реєстрація користувача

### Реєстрація нового користувача

```
POST /membership/users/register
```

**Автентифікація:** Публічний

```json
{
  "email": "jane@example.com",
  "firstName": "Jane",
  "lastName": "Doe",
  "appName": "B1 Admin",
  "appUrl": "https://app.b1.church"
}
```

Створює користувача з тимчасовим паролем і надсилає лист із привітанням та посиланням для автентифікації. Перший користувач, зареєстрований на новому екземплярі, автоматично отримує доступ адміністратора сервера.

Передбачено два необов'язкові поля для захисту від ботів: `website` (прихований поле-приманка, яке справжні користувачі залишають порожнім) і `fillMs` (скільки часу була відкрита форма, у мілісекундах). Якщо `website` заповнено або `fillMs` менше 2000, обліковий запис не створюється, але ендпоінт усе одно повертає звичайну відповідь `200`, щоб боти не могли визначити, що їх відхилено. Клієнти, які не передають обидва поля, реєструються звичайним чином.

### Реєстрація нової церкви

```
POST /membership/churches/add
```

**Автентифікація:** JWT

Після реєстрації користувача викличте цей ендпоінт, щоб створити церкву та пов'язати з нею користувача.

## Керування паролями

| Метод | Шлях | Автентифікація | Опис |
|-------|------|----------------|------|
| POST | `/membership/users/forgot` | Публічний | Надсилає лист для скидання пароля. Тіло: `{ "userEmail": "...", "appName": "...", "appUrl": "..." }` |
| POST | `/membership/users/setPasswordGuid` | Публічний | Встановлює новий пароль за допомогою authGuid з листа для скидання. Тіло: `{ "authGuid": "...", "newPassword": "..." }` |
| POST | `/membership/users/updatePassword` | JWT | Змінює пароль поточного користувача. Тіло: `{ "newPassword": "..." }` |

### Як перевіряються дозволи

У контролерах дозволи перевіряються методом `au.checkAccess()`:

```typescript
// Require specific permission
if (!au.checkAccess(Permissions.people.edit)) return this.json({}, 401);

// Or within actionWrapper — the CRUD system checks automatically
crudSettings: {
  permissions: {
    view: Permissions.people.view,
    edit: Permissions.people.edit
  }
}
```

### Адміністратор сервера

Дозвіл `Server.Admin` надає повний доступ до всіх церков. Його отримує перший зареєстрований користувач, і його можна надати іншим через роль адміністратора сервера.

## OAuth 2.0

API підтримує OAuth 2.0 для інтеграцій сторонніх застосунків. Доступні два типи грантів.

### Потік коду авторизації

1. **Авторизація:** `POST /membership/oauth/authorize` (потрібен JWT)
   - Тіло: `{ "client_id": "...", "redirect_uri": "...", "response_type": "code", "scope": "...", "state": "...", "code_challenge": "...", "code_challenge_method": "S256" }`
   - `code_challenge` і `code_challenge_method` (PKCE, лише `S256`) є обов'язковими для публічних клієнтів без секрету
   - Повертає: `{ "code": "...", "state": "..." }`

2. **Обмін коду на токен:** `POST /membership/oauth/token` (публічний)
   - Тіло: `{ "grant_type": "authorization_code", "code": "...", "client_id": "...", "client_secret": "...", "redirect_uri": "...", "code_verifier": "..." }`
   - Надсилайте `code_verifier`, якщо на кроці авторизації використовувався `code_challenge`; публічні клієнти не передають `client_secret`. Приймаються тіла у форматі JSON або form-encoded
   - Повертає: `{ "access_token": "...", "token_type": "Bearer", "expires_in": 43200, "refresh_token": "...", "scope": "..." }`

3. **Оновлення токена:** `POST /membership/oauth/token` (публічний)
   - Тіло: `{ "grant_type": "refresh_token", "refresh_token": "...", "client_id": "...", "client_secret": "..." }`

Термін дії токенів доступу спливає через **12 годин**.

### Потік коду пристрою (RFC 8628)

Для пристроїв без браузера (застосунки для телевізорів, кіоски):

1. **Запит коду пристрою:** `POST /membership/oauth/device/authorize` (публічний)
   - Тіло: `{ "client_id": "...", "scope": "..." }`
   - Повертає: `{ "device_code": "...", "user_code": "ABCD-1234", "verification_uri": "https://app.b1.church/device", "expires_in": 900, "interval": 5 }`

2. **Користувач вводить код** за адресою перевірки та підтверджує або відхиляє запит

3. **Опитування токена:** `POST /membership/oauth/token` (публічний)
   - Тіло: `{ "grant_type": "urn:ietf:params:oauth:grant-type:device_code", "device_code": "...", "client_id": "..." }`
   - Повертає `authorization_pending`, доки запит не підтверджено, а потім повертає токен доступу

### Керування клієнтами OAuth

| Метод | Шлях | Автентифікація | Дозвіл | Опис |
|-------|------|----------------|--------|------|
| GET | `/membership/oauth/clients` | JWT | Server.Admin | Перелік усіх клієнтів OAuth |
| GET | `/membership/oauth/clients/:id` | JWT | Server.Admin | Отримати клієнта за ідентифікатором |
| GET | `/membership/oauth/clients/clientId/:clientId` | JWT | — | Отримати клієнта за client ID (секрет приховано) |
| POST | `/membership/oauth/clients` | JWT | Server.Admin | Створити або оновити клієнта |
| DELETE | `/membership/oauth/clients/:id` | JWT | Server.Admin | Видалити клієнта |
| POST | `/membership/oauth/register` | Публічний | — | Динамічна реєстрація клієнта (RFC 7591) для публічних клієнтів, таких як конектори MCP. Див. [Підключені застосунки](../connected-apps#dynamic-client-registration) |

### Ендпоінти підтвердження пристрою

| Метод | Шлях | Автентифікація | Опис |
|-------|------|----------------|------|
| GET | `/membership/oauth/device/pending/:userCode` | JWT | Отримати дані про очікуваний код пристрою для інтерфейсу підтвердження |
| POST | `/membership/oauth/device/approve` | JWT | Підтвердити авторизацію пристрою. Тіло: `{ "user_code": "...", "church_id": "..." }` |
| POST | `/membership/oauth/device/deny` | JWT | Відхилити авторизацію пристрою. Тіло: `{ "user_code": "..." }` |

## Публічні та автентифіковані ендпоінти

API використовує дві функції-обгортки, які визначають вимоги до автентифікації:

- **`actionWrapper`** — вимагає дійсного JWT. Об'єкт автентифікованого користувача (`au`) доступний з `churchId`, `userId` і перевірками дозволів.
- **`actionWrapperAnon`** — автентифікація не потрібна. Використовується для входу, реєстрації, публічного пошуку вмісту та приймачів вебхуків.

У таблицях ендпоінтів цієї документації вони позначаються як **JWT** і **Публічний** відповідно в колонці «Автентифікація».
