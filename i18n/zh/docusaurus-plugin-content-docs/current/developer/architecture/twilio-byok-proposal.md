# Twilio BYOK 集成提案

:::caution 提案——并非可用的集成
这是供维护者审阅的设计方案，基于 2026 年 10 月 22 日审阅的公开源代码和 Twilio 文档。此后，一个基础的 Twilio 提供方已经发布（`@churchapps/texting` 0.6.0 以及 B1 Admin 的 **Settings > Texting**）：教会输入其 Account SID、Auth Token 和发件号码（该提供方也接受以 `MG` 开头的 Messaging Service SID，但 `fromNumber` 列仍为 `varchar(20)`，对于 34 个字符的 SID 来说太短），短信通过 Twilio 的 Messages API 逐个收件人单独发送，STOP 回复通过现有的入站 Webhook 回到 B1。请参见 [教会设置：短信](../../b1-admin/settings/church-settings.md#texting)。下文中的同意模型、高级退订处理、投递状态以及设置就绪检查仍是提案，尚非已发布的功能。配套的[教会入门草案](./twilio-byok-onboarding-draft)包含拟议的设置指南和针对教会的示例。
:::

## 推荐方案

使用 **教会自有的 Twilio 账户、API 凭据、Messaging Service 以及支持短信的电话号码**，将 Twilio 添加到 B1 现有的短信提供方体系中。教会注册自己的法律实体和短信活动，直接向 Twilio 付费，维护收件人同意记录，并在 Twilio Console 中管理审批。ChurchApps 提供集成功能和文档。

每个 B1 教会起步时只使用一个短信项目、一个 Messaging Service 和一个美国本地 10DLC 发件号码。通过 B1 现有页面支持单独短信、群组短信、工作流短信以及参与提醒。当该教会的同意书和已获批准的活动中同时描述了服务变更、活动提醒和志愿者排班这三类内容时，一个合理的首期项目可以覆盖这些内容。筹款或促销短信需要单独评估范围和同意，不得悄然加入此项目。

| 职责 | 教会 | B1 / ChurchApps |
|---|---|---|
| Twilio 账户、计费、号码所有权 | 拥有并管理这些内容 | 不负责开通平台账户，也不转售额度 |
| 品牌、活动、号码注册 | 提交准确的教会信息；处理审核和更正 | 说明前提条件，并读取可用的就绪信息 |
| 注册页面、政策、短信用途 | 发布并维护这些内容 | 提供兼容的表单控件、示例和同意记录 |
| 收件人资格和 STOP 处理 | 审查同意证据，并请求在短信之外收到的退订 | 强制执行同意、抑制、权限以及已签名的 Webhook |
| 投递与支持 | 监控 Twilio 错误、账户健康状况和入站回复 | 显示提交和投递状态，但不保证审批结果 |

以下内容推迟到后续版本：ChurchApps 拥有的 Twilio 父账户、客户子账户、号码购买、Trust Hub 提交、计费、对话收件箱、MMS/WhatsApp、国际发送以及免费电话号码的开通。免费电话号码是一条单独的已验证发件人路径，而非注册的绕过方式。这些边界确保首个版本与 B1 现有的"自带提供方"模式保持一致。

## 配置与凭据设计

使用明确、增量的配置字段，而不是复用 `fromNumber`，也不要把结构化数据存储在 API 密钥字符串中：

| 字段 | 拟定用途 |
|---|---|
| `accountSid` | 教会自有 Twilio 账户/项目标识符（`AC…`） |
| `apiKey`、`apiSecret` | 用于出站 API 访问的专用 Twilio API Key SID（`SK…`）及其密钥；加密并脱敏 |
| `webhookAuthToken` | Twilio SDK 用于验证入站签名的账户 Auth Token；单独加密并脱敏 |
| `messagingServiceSid` | 教会的 Messaging Service（`MG…`，34 个字符） |
| `fromNumber` | 所选的支持短信的 E.164 格式号码，并已在该账户/服务中验证为发件人 |
| 项目配置 | 稳定的项目 ID、名称、允许的用途、注册/政策 URL 以及披露版本 |

Twilio [推荐使用 API 密钥进行 REST 身份验证](https://www.twilio.com/docs/iam/api-keys)。应使用经过测试的、最小化的密钥权限，以覆盖发送及所需的只读设置检查。账户 Auth Token 仍需用于[标准 Twilio Webhook 签名检查](https://www.twilio.com/docs/usage/security)。应在界面中解释这一区别：API 密钥的 secret 不等同于 Webhook 的 Auth Token。凭据应仅保存在服务器端的设置存储中，绝不可出现在公开页面、表单答案、浏览器发送请求或支持工单中。

教会在 Console 中创建和管理这些资源。B1 的验证操作只能读取已配置的服务、发件人和注册信息。它不得购买号码、创建活动、更改 Twilio 设置或作为副作用发送测试短信。应另外提供一个单独的、明确的测试发送操作，且仅限于符合条件并已同意的收件人。

只有在编辑同一个已保存的提供方时才保留脱敏凭据。切换到 Twilio 时，必须提供其专用凭据，并清除过时的提供方专用值；不得将脱敏的 Clearstream 或 Nalo 密钥带入 Twilio 配置。

每次加载和更新都应限定在已通过身份验证的 B1 教会范围内。将回调绑定到已保存的集成以及预期的 Twilio 账户/服务/发件人，并拒绝冲突的跨教会分配。凭据轮换和提供方断开连接必须使就绪状态失效，并暂停排队中的发送，但不得删除同意记录或历史投递记录。

## 同意与抑制是必须完成的发布工作

为 Twilio 项目引入绑定电话号码的订阅记录，以及仅追加的同意/抑制事件。建议的最低证据包括：教会 ID、项目 ID、规范化的电话号码、可选的已验证人员关联、明确的肯定性操作、来源表单/提交 ID 或经审阅的外部证明、服务器时间戳、披露文本/版本、来源 URL、政策 URL，以及撤回/重新订阅事件。访问和保留期限应遵循教会现有的数据安全政策。

使用 `unknown`、`pending`、`active` 和 `suppressed` 等状态。现有的手机号码、导入的联系人、出席记录、捐赠、群组成员身份、`person.optedOut = false` 以及 `allowSms` 都不构成明确的项目同意。导入已有的同意记录应是经授权、可审计的操作，并记录来源；迁移过程不得为所有人自动登记。

对于初始的网页流程，使用 B1 的标准公开表单模式。添加一个明确配置的短信同意问题：默认未勾选，保持可选，显示可点击的政策链接，并映射到一个项目和一个手机字段。在服务器端验证该映射，并在保存肯定性回复时保存所显示披露内容的快照。绝不可从任意问题标签、对话式 AI 或工作流成员身份推导同意。只有在明确的肯定性交互和证据记录经过测试后，才可启用对话式的等效方式。

未勾选的提交不会创建订阅，也不得撤回他人已有的同意。同意应绑定到提交的电话号码；工作人员可以解决模棱两可的人员关联，但无需合并家庭记录。更换手机号码需要重新获得同意。对于匿名表单，应应用滥用防护措施，并明确说明任何号码归属验证或双重确认步骤；仅勾选复选框并不能证明某人拥有该电话号码。如果使用确认步骤，应在完成前将订阅保持为待定状态，并在注册材料中描述该确切流程。

对于 Twilio，应将短信抑制与目录可见性分开。将任何旧版退订保守地迁移为抑制记录；其他旧版收件人保持为 `unknown`。明确记录且已在文档中说明的新登记可以建立短信同意，同时目录隐私保持不变。在其他提供方的迁移经过单独审阅之前，保留其现有行为。

在每次实际发送时，都必须满足：教会集成已启用/就绪，该确切电话号码具有当前的项目同意，不存在电话级别的抑制，并且调用者具备现有权限。提醒还需遵守 `allowSms`、类别偏好和免打扰时段。入队后需再次检查，解析合并字段，规范化并验证号码，并按电话号码去重。STOP 会抑制该服务/项目的所有发送，包括手动发送和工作流发送；并且还必须覆盖共用该电话号码的每一个人。

在通用的 Twilio 发送路径中一致地呈现教会身份和 STOP 说明，并预览最终的短信条数/分段数。合并字段展开和长度处理必须保留这些内容；不得悄然截断退订说明。示例与实际的提醒/工作流模板应保持一致。

## Twilio 发送、回复与投递状态

通过 Messages API，使用所选的 Messaging Service 和发件人实现 `TwilioProvider.sendMessage`。返回 Provider Message SID 以及"已接受/已提交"的结果；HTTP 接受并不等同于送达手机。群组发送按输入顺序返回每个收件人的结果。

对 **`sendBulk` 和单条发送**都要限制出站并发数：当前的合并字段分支会扇出 `sendMessage` 调用。对于无法在请求预算内完成的群组，应持久化发送意图和可领取的工作项；复用现有的部署模型，而不是要求教会运行另一个服务。对已知的临时性/限流失败进行带退避的重试。将模糊的超时视为需要核对的未知结果，而不是盲目重发——否则可能导致重复短信和重复收费。

配置教会专属的入站和状态回调 URL。使用 SDK、确切的已配置外部 URL、原始表单参数以及匹配的账户 Auth Token 验证 `X-Twilio-Signature`。仅有一个秘密 URL 是不够的。将回调匹配到已保存的教会/账户/消息记录，处理重复回调以及在发送结果提交之前到达的回调，并防止较早的事件覆盖终态。对入站确认返回空的 TwiML，对状态事件返回适当的成功响应。[Twilio 安全](https://www.twilio.com/docs/usage/security)、[状态回调](https://www.twilio.com/docs/messaging/guides/track-outbound-message-status)

建议启用 Messaging Service 的 **Advanced Opt-Out**。STOP/START/HELP 的确认由 Twilio 负责；B1 使用经过身份验证的 `OptOutType` 事件，且不再发送重复的确认。STOP 会立即记录抑制；START 仅能恢复已知订阅者对同一已披露项目的订阅，并附带一个新的重新订阅事件；它不得让新号码加入无关的消息或开启提醒偏好。HELP 不会登记任何人。其他入站回复不在 B1 收件箱的范围内；教会需要有记录的方式在 Twilio 中监控这些回复。[高级退订](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out)

将 Twilio 消息 SID、账户/服务绑定、提交时间、最终状态/错误代码以及回调时间与投递日志一同存储。准确显示已排队/已接受、已投递、失败、未投递或未知的状态。保持其他提供方现有的响应契约，并明确汇总的成功计数代表的是提交数还是投递数。

## 设置就绪与审批验证

分别显示以下检查点：凭据、服务/发件人所有权、活动验证、号码注册、Webhook 检查，以及已送达的冒烟测试。绝不能仅仅因为凭据可用就显示单一的绿色"已批准"徽章。

对于美国本地号码，读取服务的 [Usa2p 活动资源](https://www.twilio.com/docs/messaging/api/usapptoperson-resource)，并要求相关活动处于 `VERIFIED` 状态。另外验证所选电话号码已关联到该服务，并已完成号码注册：已获批准的活动仍可能有待处理的号码。如果受支持的读取 API 不提供某项所需信号，则显示 **需要在 Console 中手动验证**，并将教会管理员带有日期的确认记录为手动确认；不得将其标记为 API 已验证。自动化的号码注册事件可以作为后续工作。[号码注册错误](https://www.twilio.com/docs/api/errors/30035)、[A2P 注册事件](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/event-streams-setup)

在启用发送之前，需要当前有效的检查；记录检查的时间和方式，使过期的检查失效，并在凭据被吊销、发件人发生变化、注册失败或出现持续性账户错误时暂停。冒烟测试的送达只能证明所测试的路径，并不代表普遍的运营商批准或收件人同意。配套草案规定了教会在提交前、上线前以及持续运营中的检查项。

## 代码仓库与发布计划

[组织贡献指南](https://github.com/ChurchApps/.github/blob/main/CONTRIBUTING.md)要求将 B1 功能请求提交到 ChurchAppsSupport，将实现 PR 提交到所属的代码仓库。应使用一个中心化的功能请求，并将聚焦的实现 PR 链接到该请求：

1. **ChurchAppsSupport：** 在将 Twilio 作为可用的用户功能呈现之前，审阅本设计及其入门草案。
2. **Packages：** 添加 Twilio 适配器、明确的共享配置/接口，以及由 B1Admin/B1App 共用的短信同意表单渲染。在更新使用方之前，添加变更集并通过现有的发布流程发布。
3. **Api：** 添加增量迁移，用于集成元数据、同意/抑制以及投递状态；实现配置验证、共享发送门控、表单证据采集、Webhook 处理以及派发持久化。
4. **B1Admin：** 添加 Twilio 配置/就绪界面、项目/同意管理、支持提供方感知的发件人保存，以及准确的投递报告。不得通过普通的人员编辑来覆盖短信同意。
5. **B1App：** 对照共享控件验证公开表单/页面和政策链接体验，包括匿名访客和移动端访客。无需单独的 Twilio 浏览器客户端。
6. **ChurchAppsSupport：** 发布后，将入门草案转化为受支持的设置/帮助页面，添加实际截图，从短信设置中链接过来，并安排翻译。

在使用方之前部署架构和共享包。将 Twilio 限定在功能开关之后，用于小规模的自愿试点；现有提供方必须继续正常工作。回滚时应禁用 Twilio 派发，并取消未提交的任务，同时保留退订记录和证据；不得自动将收件人切换到其他提供方或发件人。

## 工作量评估

以下为面向熟悉该生态系统的贡献者的规划估算；本评估未使用任何生产凭据，也未发送任何真实短信：

| 工作内容 | 开发人日 |
|---|---|
| 适配器、配置/架构扩展、设置界面 | 2–3 |
| 电话/项目同意、独立抑制、共享发送门控、公开表单集成 | 3–5 |
| 已签名回调、投递持久化、有界/持久化派发 | 2–3 |
| 就绪界面、教会指南、集成与回归测试、试点修复 | 3–4 |
| **推荐的上线范围** | **总计 10–15** |

基础的适配器/设置概念验证大约需要 1–2 天。仅针对发件人的估算不包括为本建议所必需的同意和入门工作。Twilio/运营商的外部审核时间单独计算且不固定；项目不应承诺审批日期或审批结果。

## 验收标准

- [ ] 教会拥有并为账户、服务、已注册发件人和活动付费；不需要 ChurchApps 管理的 Twilio 账户。
- [ ] 凭据经过加密和脱敏，限定于租户范围，可轮换，并且不会出现在日志或公开内容中；验证操作为只读。
- [ ] 可选的未勾选同意会渲染真实的政策链接，并在服务器端保存项目/电话/披露的证据；拒绝同意仍允许完成主要的表单操作。
- [ ] 所有手动、群组、合并字段、工作流和提醒路径都执行相同的 Twilio 资格门控。未知、未同意、更换号码或被抑制的收件人会被跳过，并给出有用的原因；在展开和长度处理之后，渲染内容仍保留教会身份/STOP 说明。
- [ ] 旧版目录隐私设置不会为收件人登记；STOP/START 绝不会改变目录可见性或无关的偏好。共用电话号码和跨教会的情况均已测试。
- [ ] 已覆盖已签名的 STOP/START/HELP、无效签名、错误的账户/服务、重复事件、重放的表单提交以及伪造的同意映射。
- [ ] 群组规模/超时、速率限制、部分失败、模糊结果、回调竞争以及乱序投递事件均已测试，且不产生重复发送。
- [ ] 活动审批和已完成的号码注册与凭据验证相互区分。手动确认被明确标注；过期或被吊销的就绪状态会阻止发送。
- [ ] 试点教会检查其注册页面、已接受和已拒绝的表单路径、确切的政策 URL，以及一位已同意的测试收件人，涵盖提交、投递、STOP 抑制和允许的重新订阅。
- [ ] 现有的 Clearstream、Text In Church 和 Nalo 设置及发送行为通过回归检查；帮助文案清楚区分提案与已发布的功能。
