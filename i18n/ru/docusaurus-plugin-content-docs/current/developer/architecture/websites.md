# Маршрутизация сайтов и несколько сайтов

<div class="article-intro">

Одна церковь теперь может обслуживать несколько разных сайтов, и каждый из них может располагаться на поддомене `*.b1.church` или на полностью пользовательском домене, принадлежащем церкви. На этой странице описан слой маршрутизации, который находится *под* конструктором: как входящий запрос определяет и церковь, **и** конкретный сайт, модель данных для нескольких сайтов (сентинел `siteId`, который сохраняет работу всех прежних сайтов без изменений) и граница для пользовательских доменов — самостоятельно управляемый прокси Caddy на EC2, который завершает TLS и переписывает каждый домен церкви на её апстрим `*.b1.church`. О том, что именно отображается, когда запрос уже определил сайт, — дерево страниц, разделов и элементов — см. в [Конструкторе сайтов](./website-builder.md).

</div>

## Обзор

```
   grace.b1.church              www.gracechurch.org  (пользовательский домен)
   (поддомен b1.church)                  │
          │                               ▼
          │             ┌──────────────────────────────────────────┐
          │             │ Граница Caddy — EC2 3.23.251.61           │
          │             │             (proxy.b1.church)             │
          │             │  • завершает TLS (LE-сертификат на домен) │
          │             │  • переписывает Host → {sub}.b1.church    │
          │             │  • проксирует на B1App                    │
          │             └────────────────────┬─────────────────────┘
          │                  Host = {sub}.b1.church
          ▼                                  ▼
   ┌────────────────────────────────────────────────────────────┐
   │ B1App src/middleware.ts                                     │
   │  • всегда: удаляет любой клиентский x-site (защита от подмены) │
   │  • внутренний Host *.b1.church ⇒ поиск домена остаётся неактивным │
   │  • сырой пользовательский Host (в обход Caddy) ⇒ поиск → установка x-site │
   └───────────────────────────┬────────────────────────────────┘
                               ▼  next.config.mjs → первая метка хоста → /[sdSlug]/…
              ┌─────────────────────────────────────────────────┐
              │ [sdSlug] · ConfigHelper.load(sdSlug)             │
              │   GET /membership/churches/lookup/?subDomain=…   │
              │   → { id, name, subDomain, siteId? }             │
              │   передаёт ?siteId= во все вызовы контента:      │
              │   /content/pages/:id/tree · /globalStyles ·      │
              │   /blocks/public/footer · /links · sitemap       │
              └─────────────────────────────────────────────────┘

  сохранение/удаление домена (B1Admin Settings→Domains → POST /membership/domains)
        └─ best-effort CaddyHelper.updateCaddy()  (обёрнуто, не фатально, таймаут 10 с)
  Caddy сам читает таблицу доменов через два анонимных эндпоинта:
        GET /membership/domains/authorize  — `ask` для on-demand TLS (200 известный / 404 неизвестный)
        GET /membership/domains/hostmap    — карта host→{sub}.b1.church (обновление каждые 5 мин)
```

Три правила действуют в этом слое:

1. **Сентинел сохраняет обратную совместимость.** `siteId = ''` — это основной сайт. Каждая страница, блок, ссылка, глобальный стиль и строка домена, существовавшие до этой функции, содержат `''` и отображаются точно так же, как раньше. *Второй* сайт — это просто набор строк с непустым `siteId`, а любой эндпоинт контента, вызванный без `?siteId=`, возвращает основной сайт — побайтно прежний запрос.
2. **Определение основано на метке хоста и сходится.** Поддомен `*.b1.church` маршрутизируется напрямую по своей метке хоста; пользовательский домен переписывается в метку `{sub}.b1.church` на границе Caddy до того, как B1App его увидит (а поиск в базе в middleware ставит заголовок `x-site` как запасной вариант для любого сырого пользовательского `Host`). Оба пути попадают в один и тот же маршрут `[sdSlug]` и один и тот же вызов `churches/lookup`, поэтому последующий рендеринг идентичен.
3. **Граница Caddy не хранит состояния поверх одного источника истины.** Пользовательские домены завершаются на самостоятельно управляемом прокси Caddy на EC2, который переписывает каждый домен на его апстрим `{sub}.b1.church`. Сохранение домена запускает один best-effort `CaddyHelper.updateCaddy()`, а Caddy также читает таблицу `domains` напрямую (эндпоинты `authorize` и `hostmap` ниже). Таблица является авторитетной — недоступный Caddy никогда не может сорвать сохранение.

## Определение сайта

### Поддомены `*.b1.church`

`B1App/next.config.mjs` переписывает входящие запросы по хосту. Правило хоста с шаблоном `(?<subdomain>.*?)\..*` захватывает **первую метку** хоста и переписывает `/` и `/:path*` в `/{subdomain}` — сегмент App Router `[sdSlug]`. Так `grace.b1.church/about` превращается в `/grace/about`.

Внутри `src/app/[sdSlug]/` функция `ConfigHelper.load(sdSlug)` (`src/helpers/ConfigHelper.ts`) вызывает `GET /membership/churches/lookup/?subDomain={sdSlug}`. Ответ `ChurchController.getBySubDomain` теперь имеет две ветки:

| Совпадение slug | Ответ | Значение |
|--------------|----------|---------|
| `churches.subDomain` | `{ id, name, subDomain }` | Основной сайт этой церкви |
| `sites.subDomain` | `{ id, name, subDomain, siteId }` | **Вторичный сайт** — контроллер переходит к `sites`, определяет владеющую церковь и возвращает запрошенный slug плюс дополнительный `siteId` |

Этот дополнительный `siteId` — единственное, что отличает запрос вторичного сайта от основного; всё остальное в конвейере общее.

Slug, который не совпадает ни с одной таблицей, возвращается как `{}` с кодом `200`. `ConfigHelper.load` считает ответ без `id` неизвестным сайтом и вызывает `notFound()` Next, поэтому неизвестный поддомен получает настоящую 404, а не последующие вызовы к `/…/undefined`. Маршрут страницы конструктора также строит путь дерева через `pageTreePath()` (`src/helpers/pageTreePath.ts`), который кодирует slug в URL, поэтому некорректный slug (обратные слэши, пробелы) даёт 404, а не превращает `400` API в 500.

### Пользовательские домены {#custom-domains}

Домен, принадлежащий церкви, завершается на **границе Caddy** (подробно описана ниже), которая переписывает заголовок `Host` на `{sub}.b1.church` сайта, прежде чем проксировать запрос в B1App. Поэтому в обычном пути B1App получает *внутренний* хост `*.b1.church` и определяет его по метке хоста точно так же, как нативный поддомен, — поиск в базе middleware никогда не срабатывает. `src/middleware.ts` всё равно выполняется на каждом запросе, но с одной постоянной задачей и одним запасным вариантом:

1. **Всегда** — он **удаляет любой заголовок `x-site`, переданный клиентом**. Этот заголовок — подменяемый вход для переписывания, которому доверяют только тогда, когда его ставит сам middleware; поэтому удаление — настоящая задача middleware за Caddy.
2. **Запасной вариант только для не-внутреннего `Host`** — для сырого пользовательского `Host`, который доходит до B1App *без* переписывания Caddy, он вызывает `GET /membership/domains/public/lookup/{host}` и, если тот возвращает `subDomain`, ставит `x-site: {subDomain}.b1.church`. За Caddy эта ветка неактивна, потому что `Host` уже `*.b1.church`.

Внутренние хосты — `localhost`, `b1.church` и суффиксы `.b1.church`, `.localtest.me`, `.localhost`, `.up.railway.app`, `.vercel.app` — полностью пропускают поиск (они уже определены переписыванием по метке хоста или являются хостами предпросмотра/развёртывания).

Сам поиск (`DomainRepo.loadByName`) делает left join `domains → churches` и `domains → sites` и возвращает `COALESCE(NULLIF(sites.subDomain,''), churches.subDomain)` — поддомен назначенного вторичного сайта, если домен указывает на него, иначе — поддомен церкви. Сначала совпадает точный хост; если хост начинался с `www.` и не нашёлся, поиск повторяется **один раз** для голого апекса.

В `next.config.mjs` правила переписывания `x-site` стоят **перед** общими правилами хоста, поэтому выигрывают. `x-site: grace.b1.church` → первая метка `grace` → `[sdSlug] = grace`, и дальше определение идентично пути поддомена (тот же `churches/lookup`, тот же `siteId`).

:::info
Заголовок `x-site` извне недоверенный. middleware безусловно удаляет любой входящий `x-site`, прежде чем необязательно выставить собственный, а правила переписывания видят только значение, выставленное middleware, — клиент не может навязать себя чужому контенту церкви, передав заголовок.
:::

Две операционные детали middleware:

- **Кеш.** Результат для каждого хоста (попадание *или* подтверждённый промах — никогда сетевая ошибка) кешируется на **10 минут** во внутренней `Map` в памяти, для каждого изолята serverless.
- **Matcher.** Matcher намеренно повторно включает `/sitemap.xml`, `/robots.txt` и `/manifest.webmanifest`. Его первый шаблон исключает пути с точками, что иначе отбросило бы эти файлы; их возвращают обратно, чтобы пользовательский домен тоже получал заголовок `x-site` для собственных файлов SEO/PWA церкви.
- **Канонический заголовок.** Для страниц церкви middleware добавляет к ответу заголовок `Link: <{proto}://{host}{path}>; rel="canonical"`, который называет хост, с которого страница действительно отдана — поддомен или пользовательский домен (`helpers/canonicalLink.ts`). Когда пользовательский домен доходит до B1App через [прокси Caddy](../deployment/caddy-proxy.md), хост запроса — это поддомен `{sub}.b1.church`, поэтому middleware берёт домен посетителя из `X-Church-Host` — но только после того, как `/domains/public/lookup/{host}` подтвердит, что домен соответствует тому же поддомену (`ownsSubdomain()`). Тогда канонический `Link`, `robots.txt` и `sitemap.xml` называют пользовательский домен, а не поддомен `b1.church`. Он пропускается на не-церковных хостах (`b1.church`, `localhost`, `*.vercel.app`, `*.up.railway.app`) и на `/mobile`, `/login`, `/logout` и сгенерированных файлах robots/sitemap/manifest.

### Отключённый публичный сайт

Церковь может включить **Disable Public Website** в B1Admin (настройка контента уровня церкви `hidePublicSite = "true"`). Тогда сайт отдаёт только маршруты для участников:

- **Middleware B1App** ищет поддомен (`/membership/churches/lookup`, затем `/content/settings/public/:churchId`) и перенаправляет анонимные запросы к любому пути вне списка разрешённых на `/login?returnUrl={path}{query}`. Список разрешённых (`helpers/publicSite.ts`) — `/login`, `/logout`, `/mobile/*`, `/register/*`, `/guest-register` и файлы manifest/robots/sitemap. Кешируются только подтверждённые ответы (60 секунд в продакшне, так как вызов revalidate администратора не может сбросить эту карту внутри экземпляра; в dev/test — без кеша). Ошибка API отдаёт сайт, а не закрывает его для всех.
- **Вошедшие участники видят полный сайт.** Запрос с неистёкшей cookie `jwt` (функция `hasSession()` middleware декодирует поле `exp` полезной нагрузки без проверки подписи — это мягкий барьер, а не контроль доступа) пропускает перенаправление, поэтому после входа участник возвращается на запрошенную страницу и видит обычные страницы, встроенные страницы (Groups, Sermons и т. д.) и навигацию в шапке. Компоненты страниц и `Header` больше не проверяют `hidePublicSite` сами.
- **`robots.txt`** запрещает всё, как и на хостах с noindex.
- **API.** `GET /content/pages/public/:churchId` (список страниц для sitemap) возвращает `[]`, поэтому анонимные вызовы не могут перечислить страницы.

### Передача `siteId`

`ConfigHelper` сохраняет определённый `siteId` в своём объекте `ConfigurationInterface` на запрос (с мемоизацией через `cache()` из React) и добавляет `?siteId=` к вызовам контента, которые он и компоненты страниц делают, — **условно**: пустой `siteId` (поддомен основной церкви) не добавляет параметр вообще. Затронутые эндпоинты — дерево страниц (`/content/pages/:id/tree`), список публичных страниц для sitemap (`/content/pages/public/:id`), глобальные стили (`/content/globalStyles/church/:id`), навигационные ссылки (`/content/links/church/:id`) и отдельный блок подвала (`/content/blocks/public/footer/:id`). На обычном пути рендеринга подвал приходит внутри дерева страницы (разделы с `zone: "siteFooter"`), уже загруженным с `siteId`, поэтому разрыва без привязки к сайту нет.

Публичное приложение участников (B1App `mobile`) намеренно находится вне этого: `loadChurchAppearance.ts` определяет церковь через `churches/lookup`, но читает настройки уровня церкви `/settings/public/{id}` и никогда не передаёт `siteId` — портал на первой версии общецерковный (см. ниже).

## Несколько сайтов у одной церкви

### Модель данных

Новая таблица `membership.sites` намеренно маленькая:

| Столбец | Тип | Примечания |
|--------|------|--------|
| `id` | `char(11)` PK | |
| `churchId` | `char(11)` | Церковь-владелец |
| `name` | `varchar(255)` | Отображаемое название (например, «Español», «Youth») |
| `subDomain` | `varchar(45)` | **Уникальный индекс** — глобальное пространство имён (см. ниже) |

Привязка к сайту — это затем один столбец, не допускающий NULL, который добавлен в таблицы контента и доменов:

| Таблица (модуль) | Столбец | Что означает `''` |
|----------------|--------|-----------|
| `domains` (membership) | `siteId char(11) NOT NULL DEFAULT ''` | Домен обслуживает основной сайт |
| `pages`, `links`, `globalStyles`, `blocks` (content) | `siteId char(11) NOT NULL DEFAULT ''` | Основной сайт — а у **`blocks`** `''` дополнительно означает *общий для всех сайтов* |

Две миграции добавляют всё это (`tools/migrations/membership/2026-07-02_sites.ts`, `tools/migrations/content/2026-07-02_site_id.ts`). Поскольку столбец по умолчанию равен `''`, каждая существующая строка сохраняет нынешнее поведение без заполнения данных.

**Глобальное пространство имён поддоменов.** `sites.subDomain` использует *одно* пространство имён с `churches.subDomain` — поддомен сайта никогда не может совпасть с поддоменом церкви или с поддоменом другого сайта. Это проверяется на **обоих** путях сохранения: `SiteController.save` отклоняет slug, который попадает в `churches` или `sites`, а `ChurchController.validateSave` делает то же в обратную сторону. Уникальный индекс `sites.subDomain` закрепляет это на уровне базы данных.

**Уникальность страниц** расширена с `(churchId, url)` до `(churchId, siteId, url)`, так что два сайта одной церкви могут иметь каждый свой `/about`.

### Контент по сайтам с запасными вариантами

Каждый эндпоинт **списка/дерева** контента с привязкой к сайту принимает необязательный `?siteId=` (если отсутствует ⇒ `''` = основной): дерево страниц / список / публичные страницы, список блоков / по типу / подвал, ссылки (анонимные / отфильтрованные / все) и глобальные стили. Разделы и элементы напрямую не привязаны к сайту — они наследуют эту привязку от родительской страницы или блока.

Две цепочки разрешения делают самую интересную работу:

- **Глобальные стили — `сайт → основной → по умолчанию`.** `GlobalStyleRepo.loadForChurch(churchId, siteId)` возвращает собственную строку сайта; если у вторичного сайта её нет, возвращается **строка основного (`''`) как есть** (сохраняя `id`/`siteId` основной строки, которые клиент использует для копирования при записи), а если нет и основного — `GlobalStyleController` возвращает жёстко заданную палитру и шрифты по умолчанию.
- **Блок подвала — свой сайта побеждает, общий идёт запасным.** `BlockRepo.loadByBlockType(churchId, "footerBlock", siteId)` возвращает и общие (`''`), и строки конкретного сайта; разрешитель выбирает собственный подвал сайта, если он есть, иначе общий. Та же логика работает и в `TreeHelper.insertBlocks` (дерево страницы), и в отдельном эндпоинте `/content/blocks/public/footer/:churchId`.

### Каскадное удаление сайта

`SiteController.delete` (защищён правом Settings→Edit в membership) удаляет вторичный сайт в три шага:

1. `ContentModuleGateway.deleteSiteContent(churchId, siteId)` каскадно удаляет весь контент, которым владеет сайт: его **страницы** → их разделы, элементы, `pageHistory` и `posts`; его собственные **блоки** → их разделы, элементы и `pageHistory`; его **ссылки** и **globalStyles**. Защита отказывается работать для `''` — сентинел основного/общего никогда не каскадируется.
2. `DomainRepo.clearSiteId` **переназначает** домены сайта обратно на основной (`siteId → ''`), а не удаляет их, поэтому пользовательский домен переживает удаление сайта.
3. Строка `sites` удаляется, а маршруты Caddy пересинхронизируются (best-effort).

### Поверхность B1Admin

| Возможность | Где | Механизм |
|-----------|-----------|-----------|
| Переключатель сайтов | `useSiteSelection` + `SiteSwitcher` (пусто = «Main Website») | Читает параметр URL `?site=` и передаёт его как `?siteId=` в вызовы ContentApi. Присутствует в трёх областях **списков** Site — **Pages**, **Blocks**, **Appearance** — но *не* в редакторах страниц и блоков, которые несут `siteId` в самой записи |
| Создание / удаление сайтов | `SitesDialog`, открывается из пункта «Manage websites…» переключателя | `POST /membership/sites` / `DELETE /membership/sites/:id` (название + subDomain). Защищено правом Settings→Edit в membership (`Permissions.settings.edit` на сервере; `Permissions.membershipApi.settings.edit` в B1Admin). **Только создание и удаление — переименования в v1 нет** |
| Назначение сайта для домена | `DomainSettingsEdit` в Settings→Domains | Выпадающий список сайта в каждой строке отправляет `siteId` для каждого домена в `/membership/domains`. Столбец скрывается, если API не возвращает сайты (старый бэкенд) |
| Копирование при записи для стилей | `StylesManager.prepareForSave` | Когда загруженная строка глобальных стилей имеет `siteId`, не совпадающий с выбранным сайтом (то есть API вернул унаследованный основной как запасной вариант), он убирает `id` основного и проставляет текущий `siteId`, заставляя **вставить** новую строку конкретного сайта, а не перезаписать основную. То же ветвление при несовпадении применяется к блоку подвала сайта |

:::info
**Что остаётся общецерковным в v1 (намеренное решение по области, а не ограничение модели данных):** **блог** (у `BlogPage` нет переключателя, и он загружает `/posts` без `siteId`), **виджеты сайта** (баннер объявлений и launcher), **редиректы**, **логотип / GA4 / настройки церкви** и **портал участников** (мобильная версия B1App). Заметьте, что это *не* «весь Appearance» — глобальные стили вторичного сайта (палитра, шрифты, типографика, интервалы, навигация, пользовательский CSS) **являются** пособными через копирование при записи выше; остаются общими только подпанели баннера/launcher/редиректов/логотипа на странице Appearance.
:::

## Пользовательские домены: граница Caddy (статическая конфигурация)

:::info
**Направление пересмотрено 2026-07-02.** Более ранний план переноса хостинга пользовательских доменов на домены, управляемые Vercel, был **отменён**, а весь код регистрации доменов Vercel (`VercelHelper`, его переменные окружения `vercelToken`/`vercelProjectId`/`vercelTeamId`, параметры SSM и проверки состояния) удалён из Api. Самостоятельно управляемый **прокси Caddy на EC2 остаётся** постоянной границей для пользовательских доменов. Остаётся только внутренняя работа: заменить *динамическую* конфигурацию Caddy через admin API на *статическую*, которая переживает перезапуски.
:::

### Граница

Каждый пользовательский домен церкви направляет DNS на одну коробку EC2 — `3.23.251.61`, также доступную как `proxy.b1.church`. Экран Settings→Domains в B1Admin предлагает церквям добавить апекс `A → 3.23.251.61` или `CNAME → proxy.b1.church`. Caddy завершает TLS с LE-сертификатом на каждый домен, переписывает заголовок `Host` на апстрим `{sub}.b1.church` домена и проксирует на B1App — который затем маршрутизирует по метке хоста, как любой нативный поддомен (см. [Пользовательские домены](#custom-domains) выше).

Соответствие апстрима берётся из `DomainRepo.loadPairs`, где набор соединения **COALESCE подставляет поддомен назначенного сайта**, поэтому домен проксируется на правильный *вторичный* сайт, а при его отсутствии — на основной сайт церкви:

```sql
CONCAT(COALESCE(NULLIF(s.subDomain,''), c.subDomain), '.b1.church:443')  AS dial
WHERE d.domainName NOT LIKE '%www.%'
```

Строки `www.*` исключены из карты; Caddy обслуживает `www.{host}` через перенаправление `302` на апекс.

### Два анонимных эндпоинта питают границу

`DomainController` предоставляет два неаутентифицированных, только читающих эндпоинта, которые коробка использует напрямую — анонимные по необходимости, так как граница запрашивает их до того, как появляется контекст церкви:

| Эндпоинт | Возвращает | Роль |
|----------|----------|------|
| `GET /membership/domains/authorize?domain=` | `200`, если домен — или, при промахе `www.`, его голый апекс — есть в `domains`; иначе `404` (включая пустой `domain`) | `ask` для on-demand TLS у Caddy: контроль злоупотреблений, решающий, выпускать ли сертификат для входящего SNI |
| `GET /membership/domains/hostmap` | `text/plain`, по одной отсортированной строке `{domain} {sub}.b1.church` на каждый маршрутизируемый домен | Файл карты host→апстрим, который коробка обновляет по таймеру |

`authorize` использует повторно `DomainRepo.loadByName` (точный хост, затем повтор с `www.`→апекс); `hostmap` использует повторно `loadPairs` — поэтому он учитывает сайт и исключает `www.*`, идентично маршрутам прокси, — и только убирает суффикс `:443`.

### Сохранение / удаление домена — один best-effort толчок

`DomainController.save` записывает строки `domains`, а затем делает **один best-effort** вызов `CaddyHelper.updateCaddy()`, обёрнутый в `try/catch`, который записывает в журнал (`console.error`) и проглатывает ошибку; `delete` делает то же (что также исправило прежний ошибочный маршрут при удалении), как и удаление вторичного сайта (`SiteController.delete`). Сам `updateCaddy` ограничен таймаутом Axios **10 секунд**, поэтому недоступный или остановленный Caddy никогда не может вернуть `500` при сохранении домена — таблица `domains` является источником истины.

### Текущее состояние — статическая конфигурация, без состояния во время выполнения

Коробка (Windows EC2 за постоянным Elastic IP) запускает Caddy из **статического Caddyfile**: on-demand TLS, чей `ask` указывает на `/membership/domains/authorize`, плюс файл карты host→апстрим, который каждые 5 минут обновляется из `/membership/domains/hostmap` запланированной задачей, заканчивающейся мягкой перезагрузкой `caddy reload`. Конфигурация переживает перезапуски без состояния во время выполнения — никаких танцев с повторной инициализацией — а неизвестный SNI получает **отказ TLS** (сертификат не выпускается для хоста, который отклоняет `authorize`), тогда как авторизованный, но ещё не сопоставленный хост (новый домен внутри окна синхронизации) получает чистый 404. Новые домены становятся маршрутизируемыми в течение ~5 минут после сохранения; их сертификаты выпускаются при первом обращении. Сборка / настройка, эксплуатация и проверенные на практике подводные камни: [Прокси Caddy для пользовательских доменов](../deployment/caddy-proxy.md).

### Устаревший путь push во время выполнения — путь отката, ожидает удаления

`CaddyHelper` (модуль membership) по-прежнему может управлять Caddy через его **admin API** на `caddyHost:caddyPort` (SSM `caddyHost`/`caddyPort`; ничего не делает, если не задано; отображается в группе Integrations у `ServerHealthController`): `updateCaddy()` отправляет PATCH полного массива маршрутов, а `initializeCaddy()` + эндпоинты `GET /membership/domains/caddy/init` / `GET /membership/domains/caddy` пересоздают сервер с конфигурацией во время выполнения с нуля. В этом режиме конфигурация жила только в памяти Caddy — та самая «амнезия при перезапуске», которую заменила эта архитектура. Механизм сохранён только как путь отката и запланирован к удалению, когда статическая коробка проработает стабильно; best-effort push `updateCaddy()` при сохранении/удалении домена — безвредный no-op для статической коробки (её admin API доступен только на localhost).
