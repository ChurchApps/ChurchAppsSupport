# Маршрутизация сайтов и несколько сайтов

<div class="article-intro">

Одна церковь теперь может вести более одного отдельного веб-сайта, и каждый из них может находиться на поддомене `*.b1.church` или на полностью пользовательском домене, принадлежащем церкви. Эта страница описывает уровень маршрутизации, который находится *под* конструктором: как входящий запрос определяется для церкви **и** для конкретного сайта, модель данных многосайтовости (сентинельное значение `siteId`, которое сохраняет работу всех существующих сайтов без изменений) и пограничный уровень пользовательских доменов — самостоятельно управляемый прокси Caddy на EC2, который завершает TLS и перенаправляет каждый домен церкви на его апстрим `*.b1.church`. Информацию о том, что отображается после определения запроса — дерево страниц, секций и элементов — см. в разделе [Конструктор сайтов](./website-builder).

</div>

## Обзор

```
   grace.b1.church              www.gracechurch.org  (custom domain)
   (b1.church subdomain)                  │
          │                               ▼
          │             ┌──────────────────────────────────────────┐
          │             │ Caddy edge — EC2 3.23.251.61              │
          │             │             (proxy.b1.church)             │
          │             │  • terminates TLS (per-domain LE cert)    │
          │             │  • rewrites Host → {sub}.b1.church        │
          │             │  • reverse-proxies to B1App               │
          │             └────────────────────┬─────────────────────┘
          │                  Host = {sub}.b1.church
          ▼                                  ▼
   ┌────────────────────────────────────────────────────────────┐
   │ B1App src/middleware.ts                                     │
   │  • always: delete any client-supplied x-site (anti-spoof)   │
   │  • internal *.b1.church Host ⇒ domains lookup stays inert   │
   │  • raw custom Host (bypassing Caddy) ⇒ lookup → set x-site  │
   └───────────────────────────┬────────────────────────────────┘
                               ▼  next.config.mjs → host first-label → /[sdSlug]/…
              ┌─────────────────────────────────────────────────┐
              │ [sdSlug] · ConfigHelper.load(sdSlug)             │
              │   GET /membership/churches/lookup/?subDomain=…   │
              │   → { id, name, subDomain, siteId? }             │
              │   threads ?siteId= into every content call:      │
              │   /content/pages/:id/tree · /globalStyles ·      │
              │   /blocks/public/footer · /links · sitemap       │
              └─────────────────────────────────────────────────┘

  domain save/delete (B1Admin Settings→Domains → POST /membership/domains)
        └─ best-effort CaddyHelper.updateCaddy()  (wrapped, non-fatal, 10s timeout)
  Caddy reads the domains table itself via two anonymous endpoints:
        GET /membership/domains/authorize  — on-demand-TLS `ask` (200 known / 404 unknown)
        GET /membership/domains/hostmap    — host→{sub}.b1.church map (5-min refresh)
```

Для этого уровня действуют три правила:

1. **Сентинельное значение сохраняет обратную совместимость.** `siteId = ''` — это основной сайт. Каждая страница, блок, ссылка, глобальный стиль и строка домена, существовавшие до появления этой функции, имеют `''` и отображаются точно так же, как раньше. *Второй* веб-сайт — это просто набор строк с непустым `siteId`, а любой эндпоинт контента, вызванный без `?siteId=`, возвращает основной сайт — тот же самый старый запрос байт в байт.
2. **Определение основано на метке хоста и сходится.** Поддомен `*.b1.church` маршрутизируется напрямую по своей метке хоста; пользовательский домен переписывается в метку `{sub}.b1.church` на пограничном уровне Caddy до того, как B1App его получит (а для любого сырого `Host` пользовательского домена работает резервный поиск в БД через middleware, который устанавливает заголовок `x-site`). Оба пути приходят к одному маршруту `[sdSlug]` и одному вызову `churches/lookup`, поэтому дальнейший рендеринг идентичен.
3. **Пограничный уровень Caddy не хранит состояния и опирается на единственный источник истины.** Пользовательские домены завершаются на самостоятельно управляемом прокси Caddy на EC2, который переписывает каждый домен на его апстрим `{sub}.b1.church`. Сохранение домена запускает один необязательный вызов `CaddyHelper.updateCaddy()`, а Caddy также напрямую читает таблицу `domains` (эндпоинты `authorize` и `hostmap` описаны ниже). Таблица является авторитетной — недоступный Caddy никогда не может привести к сбою сохранения.

## Определение сайта

### Поддомены `*.b1.church`

`B1App/next.config.mjs` переписывает входящие запросы по хосту. Правило хоста с шаблоном `(?<subdomain>.*?)\..*` захватывает **первую метку** хоста и переписывает `/` и `/:path*` в `/{subdomain}` — сегмент App Router `[sdSlug]`. Так `grace.b1.church/about` становится `/grace/about`.

Внутри `src/app/[sdSlug]/` функция `ConfigHelper.load(sdSlug)` (`src/helpers/ConfigHelper.ts`) вызывает `GET /membership/churches/lookup/?subDomain={sdSlug}`. Ответ `ChurchController.getBySubDomain` теперь имеет две ветви:

| Совпадение slug | Ответ | Значение |
|--------------|----------|---------|
| `churches.subDomain` | `{ id, name, subDomain }` | Основной сайт этой церкви |
| `sites.subDomain` | `{ id, name, subDomain, siteId }` | **Второстепенный сайт** — контроллер переходит к `sites`, определяет владеющую церковь и возвращает запрошенный slug вместе с дополнительным `siteId` |

Этот дополнительный `siteId` — единственное, что отличает запрос второстепенного сайта от запроса основного; всё остальное в конвейере общее.

Slug, который не совпадает ни с одной из таблиц, возвращает `{}` с кодом `200`. `ConfigHelper.load` считает ответ без `id` неизвестным сайтом и вызывает `notFound()` из Next, поэтому неизвестный поддомен получает настоящую 404, а не последующие вызовы к `/…/undefined`. Маршрут страницы конструктора также строит путь дерева через `pageTreePath()` (`src/helpers/pageTreePath.ts`), который URL-кодирует slug, поэтому некорректный slug (обратные слеши, пробелы) возвращает 404, а не превращает `400` от API в 500.

### Пользовательские домены {#custom-domains}

Пользовательский домен церкви завершается на **пограничном уровне Caddy** (подробно описан ниже), который переписывает заголовок `Host` на `{sub}.b1.church` сайта перед проксированием в B1App. Поэтому на обычном пути B1App получает *внутренний* хост `*.b1.church` и определяет его по метке хоста точно так же, как нативный поддомен — поиск middleware в БД никогда не срабатывает. `src/middleware.ts` всё равно выполняется для каждого запроса, но с одной постоянной задачей и одним резервным вариантом:

1. **Всегда** — он **удаляет любой заголовок `x-site`, переданный клиентом**. Этот заголовок является подделываемым входным параметром переписывания и доверяется только тогда, когда его устанавливает сам middleware; удаление его — настоящая задача middleware за Caddy.
2. **Резервный вариант, только для не-внутреннего `Host`** — для сырого `Host` пользовательского домена, который доходит до B1App *без* переписывания Caddy, вызывается `GET /membership/domains/public/lookup/{host}`, и если возвращается `subDomain`, устанавливается `x-site: {subDomain}.b1.church`. За Caddy эта ветка неактивна, так как `Host` уже равен `*.b1.church`.

Внутренние хосты — `localhost`, `b1.church` и суффиксы `.b1.church`, `.localtest.me`, `.localhost`, `.up.railway.app`, `.vercel.app` — полностью пропускают поиск (они уже определены переписыванием по метке хоста или являются превью- или деплой-хостами).

Сам поиск (`DomainRepo.loadByName`) выполняет left join `domains → churches` и `domains → sites` и возвращает `COALESCE(NULLIF(sites.subDomain,''), churches.subDomain)` — поддомен назначенного второстепенного сайта, если домен указывает на него, иначе поддомен церкви. Сначала он ищет точное совпадение хоста; если хост начинался с `www.` и не нашёлся, поиск повторяется **один раз** для голого апекса.

В `next.config.mjs` правила переписывания `x-site` размещены **перед** общими правилами хоста, поэтому они имеют приоритет. `x-site: grace.b1.church` → первая метка `grace` → `[sdSlug] = grace`, а дальше определение идентично пути через поддомен (тот же `churches/lookup`, тот же `siteId`).

:::info
Заголовок `x-site` извне недоверенный. Middleware безусловно удаляет любой входящий `x-site` перед тем, как optionally установить свой собственный, и правила переписывания видят только значение, установленное middleware — клиент не может навязать себя контенту другой церкви, отправив заголовок.
:::

Две эксплуатационные детали middleware:

- **Кэш.** Результат для каждого хоста (попадание *или* подтверждённый промах — никогда не сетевая ошибка) кэшируется на **10 минут** во встроенном `Map` в памяти, для каждого изолята serverless.
- **Matcher.** Matcher намеренно снова включает `/sitemap.xml`, `/robots.txt` и `/manifest.webmanifest`. Его первый шаблон исключает пути с точкой, которые иначе отбросили бы эти файлы; они добавлены обратно, чтобы SEO- и PWA-файлы каждой церкви на пользовательском домене тоже получали заголовок `x-site`.
- **Канонический заголовок.** Для страниц церкви middleware добавляет к ответу заголовок `Link: <{proto}://{host}{path}>; rel="canonical"`, который указывает хост, с которого фактически отдана страница — поддомен или пользовательский домен (`helpers/canonicalLink.ts`). Он пропускается на не-церковных хостах (`b1.church`, `localhost`, `*.vercel.app`, `*.up.railway.app`) и на `/mobile`, `/login`, `/logout`, а также на генерируемых файлах robots, sitemap и manifest.

### Отключённый публичный сайт

Церковь может включить **Disable Public Website** в B1Admin (настройка контента уровня церкви `hidePublicSite = "true"`). Тогда сайт отдаёт только маршруты для участников:

- **Middleware B1App** ищет поддомен (`/membership/churches/lookup`, затем `/content/settings/public/:churchId`) и перенаправляет анонимные запросы к любому пути вне списка разрешённых на `/login?returnUrl={path}{query}`. Список разрешённых (`helpers/publicSite.ts`): `/login`, `/logout`, `/mobile/*`, `/register/*`, `/guest-register`, а также файлы manifest, robots и sitemap. Кэшируются только подтверждённые ответы (60 секунд в продакшене, так как вызов revalidate из админки не может очистить эту карту, которая хранится в каждом экземпляре; в dev и test без кэша). Ошибка API отдаёт сайт, а не блокирует всех.
- **Авторизованные участники видят полный сайт.** Запрос с неистекшим cookie `jwt` (функция `hasSession()` в middleware декодирует `exp` из payload без проверки подписи — это мягкий шлюз, а не контроль доступа) пропускает перенаправление, поэтому после входа участник возвращается на запрошенную страницу и видит обычные страницы, встроенные страницы (Groups, Sermons и т. д.) и навигацию в заголовке. Компоненты страниц и `Header` больше сами не проверяют `hidePublicSite`.
- **`robots.txt`** запрещает всё, как и на хостах с noindex.
- **API.** `GET /content/pages/public/:churchId` (список страниц для sitemap) возвращает `[]`, поэтому анонимные вызывающие не могут получить список страниц.

### Передача `siteId`

`ConfigHelper` сохраняет разрешённый `siteId` в своём `ConfigurationInterface` для каждого запроса (мемоизировано через `cache()` из React) и добавляет `?siteId=` к вызовам контента, которые он сам и компоненты страниц делают — **условно**: пустой `siteId` (поддомен основной церкви) полностью опускает параметр. Эндпоинты, которым передаётся параметр: дерево страниц (`/content/pages/:id/tree`), публичный список страниц для sitemap (`/content/pages/public/:id`), глобальные стили (`/content/globalStyles/church/:id`), ссылки навигации (`/content/links/church/:id`) и отдельный блок футера (`/content/blocks/public/footer/:id`). На обычном пути рендеринга футер приходит внутри дерева страниц (секции с `zone: "siteFooter"`), уже полученного с `siteId`, поэтому футера без привязки к сайту не возникает.

Портал участников (B1App `mobile`) намеренно находится вне этого: `loadChurchAppearance.ts` определяет церковь через `churches/lookup`, но читает настройки уровня церкви `/settings/public/{id}` и никогда не передаёт `siteId` — в версии v1 портал общий для всей церкви (см. ниже).

## Несколько веб-сайтов у одной церкви

### Модель данных

Новая таблица `membership.sites` намеренно минимальна:

| Столбец | Тип | Примечания |
|--------|------|-------|
| `id` | `char(11)` PK | |
| `churchId` | `char(11)` | Церковь-владелец |
| `name` | `varchar(255)` | Отображаемое имя (например, "Español", "Youth") |
| `subDomain` | `varchar(45)` | **Уникальный индекс** — глобальное пространство имён (см. ниже) |

Привязка к сайту задаётся одним столбцом, не допускающим NULL, который добавляется в таблицы контента и доменов:

| Таблица (модуль) | Столбец | Значение `''` |
|----------------|--------|-----------|
| `domains` (membership) | `siteId char(11) NOT NULL DEFAULT ''` | Домен обслуживает основной сайт |
| `pages`, `links`, `globalStyles`, `blocks` (content) | `siteId char(11) NOT NULL DEFAULT ''` | Основной сайт — а для **`blocks`** `''` дополнительно означает *общий для всех сайтов* |

Две миграции добавляют всё это (`tools/migrations/membership/2026-07-02_sites.ts`, `tools/migrations/content/2026-07-02_site_id.ts`). Поскольку столбец по умолчанию равен `''`, каждая существующая строка сохраняет текущее поведение без какого-либо заполнения данных.

**Глобальное пространство поддоменов.** `sites.subDomain` использует *одно* пространство имён с `churches.subDomain` — поддомен сайта никогда не может совпасть с поддоменом церкви или другого сайта. Это соблюдается на **обоих** путях сохранения: `SiteController.save` отклоняет slug, совпадающий с `churches` или `sites`, а `ChurchController.validateSave` делает то же в обратном направлении. Уникальный индекс по `sites.subDomain` обеспечивает это на уровне базы данных.

**Уникальность страниц** расширена с `(churchId, url)` до `(churchId, siteId, url)`, поэтому два сайта одной церкви могут каждый иметь собственную страницу `/about`.

### Контент по сайтам с резервными вариантами

Каждый эндпоинт списка или дерева контента, привязанный к сайту, принимает необязательный `?siteId=` (если его нет ⇒ `''` = основной): дерево страниц, список, публичные страницы, список блоков, блоки по типу, футер, ссылки (анонимные, отфильтрованные, все) и глобальные стили. Секции и элементы напрямую не привязаны к сайту — они наследуют эту привязку через родительскую страницу или блок.

Две цепочки определения выполняют основную работу:

- **Глобальные стили — `сайт → основной → по умолчанию`.** `GlobalStyleRepo.loadForChurch(churchId, siteId)` возвращает собственную строку сайта; если у второстепенного сайта её нет, возвращается **строка основного сайта (`''`) как есть** (сохраняя её `id` и `siteId`, которые клиент использует для copy-on-write); если нет и основной строки, `GlobalStyleController` возвращает жёстко заданную палитру и шрифты по умолчанию.
- **Блок футера — приоритет у сайта, общий — резервный.** `BlockRepo.loadByBlockType(churchId, "footerBlock", siteId)` возвращает общие (`''`) *и* специфичные для сайта строки; резолвер выбирает собственный футер сайта, если он есть, иначе общий. Та же логика выполняется и в `TreeHelper.insertBlocks` (дерево страниц), и в отдельном эндпоинте `/content/blocks/public/footer/:churchId`.

### Каскадное удаление сайта

`SiteController.delete` (доступен при разрешении Settings→Edit модуля membership) удаляет второстепенный сайт в три шага:

1. `ContentModuleGateway.deleteSiteContent(churchId, siteId)` каскадно удаляет весь контент, принадлежащий сайту: его **страницы** → их секции, элементы, `pageHistory` и `posts`; его собственные **блоки** → их секции, элементы и `pageHistory`; его **ссылки** и **globalStyles**. Защита не позволяет выполнить это для `''` — основной или общий сентинел никогда не каскадируется.
2. `DomainRepo.clearSiteId` **переназначает** домены сайта обратно на основной (`siteId → ''`), а не удаляет их, поэтому пользовательский домен переживает удаление сайта.
3. Строка `sites` удаляется, а маршруты Caddy пересинхронизируются (по возможности).

### Поверхность B1Admin

| Возможность | Где | Механизм |
|-----------|-------|-----------|
| Переключатель сайтов | `useSiteSelection` + `SiteSwitcher` (пустое значение = "Main Website") | Читает параметр URL `?site=` и передаёт его как `?siteId=` в вызовы ContentApi. Присутствует в трёх разделах **списков** сайтов — **Pages**, **Blocks**, **Appearance** — но *не* в редакторах страниц и блоков, которые хранят `siteId` в самой записи |
| Создание и удаление сайтов | `SitesDialog`, открывается из пункта «Manage websites…» переключателя | `POST /membership/sites` / `DELETE /membership/sites/:id` (название и subDomain). Доступно при разрешении Settings→Edit модуля membership (`Permissions.settings.edit` на сервере; `Permissions.membershipApi.settings.edit` в B1Admin). **Только создание и удаление — переименования в v1 нет** |
| Назначение сайта для домена | `DomainSettingsEdit` в Settings→Domains | Выпадающий список сайта для каждой строки отправляет `siteId` для каждого домена в `/membership/domains`. Столбец скрывается, если API не возвращает сайты (старая версия бэкенда) |
| Copy-on-write стили | `StylesManager.prepareForSave` | Если `siteId` загруженной строки глобальных стилей не совпадает с выбранным сайтом (то есть API вернул унаследованный основной сайт как запасной вариант), он удаляет `id` основного сайта и проставляет текущий `siteId`, принудительно создавая **вставку** новой строки для сайта вместо перезаписи основной. То же разветвление при несовпадении применяется и к блоку футера сайта |

:::info
**Что остаётся общим для всей церкви в v1 (сознательное решение о области действия, а не ограничение модели данных):** **блог** (`BlogPage` не имеет переключателя и загружает `/posts` без `siteId`), **виджеты сайта** (баннер объявлений и кнопка запуска), **перенаправления**, **логотип, GA4 и настройки церкви** и **портал участников** (B1App mobile). Обратите внимание, что это *не* «весь раздел Appearance» — глобальные стили второстепенного сайта (палитра, шрифты, типографика, отступы, навигация, пользовательский CSS) **привязаны** к сайту через описанный выше путь copy-on-write; общими остаются только подпанели баннера, кнопки запуска, перенаправлений и логотипа на странице Appearance.
:::

## Пользовательские домены: пограничный уровень Caddy (план со статической конфигурацией)

:::info
**Направление пересмотрено 2026-07-02.** Более ранний план переноса хостинга пользовательских доменов на домены, управляемые Vercel, был **отменён**, а весь код регистрации доменов в Vercel (`VercelHelper`, его переменные окружения `vercelToken`/`vercelProjectId`/`vercelTeamId`, параметры SSM и записи в проверках состояния) был удалён из Api. Самостоятельно управляемый **прокси Caddy на EC2 остаётся** постоянным пограничным уровнем для пользовательских доменов. Оставшаяся работа носит внутренний характер: замена *динамической* конфигурации Caddy через admin API на *статическую* конфигурацию, которая переживает перезапуски.
:::

### Граница

Каждый пользовательский домен церкви указывает DNS на одну коробку EC2 — `3.23.251.61`, доступную также как `proxy.b1.church`. Экран Settings→Domains в B1Admin предлагает церквям добавить апекс `A → 3.23.251.61` или `CNAME → proxy.b1.church`. Caddy завершает TLS с сертификатом Let's Encrypt для каждого домена, переписывает заголовок `Host` на апстрим `{sub}.b1.church` домена и проксирует запросы в B1App — который затем маршрутизирует их по метке хоста, как любой нативный поддомен (см. [Пользовательские домены](#custom-domains) выше).

Соответствие апстримов берётся из `DomainRepo.loadPairs`, в котором вычисляемое значение `dial` использует COALESCE для поддомена назначенного сайта, поэтому домен проксируется на правильный *второстепенный* сайт, а при его отсутствии — на основной сайт церкви:

```sql
CONCAT(COALESCE(NULLIF(s.subDomain,''), c.subDomain), '.b1.church:443')  AS dial
WHERE d.domainName NOT LIKE '%www.%'
```

Строки `www.*` исключаются из карты; Caddy обслуживает `www.{host}` через перенаправление `302` на апекс.

### Два анонимных эндпоинта питают пограничный уровень

`DomainController` предоставляет два неаутентифицированных эндпоинта только для чтения, которые коробка использует напрямую — они анонимны по необходимости, так как пограничный уровень обращается к ним до того, как появляется какой-либо контекст церкви:

| Эндпоинт | Возвращает | Роль |
|----------|---------|------|
| `GET /membership/domains/authorize?domain=` | `200`, если домен — или, для промаха по `www.`, его голый апекс — существует в `domains`; иначе `404` (включая пустой `domain`) | On-demand-TLS `ask` у Caddy: контроль злоупотреблений, решающий, выпускать ли сертификат для входящего SNI |
| `GET /membership/domains/hostmap` | `text/plain`, по одной отсортированной строке `{domain} {sub}.b1.church` для каждого маршрутизируемого домена | Файл карты host→апстрим, который коробка обновляет по таймеру |

`authorize` переиспользует `DomainRepo.loadByName` (точное совпадение хоста, затем один повтор с `www.`→апекс); `hostmap` переиспользует `loadPairs` — поэтому он учитывает сайт и исключает `www.*`, идентично маршрутам прокси, и лишь убирает суффикс `:443`.

### Сохранение и удаление домена — один необязательный push

`DomainController.save` записывает строки `domains`, а затем выполняет **один необязательный** вызов `CaddyHelper.updateCaddy()`, обёрнутый в `try/catch`, который логирует (`console.error`) и подавляет ошибку; `delete` делает то же (что также исправило прежнюю ошибку устаревшего маршрута при удалении), как и удаление второстепенного сайта (`SiteController.delete`). `updateCaddy` дополнительно ограничен таймаутом Axios в **10 секунд**, поэтому недоступный или остановленный Caddy никогда не может вызвать `500` при сохранении домена — источником истины является таблица `domains`.

### Текущее состояние — статическая конфигурация, без состояния выполнения

Коробка (Windows EC2 за постоянным Elastic IP) запускает Caddy из **статического Caddyfile**: on-demand TLS, где `ask` указывает на `/membership/domains/authorize`, плюс файл карты host→апстрим, который обновляется каждые 5 минут из `/membership/domains/hostmap` запланированной задачей, завершающейся корректной командой `caddy reload`. Конфигурация переживает перезапуски без какого-либо состояния выполнения — без повторной «подготовки» — а неизвестный SNI получает отказ TLS (сертификат для хоста, который отклоняет `authorize`, не выпускается), тогда как авторизованный, но ещё не сопоставленный хост (только что добавленный домен внутри окна синхронизации) получает чистый 404. Новые домены становятся маршрутизируемыми в течение примерно 5 минут после сохранения; их сертификаты выпускаются при первом обращении. Сборка и настройка, эксплуатация и проверенные на практике подводные камни: [Прокси Caddy для пользовательских доменов](../deployment/caddy-proxy).

### Устаревший push во время выполнения — путь отката, ожидает удаления

`CaddyHelper` (модуль membership) всё ещё может управлять Caddy через его **admin API** по адресу `caddyHost:caddyPort` (параметры SSM `caddyHost`/`caddyPort`; ничего не делает, если они не заданы; отображается в группе Integrations `ServerHealthController`): `updateCaddy()` выполняет PATCH всего массива маршрутов, а `initializeCaddy()` и эндпоинты `GET /membership/domains/caddy/init` / `GET /membership/domains/caddy` заново пересоздают сервер с конфигурацией во время выполнения. Конфигурация этого режима существовала только в памяти Caddy — та самая «амнезия при перезапуске», которую заменила эта архитектура. Механизм сохраняется исключительно как путь отката и запланирован к удалению после того, как статическая коробка проработает стабильно; push `updateCaddy()` при сохранении и удалении домена безвреден для статической коробки (её admin API доступен только с localhost).
