# Предложение по интеграции Twilio BYOK

:::caution Предложение — интеграция пока недоступна
Это проект для рассмотрения мейнтейнерами, основанный на публичном исходном коде и документации Twilio, просмотренных 22 октября 2026 года. С тех пор выпущен базовый провайдер Twilio (`@churchapps/texting` 0.6.0 и раздел **Settings > Texting** в B1 Admin): церковь вводит свой Account SID, Auth Token и номер отправителя From (провайдер также принимает Messaging Service SID, начинающийся с `MG`, но столбец `fromNumber` все еще имеет тип `varchar(20)`, слишком короткий для 34-символьного SID). Тексты отправляются отдельным запросом для каждого получателя через Messages API Twilio, а ответы STOP поступают в B1 через существующий входящий вебхук. См. [Настройки церкви: Texting](../../b1-admin/settings/church-settings.md#texting). Модель согласия, обработка расширенного отказа от рассылки (Advanced Opt-Out), статус доставки и проверки готовности настройки, описанные ниже, по-прежнему остаются предложениями, а не реализованным поведением. Сопутствующий [черновик руководства по подключению церкви](./twilio-byok-onboarding-draft) содержит предлагаемые инструкции по настройке и примеры для церквей.
:::

## Рекомендуемый путь

Добавить Twilio в существующую систему провайдеров текстовых сообщений B1, используя **собственный аккаунт Twilio церкви, учетные данные API, Messaging Service и номер телефона с поддержкой SMS**. Церковь регистрирует собственное юридическое лицо и кампанию по сообщениям, оплачивает Twilio напрямую, поддерживает согласие получателей и управляет одобрением в Twilio Console. ChurchApps предоставляет интеграцию и документацию.

Начинать следует с одной программы сообщений, одного Messaging Service и одного локального US-отправителя 10DLC на каждую церковь B1. Поддерживать индивидуальные сообщения, групповые сообщения, сообщения из процессов и напоминания о подписке через существующие экраны B1. Разумная первая программа охватывает изменения служений, напоминания о событиях и планирование волонтеров — при условии, что все три описаны в согласии этой церкви и в одобренной кампании. Сбор средств или рекламные сообщения требуют отдельной оценки области применения и согласия; не добавляйте их молча в эту программу.

| Зона ответственности | Церковь | B1 / ChurchApps |
|---|---|---|
| Аккаунт Twilio, биллинг, владение номером | Владеет и администрирует | Не создает платформенный аккаунт и не перепродает кредиты |
| Бренд, кампания, регистрация номера | Подает точные данные о церкви; занимается проверкой и исправлениями | Объясняет предварительные требования и читает доступную информацию о готовности |
| Страница подписки, политики, цель сообщений | Публикует и поддерживает их | Предоставляет совместимые элементы форм, примеры и записи о согласии |
| Право получателя и обработка STOP | Проверяет доказательства согласия и запросы, полученные вне SMS | Соблюдает согласие, подавление, разрешения и подписанные вебхуки |
| Доставка и поддержка | Следит за ошибками Twilio, состоянием аккаунта и входящими ответами | Показывает статус подачи и доставки, не обещая гарантий одобрения |

Отложить собственный родительский аккаунт Twilio ChurchApps, дочерние аккаунты клиентов, покупку номеров, подачу в Trust Hub, биллинг, инбокс диалогов, MMS/WhatsApp, международную отправку и подключение toll-free. Toll-free — это отдельный путь для проверенного отправителя, а не обход регистрации. Эти границы позволяют первому релизу соответствовать существующей модели B1 «принеси собственного провайдера» (bring-your-own-provider).

## Конфигурация и дизайн учетных данных

Использовать явные, аддитивные поля конфигурации вместо перегрузки `fromNumber` или хранения структурированных данных в строке ключа API:

| Поле | Предлагаемое назначение |
|---|---|
| `accountSid` | Идентификатор аккаунта/проекта Twilio, принадлежащего церкви (`AC…`) |
| `apiKey`, `apiSecret` | Идентификатор ключа API Twilio (`SK…`) и секрет для исходящего доступа к API; зашифрованы и скрыты |
| `webhookAuthToken` | Auth Token аккаунта, которым SDK Twilio проверяет входящие подписи; отдельно зашифрован и скрыт |
| `messagingServiceSid` | Messaging Service церкви (`MG…`, 34 символа) |
| `fromNumber` | Выбранный номер с поддержкой SMS в формате E.164, подтвержденный как отправитель в этом аккаунте/сервисе |
| Конфигурация программы | Стабильный ID программы, название, разрешенные цели, URL страниц подписки и политик, версия раскрытия информации |

Twilio [предпочитает ключи API для аутентификации REST](https://www.twilio.com/docs/iam/api-keys). Используйте самые узкие протестированные права ключа, которых достаточно для отправки и требуемых проверок настройки только для чтения. Auth Token аккаунта по-прежнему нужен для [стандартной проверки подписи вебхуков Twilio](https://www.twilio.com/docs/usage/security). Объясните это различие в интерфейсе: секрет API — это не Auth Token для вебхуков. Храните учетные данные исключительно в серверном хранилище настроек, никогда — на публичных страницах, в ответах на формы, в запросах отправки из браузера или в обращениях в поддержку.

Церковь создает и управляет этими ресурсами в Console. Действие проверки B1 должно только читать настроенный сервис, отправителей и данные о регистрации. Оно не должно покупать номера, создавать кампании, менять настройки Twilio или отправлять тестовое сообщение как побочный эффект. Предоставьте отдельное явное действие тестовой отправки, ограниченное подходящим получателем, давшим согласие.

Сохранять замаскированные учетные данные только при редактировании того же сохраненного провайдера. Переключение на Twilio должно требовать собственных учетных данных и очищать устаревшие значения, специфичные для провайдера; не переносите замаскированный ключ Clearstream или Nalo в конфигурацию Twilio.

Ограничивайте каждую загрузку и обновление аутентифицированной церковью B1. Привязывайте обратные вызовы к сохраненной интеграции и ожидаемым аккаунту/сервису/отправителю Twilio, а также отклоняйте конфликтующие назначения между церквями. Ротация учетных данных и отключение провайдера должны сбрасывать готовность и приостанавливать отправки в очереди, не стирая записи о согласии и историю доставки.

## Согласие и подавление — обязательная работа для выпуска

Ввести записи подписки, привязанные к телефону, для программы Twilio, а также журналы согласия/подавления, которые только дополняются. Предлагаемый минимум доказательств: ID церкви, ID программы, нормализованный телефон, необязательная проверенная связь с человеком, утвердительное действие, ID исходной формы/отправки или проверенное внешнее подтверждение, серверная метка времени, текст/версия раскрытия информации, исходный URL, URL политик и события отзыва/возобновления. Ограничьте доступ и срок хранения в рамках существующей политики безопасности данных церкви.

Использовать такие состояния, как `unknown`, `pending`, `active` и `suppressed`. Существующие мобильные номера, импортированные контакты, посещаемость, пожертвования, членство в группах, `person.optedOut = false` и `allowSms` не являются утвердительным согласием на программу. Импорт задокументированного согласия должен быть действием с разрешением и аудитом, с записанным источником; миграция не должна подписывать всех подряд.

Для первоначального веб-процесса используйте стандартный режим публичной формы B1. Добавьте явно настроенный вопрос о согласии на SMS, который изначально не отмечен, остается необязательным, отображает кликабельные ссылки на политики и связан с одной программой и одним мобильным полем. Проверяйте это сопоставление на сервере и сохраняйте снимок показанного раскрытия информации при сохранении утвердительного ответа. Никогда не выводите согласие из произвольных подписей к вопросам, из разговорного ИИ или из членства в процессе. Включайте разговорный аналог только после того, как протестированы его явное утвердительное взаимодействие и запись доказательств.

Непомеченная отправка не создает подписки и не должна отзывать существующее согласие другого человека. Привязывайте согласие к отправленному телефону; персонал может разрешать неоднозначные связи с человеком, не объединяя записи домохозяйств. При смене мобильного номера требуется новое согласие. Для анонимных форм применяйте средства защиты от злоупотреблений и явно указывайте любую проверку владения номером или шаг двойного подтверждения; один отмеченный флажок не доказывает, кому принадлежит телефон. Если используется подтверждение, оставьте подписку в статусе ожидания до его завершения и точно опишите этот процесс в материалах для регистрации.

Для Twilio отделите подавление SMS от видимости в каталоге. Осторожно переносите любой устаревший отказ от рассылки в запись подавления; остальных устаревших получателей оставляйте в состоянии `unknown`. Явная, задокументированная новая подписка может установить согласие на SMS, при этом приватность каталога остается неизменной. Сохраняйте поведение других провайдеров, пока их миграции не будут отдельно рассмотрены.

При каждой фактической отправке требуется, чтобы интеграция церкви была включена и готова, чтобы было действующее согласие программы на точный телефон, не было подавления на уровне телефона и выполнялось существующее разрешение вызывающего. Напоминания дополнительно учитывают `allowSms`, предпочтения по категориям и тихие часы. Повторно проверяйте после постановки в очередь, подставляйте поля, нормализуйте и проверяйте номера, удаляйте дубликаты по телефону. STOP подавляет все отправки для службы/программы, включая ручные отправки и процессы; он также должен охватывать всех людей, использующих этот телефон.

Единообразно выводите идентификацию церкви и инструкцию STOP в общем пути отправки Twilio и показывайте предварительный подсчет итогового SMS/сегментов. Подстановка полей и обработка длины должны сохранять эти элементы; не обрезайте молча инструкцию об отказе. Держите примеры и реальные шаблоны напоминаний/процессов согласованными.

## Отправка, ответы и состояние доставки Twilio

Реализуйте `TwilioProvider.sendMessage` через Messages API с выбранным Messaging Service и отправителем. Возвращайте SID сообщения провайдера и результат «принято/отправлено»; подтверждение HTTP — это не доставка на телефон получателя. Групповая отправка использует результаты по каждому получателю в порядке входных данных.

Ограничивайте параллельность исходящих запросов для **и** `sendBulk`, и отдельных отправок: текущая ветка слияния полей запускает параллельные вызовы `sendMessage`. Сохраняйте намерение отправки и задачи, которые можно забрать, для групп, не умещающихся в бюджет запроса; повторно используйте существующую модель развертывания, не требуя от церквей запускать еще один сервис. Повторяйте известные временные ошибки и ошибки ограничения частоты с экспоненциальной задержкой. Рассматривайте неоднозначные тайм-ауты как неизвестный результат, который нужно сверить, а не как повод слепо переотправить и рискнуть получить дубликаты сообщений и списаний.

Настройте обратные вызовы входящих сообщений и статусов для конкретной церкви. Проверяйте `X-Twilio-Signature` с помощью SDK, точного настроенного внешнего URL, исходных параметров формы и соответствующего Auth Token аккаунта. Одного секретного URL недостаточно. Сопоставляйте обратные вызовы с сохраненными записями церкви/аккаунта/сообщения, обрабатывайте дубликаты и обратные вызовы, которые приходят до фиксации результата отправки, и не позволяйте более старым событиям перезаписывать окончательный статус. Возвращайте пустой TwiML для подтверждения входящего сообщения и соответствующий ответ об успехе для событий статуса. [Безопасность Twilio](https://www.twilio.com/docs/usage/security), [обратные вызовы статуса](https://www.twilio.com/docs/messaging/guides/track-outbound-message-status)

Рекомендуйте **Advanced Opt-Out** для Messaging Service. Twilio сам отвечает за подтверждения STOP/START/HELP; B1 использует аутентифицированные события `OptOutType` и не отправляет повторных подтверждений. STOP сразу записывает подавление; START восстанавливает подписку только для известного человека на ту же раскрытую программу, с новым событием возобновления, и не должен подписывать новый телефон на несвязанные сообщения или включать предпочтения напоминаний. HELP никого не подписывает. Прочие входящие ответы остаются вне области инбокса B1; церквям нужно задокументированное способ отслеживать их в Twilio. [Advanced Opt-Out](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out)

Храните SID сообщения Twilio, привязку к аккаунту/сервису, время подачи, окончательный статус/код ошибки и время обратного вызова вместе с журналом доставки. Точно отображайте статусы «в очереди/принято», «доставлено», «не доставлено», «недоставлено» или «неизвестно». Сохраняйте существующий контракт ответа для других провайдеров и определите, означают ли агрегированные счетчики успеха подачу или доставку.

## Готовность настройки и проверка одобрения

Показывайте отдельные контрольные точки для учетных данных, принадлежности сервиса/отправителя, верификации кампании, регистрации номера, проверок вебхуков и доставленного контрольного теста. Никогда не показывайте один зеленый значок «одобрено» только потому, что учетные данные работают.

Для локальных US-номеров читайте [ресурс кампании Usa2p](https://www.twilio.com/docs/messaging/api/usapptoperson-resource) сервиса и требуйте, чтобы соответствующая кампания имела статус `VERIFIED`. Отдельно проверяйте, что выбранный телефон связан с этим сервисом и завершил регистрацию номера: одобренная кампания может иметь номер в ожидании. Если поддерживаемый API для чтения не раскрывает нужный сигнал, показывайте **требуется ручная проверка в Console** и записывайте датированное подтверждение администратора церкви как таковое; не помечайте его как проверенное через API. Автоматические события регистрации номеров могут стать последующей задачей. [Ошибки регистрации номера](https://www.twilio.com/docs/api/errors/30035), [события регистрации A2P](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/event-streams-setup)

Требуйте актуальные проверки перед включением отправок; записывайте, когда и как проверялась готовность, сроки устаревших проверок и приостанавливайте отправки при отзыве учетных данных, смене отправителей, ошибках регистрации или постоянных ошибках аккаунта. Успешная доставка контрольного теста подтверждает проверенный путь, но не универсальное одобрение оператором связи или согласие получателя. Сопутствующий черновик описывает проверки церкви перед подачей, перед запуском и в ходе постоянной эксплуатации.

## План репозиториев и выпуска

[Руководство по вкладу в организацию](https://github.com/ChurchApps/.github/blob/main/CONTRIBUTING.md) направляет запросы функций B1 в ChurchAppsSupport, а реализационные PR — в соответствующие репозитории. Используйте один центральный запрос функции и связывайте с ним целевые PR с реализацией:

1. **ChurchAppsSupport:** проверить этот проект и его черновик руководства перед тем, как представлять Twilio как доступную функцию для пользователей.
2. **Packages:** добавить адаптер Twilio, явные общие конфигурацию/интерфейсы и отрисовку формы согласия на SMS там, где она общая для B1Admin/B1App. Включить changesets и опубликовать через существующий релизный процесс до обновления потребителей.
3. **Api:** добавить аддитивные миграции для метаданных интеграции, согласия/подавления и состояний доставки; реализовать проверку конфигурации, общие шлюзы отправки, сохранение доказательств из форм, обработку вебхуков и устойчивое сохранение отправок.
4. **B1Admin:** добавить UI конфигурации и готовности Twilio, управление программой и согласием, сохранение отправителя с учетом провайдера и точную отчетность о доставке. Не предоставлять переопределение согласия на SMS через обычное редактирование человека.
5. **B1App:** проверить публичную форму/страницу и опыт работы со ссылками на политики относительно общих элементов управления, включая анонимных посетителей и посетителей с мобильных устройств. Отдельный браузерный клиент Twilio не нужен.
6. **ChurchAppsSupport:** после выпуска превратить черновик руководства в поддерживаемые страницы настроек/справки, добавить реальные скриншоты, поставить ссылку из настроек Texting и организовать переводы.

Сначала развертывайте схему и общие пакеты, затем потребителей. Держите Twilio за функциональным флагом для небольшого пилота с добровольным участием; существующие провайдеры должны продолжать работать. Откат отключает отправку через Twilio и отменяет неотправленные задания, сохраняя отказы от рассылки и доказательства; он не должен автоматически переключать получателей на другого провайдера или отправителя.

## Оценка трудозатрат

Плановая оценка для участника, знакомого с экосистемой; в этой оценке не использовались рабочие учетные данные или реальные SMS:

| Работа | Дни разработки |
|---|---|
| Адаптер, расширения конфигурации/схемы, UI настроек | 2–3 |
| Согласие по телефону/программе, независимое подавление, общие шлюзы отправки, интеграция с публичной формой | 3–5 |
| Подписанные обратные вызовы, сохранение доставки, ограниченная/устойчивая диспетчеризация | 2–3 |
| UI готовности, руководство для церкви, интеграционное и регрессионное тестирование, исправления пилота | 3–4 |
| **Рекомендуемый объем запуска** | **10–15 всего** |

Базовый прототип адаптера/настроек занимает примерно 1–2 дня. Оценка только отправителя не включает работу по согласию и руководству, необходимую для этой рекомендации. Время внешней проверки Twilio и операторов связи отдельное и переменное; проект не должен обещать дату одобрения или результат одобрения.

## Критерии приемки

- [ ] Церковь владеет аккаунтом, сервисом, зарегистрированным отправителем и кампанией и оплачивает их; аккаунт Twilio, управляемый ChurchApps, не требуется.
- [ ] Учетные данные зашифрованы и скрыты, ограничены по арендатору, подлежат ротации и отсутствуют в логах и публичном контенте; проверка только читает данные.
- [ ] Необязательный неотмеченный флажок согласия отображает реальные ссылки на политики и сохраняет на сервере доказательства по программе/телефону/раскрытию информации; отказ все равно позволяет выполнить основное действие формы.
- [ ] Все ручные, групповые, пути с подстановкой полей, процессов и напоминаний применяют один и тот же шлюз допуска Twilio. Получатели без статуса, без согласия, со сменившимся телефоном или с подавлением пропускаются с понятной причиной; при отрисовке после подстановки и обработке длины сохраняются идентификация церкви и инструкции STOP.
- [ ] Устаревшая приватность каталога не подписывает получателей; STOP/START никогда не меняют видимость в каталоге или несвязанные предпочтения. Протестированы случаи общего телефона и нескольких церквей.
- [ ] Покрыты подписанные STOP/START/HELP, недействительные подписи, неверные аккаунты/сервисы, дублирующиеся события, повторно отправленные формы и подделанные сопоставления согласия.
- [ ] Протестированы размер группы/тайм-ауты, ограничения частоты, частичные сбои, неоднозначные результаты, гонки обратных вызовов и события доставки не по порядку — без дублирования отправок.
- [ ] Одобрение кампании и завершенная регистрация номера отличаются от проверки учетных данных. Ручные доказательства четко помечены; устаревшая или отозванная готовность блокирует отправки.
- [ ] Пилотная церковь проверяет свою страницу подписки, пути принятия и отказа от формы, точные URL политик и тестового получателя, давшего согласие, — от отправки и доставки через подавление STOP до разрешенной повторной подписки.
- [ ] Существующие настройки и поведение отправки для Clearstream, Text In Church и Nalo проходят регрессионные проверки; тексты справки отличают предложения от выпущенных функций.
