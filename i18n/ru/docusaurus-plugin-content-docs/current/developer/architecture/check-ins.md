# Регистрация (Check-In)

<div class="article-intro">

Регистрация — это одна система с тремя точками входа: киоск B1Checkin для станций с сотрудниками и для самообслуживания, самостоятельная регистрация в портале участников B1App и учёт посещаемости в B1Admin. Все три пишут в один модуль посещаемости ядра Api, а маршрутизация по классам полностью определяется Группами — отдельной сущности «локаций» или «комнат» нет. Поверх этого работает слой безопасности детей: типы регистрации для каждого визита, серверные ограничения по вместимости и соотношению волонтёров, проверка возраста и класса на стороне киоска, проверка доверенного лица при выдаче ребёнка и оповещение родителей через SMS-провайдера церкви. На этой странице описаны модель данных, сценарии регистрации, слой безопасности и конвейер печати этикеток.

</div>

### Как сохраняется завершённая регистрация

`VisitController.postCheckin` (`Api/src/modules/attendance/controllers/VisitController.ts`) обрабатывает `POST /attendance/visits/checkin?serviceId=&peopleIds=`. Тело запроса — это массив объектов `Visit`, каждый из которых содержит `visitSessions`, где вложенная `session` указывает только пару `(serviceTimeId, groupId)`. Затем сервер:

1. **Проверяет вместимость и соотношения до любой записи.** `evaluateGates()` → `CheckinGateHelper.evaluate()` проверяет вместимость каждой целевой комнаты, вместимость для гостей, флаг закрытия и соотношение волонтёров относительно текущей загрузки. postCheckin **не выполняется в транзакции**, поэтому шлюз должен сработать до первого сохранения: жёсткое нарушение возвращает 409 с указанием комнат, и ничего не сохраняется. См. [Ограничения по вместимости и соотношению волонтёров](#capacity-and-volunteer-ratio-gates).
2. **Лениво определяет сессии.** `getSessionId()` находит или создаёт строку `sessions` для `(groupId, serviceTimeId, today)` — идентификаторы сессий кешируются в процессе для каждой даты. Новые сессии генерируют вебхук `session.created`. Цикл — это ожидаемый `for..of`: более ранний вариант `forEach(async …)` без ожидания гонялся с сохранением и записывал NULL в sessionId при создании первой сессии (исправлено; отмечено комментарием в коде у цикла).
3. **Заменяет записи за день.** Все существующие визиты этих людей на это служение за сегодня удаляются вместе с их visitSessions, после чего сохраняется отправленный набор. Повторная регистрация семьи, таким образом, — это идемпотентная операция «вот текущее состояние», а не добавление. Передача `?checkDuplicates=true` вместо этого возвращает `{ duplicates: [personId…] }` без записи — так киоск предупреждает перед перезаписью.
4. **Генерирует один код безопасности на пакет.** `SecurityCodeHelper.generate()` создаёт 4-символьный код из алфавита `23456789BCDFGHJKLMNPQRSTVWXYZ` (без гласных и похожих символов, поэтому коды не складываются в слова и их не путают). Сервер повторяет генерацию при коллизии с открытыми визитами той же церкви за сегодня и проставляет код в каждый визит пакета.
5. **Возвращает `{ streaks, securityCode }`.** `streaks` сопоставляет personId с количеством последовательных недель посещения; киоск отмечает вехи (каждая 5-я неделя) конфетти.

Каждый сохранённый визит также генерирует вебхук `attendance.recorded`. Чтение, `GET /attendance/visits/checkin`, возвращает визиты людей с их **последней зафиксированной даты**. Если это была предыдущая неделя, идентификаторы удаляются, и клиент получает предзаполненную копию выбора комнат прошлой недели, которая сохранится как новые записи.

### Выдача ребёнка

Два эндпоинта завершают цикл (`VisitController`):

- `GET /attendance/visits/code/:code` — сегодняшние визиты с этим кодом безопасности, которые ещё не отмечены как выданные, с заполненными сессиями.
- `POST /attendance/visits/checkout` — тело `{ visitIds, checkedOutBy?, checkedOutById? }`; проставляет `checkoutTime` и того, кто забрал ребёнка, и генерирует вебхук `attendance.checkout` для каждого визита.

Права доступа: киоски аутентифицируются с `attendance.checkin`, которое даёт ровно доступ к регистрации, выдаче и шаблонам этикеток; `attendance.view`/`attendance.edit` покрывают отчёты и ручной ввод; структура (служения, времена служения, назначения групп) требует `services.edit`. Самостоятельная регистрация участника (B1App) не требует никаких прав: любой авторизованный пользователь, связанный с человеком в церкви, может вызывать `GET`/`POST /attendance/visits/checkin`, а сервер ограничивает отправленные `personId` собственной семьёй вызывающего (иначе 403 — именно этот барьер не даёт читать чужие `securityCode`). Членство и есть разрешение; то, видят ли участники эту функцию, контролируется вкладками навигации церкви в B1App. Остальные эндпоинты регистрации (`code/:code`, `checkout`, `guardians`, `CheckinController`) остаются только для киосков и сотрудников.

## Группы управляют маршрутизацией по комнатам

Нигде в системе нет сущности комнаты или класса. «Комната» — это группа членства с включённым `trackAttendance`, связанная с одним или несколькими временами служения через `groupServiceTimes`. Поля группы (в `Api/src/modules/membership/models/Group.ts`), которые определяют поведение киоска:

| Поле | Эффект |
|------|--------|
| `trackAttendance` | Группа вообще участвует в посещаемости; дерево настройки в B1Admin помечает группы с `trackAttendance` без строки `groupServiceTimes` как неназначенные |
| `parentPickup` | Помечает детскую комнату: регистрация в неё делает визит «детским», что печатает этикетку выдачи семье и помещает код безопасности на бейдж |
| `printNametag` | Печатать ли бейдж при регистрации в эту группу |
| `capacity` / `guestCapacity` / `checkinClosed` | Ограничения вместимости комнаты и жёсткий переключатель «закрыто», который применяется на сервере шлюзом регистрации (редактируется в настройках группы в B1Admin в разделе «Вместимость регистрации») |
| `volunteerRatio` / `minVolunteers` | Соотношение детей и волонтёров и минимальное число волонтёров, применяются согласно общецерковной настройке `ratioEnforcement` |
| `minAgeMonths` / `maxAgeMonths` / `minGrade` / `maxGrade` | Границы возраста и класса для допуска, проверяются на стороне киоска для выделения или затемнения комнат |

Каждый клиент денормализует данные одинаково (например, `B1Checkin/app/services.tsx`, `B1App/src/app/[sdSlug]/mobile/components/screens/CheckinPage.tsx`): параллельно загружаются `GET /attendance/servicetimes?serviceId=`, `GET /attendance/groupservicetimes` и `GET /membership/groups`, затем для каждого времени служения собираются группы, чья строка `groupServiceTimes` на него указывает, в `serviceTime.groups`. Этот массив и показывает выбор комнаты, упорядоченный по `categoryName` группы.

Назначения редактируются со страницы группы в B1Admin (`B1Admin/src/groups/components/ServiceTimesEdit.tsx` — `POST`/`DELETE /attendance/groupservicetimes`), а всё дерево Кампус → Служение → Время служения → Группа визуализируется в `B1Admin/src/attendance/components/AttendanceSetup.tsx` через `GET /attendance/attendancerecords/tree`.

:::info
Поскольку группы — это единственный источник истины, одно и то же членство в группе обеспечивает маршрутизацию на киоске, посещаемость в виде списка на страницах групп в B1Admin и отчёты о посещаемости — назначение группы на время служения является единственным шагом, чтобы сделать её пунктом регистрации.
:::

## Безопасность детей

### Типы регистрации

Каждый визит содержит `checkinType` — `member`, `guest` или `volunteer` (NULL означает устаревший/member; миграция `tools/migrations/attendance/2026-07-03_checkin_type.ts`). Тип выбирается **на стороне киоска**: чипы «Участник» / «Гость» / «Волонтёр» в развёрнутой строке участника (`B1Checkin/src/components/MemberServiceTimes.tsx`), проставляются на каждый ожидающий визит при завершении (`app/checkinComplete.tsx`, по умолчанию `member`). Сервер использует это значение в шлюзе: волонтёры учитываются в покрытии соотношения вместо вместимости, а гости — в `guestCapacity`.

### Ограничения по вместимости и соотношению волонтёров {#capacity-and-volunteer-ratio-gates}

`CheckinGateHelper.evaluate()` (`Api/src/modules/attendance/helpers/CheckinGateHelper.ts`) выполняется внутри `postCheckin` до любого сохранения (эндпоинт не транзакционный, поэтому корректность обеспечивается проверкой до сохранения). Он загружает текущую загрузку по каждой целевой группе (`VisitRepo.countActiveByGroupToday`) и конфигурацию группы через шлюз модуля membership, затем классифицирует нарушения:

- **Жёсткие (всегда блокируют):** `checkinClosed`, `current + incoming > capacity`, количество гостей больше `guestCapacity`. Пакет отклоняется с `409 { error: "capacity", groups: [{ groupId, groupName, reason }] }` — киоск показывает названную комнату.
- **Соотношение (предупреждение или блокировка):** входящие не-волонтёры в комнату, где `volunteers < minVolunteers`, волонтёров нет вовсе, или `children > volunteers × volunteerRatio`. Серьёзность определяется настройкой церкви `ratioEnforcement` (`"warn"` по умолчанию / `"block"`, редактируется в B1Admin Manage Church → Check-In, `CheckinSettingsEdit.tsx`). В режиме предупреждения возвращается `409 { warning: true, error: "ratio", … }`, если клиент не отправит повторно с `acknowledgeWarnings=true` — это повторная отправка и есть переопределение, подтверждаемое сотрудником на киоске.

### Окна регистрации по расписанию {#scheduled-check-in-windows}

Время служения может иметь необязательное недельное расписание (`dayOfWeek` 0–6, где 0 = воскресенье, `startTime`/`endTime` в формате `HH:mm`, `checkinOpenMinutes`, `checkinCloseMinutes`), редактируется в форме времени служения в B1Admin → **Посещаемость → Настройка** (`B1Admin/src/attendance/components/ServiceTimeEdit.tsx`, «Расписание регистрации»). `CheckinGateHelper.hasSchedule()` считает время служения запланированным только тогда, когда заданы оба поля `dayOfWeek` и `startTime`; незапланированные времена никогда не ограничиваются по времени. `isServiceTimeOpen()` вычисляет окно в местном времени церкви (`DateHelper.toChurchTime`). Часовой пояс — это `timeZone` церкви; если он не задан, используется первый неудалённый кампус с полем `timezone` (`MembershipModuleGateway.loadCampusTimeZone`), и только тогда — `America/New_York`. И список, и отправка ниже определяют часовой пояс одинаково: окно начинается за `checkinOpenMinutes` до начала и заканчивается через `checkinCloseMinutes` после конца (или после начала, если конца нет), обрабатывая окна, которые переходят через полночь или границу недели.

Окно соблюдается в двух местах:

- **Список:** `GET /attendance/servicetimes` добавляет к каждой строке вычисленный булев флаг `checkinOpen`. Самостоятельная регистрация в B1App (`CheckinPage.tsx`) и выбор служения на киоске B1Checkin (`app/services.tsx`) оба убирают времена с `checkinOpen === false` и показывают «Регистрация для этого служения сейчас не открыта», если у служения есть времена, но ни одно не открыто (на киоске доступна кнопка «Назад», чтобы выбрать другое служение).
- **Отправка:** внутри `evaluateGates()`, перед оценкой вместимости и соотношения, `findClosedServiceTimeGroups()` отклоняет пакет с `409 { error: "notOpen", groups: [{ groupId, groupName, reason: "notOpen" }] }`, если время служения любой целевой сессии вне своего окна. B1Checkin выводит это через экран жёсткой блокировки с причиной «регистрация сейчас не открыта» (нарушения вместимости по-прежнему показывают «комната заполнена или закрыта»).

### Допуск по возрасту и классу (на стороне киоска) {#agegrade-eligibility-kiosk-side}

Допуск в комнату — это рекомендательный элемент интерфейса, который вычисляется на киоске, а не применяется сервером. `B1Checkin/src/helpers/EligibilityHelper.ts` сравнивает дату рождения / класс человека с `minAgeMonths`/`maxAgeMonths`/`minGrade`/`maxGrade` группы (порядок классов: PreK, K, 1–12, Graduated) и возвращает `eligible` / `ineligible` / `unknown` — отсутствие данных даёт `unknown` и никогда не скрывает комнату. Возраст и класс вычисляются на дату **перевода в следующий класс** церкви (настройка `gradePromotionDate`, `"MM-DD"`, редактируется в `B1Admin/src/settings/components/GradePromotionSettingsEdit.tsx`); киоск получает её из `GET /attendance/checkin/settings`, а `resolveAsOfDate` выбирает ближайшее вхождение на сегодня или раньше. Выбор комнаты подсвечивает подходящие комнаты и затемняет неподходящие; выбор затемнённой комнаты требует подтверждения сотрудника.

### Выдача доверенным лицам и лицам без разрешения {#trusted-and-not-authorized-pickup}

Лица для выдачи — это сущность членства, привязанная к семье: `householdPickupPeople` (`Api/src/modules/membership/models/HouseholdPickupPerson.ts` — householdId, необязательный personId, name, photoUrl, relationship, `status` `trusted` / `notAuthorized`, notes). CRUD: `GET /membership/householdpickup/:householdId` (любой авторизованный пользователь церкви, чтобы киоски могли его читать), а `POST` / `DELETE` ограничены правом `people.edit`. Сотрудники ведут список на карточке **Выдача** на странице человека (`B1Admin/src/people/components/PickupPeople.tsx`) — фото, степень родства и чип статуса «Доверенное лицо» / «Без разрешения».

При выдаче (`B1Checkin/app/checkout.tsx`) киоск загружает список лиц для выдачи семьи: записи `trusted` отображаются как карточки для нажатия рядом с сеткой фото взрослых членов семьи, а свободно введённое имя «Другой» сравнивается с записями `notAuthorized` нечётким совпадением (расстояние Левенштейна, `src/helpers/PickupMatchHelper.ts`) — совпадение блокирует выдачу с предупреждающим листом и кнопкой сотрудника **Переопределить**. Переопределение фиксируется в самом визите: оно отправляет `checkedOutBy` как `"OVERRIDE: {name}"` через обычный `POST /attendance/visits/checkout`, поэтому оно попадает в запись посещаемости и вебхук `attendance.checkout`, а не в отдельную таблицу аудита.

### Оповещение родителя и экстренная рассылка

`CheckinController` (`Api/src/modules/attendance/controllers/CheckinController.ts`, `/attendance/checkin`) предоставляет два SMS-эндпоинта:

- `POST /page` — `{ visitId, message }`: оповещает опекунов одного зарегистрированного ребёнка (экран выдачи на киоске, ручной режим).
- `POST /broadcast` — `{ serviceId, message }`: отправляет SMS всем взрослым зарегистрированных семей на служение (настройки администратора киоска, за подтверждающим листом, где нужно ввести `EMERGENCY`, в `B1Checkin/app/adminSettings.tsx`).

Оба эндпоинта находят взрослых членов семьи через шлюз membership, затем передают доставку в **`MessagingModuleGateway.sendBulkText`** (`Api/src/shared/modules/MessagingModuleGateway.ts`) — межмодульный вход к настроенному у церкви SMS-провайдеру (`@churchapps/texting`: TextInChurch, Clearstream или MutualMinistry; встроенного SMS-отправителя нет). Шлюз записывает строку `sentText` и записи `deliveryLog` для каждого получателя и ограничивает пакет 500 получателями; если провайдер не настроен, он возвращает `no_provider`, и киоск выводит «Провайдер SMS не настроен». Метод `dispatch()` контроллера убирает дубликаты номеров и пропускает людей без мобильного номера или с установленным `optedOut`, возвращая `{ sent, failed, skippedOptedOut, skippedNoPhone }`, чтобы киоск мог показать, что было пропущено.

## Киоск (B1Checkin)

Экраны — это файлы expo-router в `B1Checkin/app/`; общее состояние между экранами хранится в статическом классе `CachedData` (`src/helpers/CachedData.ts`), а не в состоянии React.

```
index (boot/auto-login) → selectChurch → services ──▶ lookup ──▶ household ──▶ checkinComplete
                                          │             │  ▲         │ │            │
             loads serviceTimes, groups,  │             │  └─────────┘ └▶ addGuest  └▶ print labels,
             groupServiceTimes,           │             └▶ checkout (manned)           auto-return
             labelTemplates               │                                            to lookup
```

1. **Поиск** (`app/lookup.tsx`) — поиск по телефону (`GET /membership/people/search/phone?number=`, последние 4 цифры или полный номер) или по имени (`GET /membership/people/search?term=`). При выборе совпадения загружается семья (`GET /membership/people/household/{householdId}`) и существующие визиты (`GET /attendance/visits/checkin`), и в `pendingVisits` подставляется выбор прошлой недели.
2. **Проверка семьи** (`app/household.tsx`, `src/components/MemberList.tsx`) — в строке каждого члена семьи есть метка «уже зарегистрирован», значок аллергии / `nametagNotes` и чипы текущих комнат. При раскрытии участника показывается каждое время служения с кнопкой комнаты и чипами типа регистрации «Участник» / «Гость» / «Волонтёр» (`MemberServiceTimes.tsx`). Под названием каждого времени служения `ServiceTimeHelper.getGroupSummary()` показывает группы, предлагаемые на нём (названия из `serviceTime.groups`, без пробелов по краям, без дубликатов с точностью до регистра, через запятую); если у времени нет групп, ничего не выводится.
3. **Назначение группы** (`app/selectGroup.tsx`) — дерево категорий, построенное из `serviceTime.groups`, с подсвеченными комнатами, подходящими по возрасту/классу, и затемнёнными неподходящими за подтверждением сотрудника (см. [Допуск по возрасту и классу](#agegrade-eligibility-kiosk-side)); выбор комнаты записывает визит сессии `{ session: { serviceTimeId, groupId } }` в ожидающий визит этого человека (`src/helpers/VisitSessionHelper.ts`). «Нет» очищает выбор.
4. **Завершение** (`app/checkinComplete.tsx`) — `POST /attendance/visits/checkin` с `pendingVisits` (каждый с проставленным `checkinType`), затем печать этикеток, если настроен принтер, и автоматический возврат к поиску. Ответ `409` с ошибкой вместимости или `notOpen` показывает названную комнату с причиной (заполнена/закрыта или регистрация не открыта); предупреждение о соотношении предлагает подтверждение сотрудника, которое повторно отправляет запрос с `acknowledgeWarnings=true`.

Экран **выдачи** (`app/checkout.tsx`) принимает 4-символьный код безопасности через поле с автофокусом — поэтому сканеры штрих-кодов USB/Bluetooth, работающие как клавиатура, работают без камеры — либо через экранную клавиатуру с тем же алфавитом, которая отправляется автоматически при 4 символах. Кнопка **Сканировать** открывает лист с общей камерой `src/components/CodeScanner.tsx` (по умолчанию основная камера, принимаются QR, Code 128 и Code 39), так что станции без сканера-клавиатуры могут считать этикетку выдачи; отсканированный код поступает в тот же путь `handleCode()`, что и введённый вручную. Экран ищет код, показывает детей, которых забирают, и выводит **доверенных лиц для выдачи** семьи в виде карточек для нажатия вместе с сеткой фото взрослых членов семьи (плюс вариант «Другой» со свободным вводом, который нечётко сверяется с именами без разрешения — см. [Выдача доверенным лицам и лицам без разрешения](#trusted-and-not-authorized-pickup)), затем отправляет `POST /attendance/visits/checkout` с именем/id выбранного лица. В ручном режиме экран также предлагает **Оповестить родителя** (`POST /attendance/checkin/page`) и **повторную печать этикетки безопасности** — `reprint()` пересобирает этикетки семьи через `LabelHelper.getAllLabelsFor(...)` и передаёт их через тот же конвейер `PrintUI`, что и регистрация.

Режим станции задаётся флагом AsyncStorage `@StationMode` (`"self"` | `"manned"`, переключается в `app/adminSettings.tsx`). Ручной режим добавляет точку входа выдачи на экран поиска и редактирование профиля участника (`POST /membership/people`) с экрана семьи. Защита киоска встроена: необязательный PIN (`app/setPin.tsx`, `src/components/PinEntryModal.tsx`) защищает экраны администратора и принтера, экран администратора открывается только 7 быстрыми нажатиями на логотип в шапке, а экран-заставка при бездействии (`src/hooks/useInactivityTimer.ts`) появляется между семьями.

## Самостоятельная регистрация (B1App)

Участники регистрируются на портале b1.church на экране `/mobile/checkin` (маршрутизация через `B1App/src/app/[sdSlug]/mobile/components/ScreenRouter.tsx` на `screens/CheckinPage.tsx`). Нужен вход в систему, и пользователь проходит те же четыре шага, что и на киоске — служения → семья → группы → завершение — через те же эндпоинты, а состояние хранится в `B1App/src/helpers/CheckinHelper.ts`. Отличия от киоска: семья берётся из собственного `householdId` вошедшего пользователя (шага поиска нет), и печати этикеток нет — вместо этого экран завершения показывает код безопасности пакета в виде QR-кода (`qrcode.react`) с подсказкой «покажите это на станции регистрации». Если семья уже зарегистрирована при загрузке страницы, кнопка «Показать код регистрации» заново показывает QR-код из первого существующего визита (из `GET /attendance/visits/checkin`), который содержит `securityCode`. Регистрация записывается сразу при отправке (состояния ожидания нет); QR-код нужен только для печати этикеток на киоске.

**Печать этикеток с телефона на киоске** (`B1Checkin/app/scan.tsx`, открывается кнопкой «Сканировать код» с QR на экране поиска): киоск показывает `CodeScanner` (`expo-camera` `CameraView`, по умолчанию фронтальная камера, можно переключить), который сканирует QR-коды. `ScanCodeHelper.parse()` принимает данные только тогда, когда это голый 4-символьный код из алфавита кодов безопасности, а `ScanCodeHelper.isRepeat()` игнорирует тот же код в течение 4 секунд, поэтому работают и QR из B1App, и QR-блок напечатанной этикетки. Затем экран следует по пути повторной печати при выдаче — `GET /attendance/visits/code/{code}` → `GET /membership/people/ids` → `LabelHelper.getAllLabelsFor(visits, people, code)` → `PrintUI` — и возвращается к поиску. Во время сканирования запись посещаемости не создаётся; печатаются только этикетки. Коды без активных визитов, станции без принтера и группы без этикеток каждый показывают всплывающее уведомление и возвращают к поиску.

Типы и `ApiHelper`/`ArrayHelper` берутся из `@churchapps/helpers` и `@churchapps/apphelper`; React-компоненты с B1Admin не используются совместно.

## Посещаемость на стороне администратора (B1Admin)

- **Настройка** — `/attendance` (`B1Admin/src/attendance/AttendancePage.tsx`) отображает дерево структуры и создаёт служения (`ServiceEdit.tsx`) и времена служения (`ServiceTimeEdit.tsx`). Данные о кампусах поступают из membership через хук `useCampuses()`.
- **Ручная посещаемость** находится в разделе групп, а не в разделе посещаемости: `B1Admin/src/groups/components/GroupSessionsTab.tsx` создаёт сессии (`POST /attendance/sessions`; при добавлении `SessionEdit.tsx` может создать по одной сессии для каждой другой группы с выбранным временем служения, пропуская группы, у которых уже есть сессия на эту дату) и отмечает людей присутствующими через `POST /attendance/visitsessions/log`, который находит или создаёт визит этого человека на эту сессию. Руководители групп могут отмечать посещаемость своих групп без права `attendance.edit` — контроллеры проверяют `au.leaderGroupIds`.
- **Отчёты** — тренд посещаемости и посещаемость группы — это отчёты, определённые на сервере (`B1Admin/src/components/reporting/ReportWithFilter.tsx` с ReportingApi; определения в `Api/reports/*.json`). Оба принимают `startDate`/`endDate` (дата окончания включительно); отчёт о тренде по умолчанию охватывает период от года назад до сегодня и добавляет колонку `sessionDates` по неделям, а дерево посещаемости группы на экране включает `checkinTime` каждого визита и `membershipStatus` человека. CSV посещаемости группы берётся из связанного отчёта `groupAttendanceDownload`, который `GroupAttendanceDownloadHelper` преобразует в одну строку на каждого участника группы с колонкой «присутствовал / отсутствовал» для каждой датированной сессии; история по человеку — `GET /attendance/attendancerecords?personId=` (`B1Admin/src/people/components/PersonAttendance.tsx`).

## Печать этикеток

### Шаблоны и редактор

Церкви создают собственные этикетки в B1Admin по адресу `/mobile/checkin/labels` (`B1Admin/src/attendance/LabelsPage.tsx` + `components/LabelEditor.tsx`, открывается со страницы настроек регистрации). Шаблон — это строка `labelTemplates`, поле `content` которой — JSON-массив блоков: `text`, `field`, `barcode`, `qrcode` или `box`; каждый блок позиционируется в процентных координатах со шрифтом, выравниванием, символикой (`code39`/`code128`/`qr`) и необязательными условиями видимости (например, выводить блок аллергии только тогда, когда `person.nametagNotes` не пусто). Существует два значения `labelType`: `nametag` (по одному на каждого зарегистрированного человека; поля вроде `person.displayName`, `sessions`, `securityCode` и `person.isBirthdayWeek` — `"true"`, если день и месяц рождения находятся в пределах 3 дней от сегодня, с переходом через конец года, вычисляется `LabelHelper.isBirthdayWithin()`) и `pickup` (по одному на семью; поля вроде `children`, `childrenAllergies`). Сервер поддерживает один шаблон по умолчанию для каждого типа в церкви (`LabelTemplateController.save`). Редактор содержит стартовые шаблоны, повторяющие встроенные этикетки киоска, и показывает предпросмотр на примерных данных.

### Рендеринг и печать на киоске

При завершении регистрации `B1Checkin/src/helpers/LabelHelper.ts` определяет, что печатать, по флагам групп каждого ожидающего визита: бейджи для групп с `printNametag`, плюс одна семейная этикетка выдачи, если какой-либо визит попал в группу с `parentPickup`. Визиты с `checkinType` `volunteer` пропускаются функцией `LabelHelper.selectChildVisits()`, поэтому волонтёр детской комнаты с пометкой «Выдача» никогда не вызывает печать этикетки выдачи. Код безопасности из ответа на регистрацию попадает на детские бейджи и этикетку выдачи; бейджи взрослых печатаются без кода. Если у церкви есть шаблоны, `LabelRenderer` (`src/helpers/LabelRenderer.ts`) превращает блоки и контекст полей в самостоятельный HTML-документ; иначе используются встроенные HTML-этикетки из `B1Checkin/assets/labels/` с подстановкой плейсхолдеров.

Штрих-коды генерируются как встроенный SVG чистыми TypeScript-кодировщиками из `B1Checkin/src/helpers/barcode.ts` — таблицы шаблонов Code 39 и таблицы ширин Code 128 (набор B с контрольной суммой mod-103), а QR — через пакет `qrcode`. **Эти кодировщики намеренно продублированы в B1Admin** (`LabelEditor.tsx` встраивает те же таблицы, что отмечено комментарием в коде), чтобы предпросмотр в редакторе точно совпадал с выводом киоска; изменение в одном месте нужно повторить в другом.

Конвейер печати (`src/components/PrintUI.tsx`) рендерит каждую HTML-этикетку в `WebView`, снимает её в JPG через `react-native-view-shot` и передаёт URI изображений нативному модулю Expo **printer-helper** (`B1Checkin/modules/printer-helper/`). Модуль предоставляет `scan()`, `checkInit()`, `printUris()` и события статуса, с провайдером для каждого бренда на обеих платформах:

| Бренд | Android | iOS | Примечания |
|-------|---------|-----|-------|
| Brother | `BrotherProvider.kt` (Brother print SDK) | `BrotherProvider.swift` (`BRLMPrinterKit.xcframework`) | Сетевые принтеры серии QL (QL-800/810W/820NWB/1100/1110NWB…), бумажные этикетки 29×90 с высечкой, рекомендуемый вариант по умолчанию |
| Zebra | `ZebraProvider.kt` (Link-OS SDK) | `ZebraProvider.swift` + `ZebraBridge` | Сетевое обнаружение + печать изображений по TCP/ZPL |

Выбор принтера находится в `app/printers.tsx` (сканирование сети возвращает записи `brand~model~ip`; выбор сохраняется в AsyncStorage), а `src/helpers/PrinterLog.ts` ведёт диагностический журнал на устройстве, который выводится через индикатор статуса в шапке киоска.

## Регистрация гостей

Два пути создают человека прямо во время регистрации:

- **На киоске** — кнопка «Добавить гостя» на экране семьи открывает `B1Checkin/app/addGuest.tsx`, который сначала ищет существующее совпадение среди не-участников через `GET /membership/people/search?term=`, а если его нет — создаёт человека через `POST /membership/people` и прикрепляет к текущей семье. Далее гость проходит назначение группы, как и любой участник.
- **Самостоятельно через QR** — если включена настройка церкви `enableQRGuestRegistration` (задаётся в настройках регистрации в B1Admin и читается из `GET /membership/settings/public/{churchId}`), на экране поиска киоска показывается QR-код со ссылкой `https://{subdomain}.b1.church/guest-register?serviceId=`. Эта страница B1App (`src/app/[sdSlug]/(public)/guest-register/page.tsx`) позволяет приехавшей семье зарегистрироваться самостоятельно со своего телефона через анонимный эндпоинт `POST /membership/people/guest-register`, не задерживая очередь на киоске. В окне с QR-кодом также есть кнопка **Зарегистрироваться здесь**, которая открывает ту же страницу на самом киоске (`app/guestRegister.tsx`) в `WebView` в режиме инкогнито без кеша; `src/helpers/GuestRegisterHelper.ts` строит URL и для QR, и для `WebView`, а также блокирует переходы за пределы `https://{subdomain}.b1.church/guest-register`. Экран возвращается к поиску по кнопке **Готово**, «назад» или через 120 секунд бездействия (ввод текста в форме передаётся из `WebView` как активность), а `WebView` размонтируется, чтобы данные одной семьи не попали к следующей.
