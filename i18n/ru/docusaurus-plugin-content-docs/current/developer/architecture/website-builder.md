# Архитектура конструктора веб-сайтов

<div class="article-intro">

Каждый веб-сайт церкви, обслуживаемый B1App, отображается из дерева контента — страниц, разделов, элементов — сохраненного в ContentApi и редактируемого визуально в B1Admin. Одна общая библиотека компонентов отображает как предварительный просмотр редактора, так и живой сайт, один каталог типов элементов определяет, что может появиться на странице, и отдельный сервис AI может генерировать или переписывать это дерево. На этой странице отображается весь стек: контракт элемента в `@churchapps/helpers`, конвейер рендеринга, элементы данных церкви, виджеты на уровне сайта, слой блога, страницы с контролируемым доступом, SEO, генерация AI и диалоговые формы.

</div>

## Обзор

```
┌──────────────────────────────┐             ┌─────────────────────────────────────────┐
│  B1Admin — editor            │             │  Api — /content module (ContentApi)     │
│  ContentEditor · SectionEdit │  POST /…    │                                         │
│  ElementEdit · PageLinkEdit  │ ──────────▶ │  pages ─ sections ─ elements   blocks   │
│  SiteWidgetsEdit · Blog      │             │  posts   redirects   settings   styles  │
└──────────┬───────────────────┘             └───────────────┬─────────────────────────┘
           │                                                 │ GET /content/pages/:churchId/tree?url=…
           │        shared render pipeline                   ▼            (anon, JWT honored)
           │   ┌───────────────────────────────┐   ┌─────────────────────────────────┐
           └──▶│  @churchapps/helpers          │◀──│  B1App — public site (Next.js)  │
               │    ElementTypes.ts (catalog)  │   │  Zone → Section → Element       │
               │  @churchapps/apphelper        │   │  + widgets, JSON-LD, sitemap,   │
               │    ElementRegistry, renderers │   │    redirects, branded 404       │
               │    SectionDivider, widgets    │   └───────────────┬─────────────────┘
               └───────────────────────────────┘                   │ church-data elements
┌──────────────────────────────┐                                   ▼
│  AskApi — /website/* (AI)    │             ┌─────────────────────────────────────────┐
│  generateSite · rewriteSection│            │  /giving/funds/public/…/total           │
│  generateAltText · metaDesc  │             │  /membership/groupmembers/public/…      │
│  returns JSON; B1Admin saves │             │  /attendance/servicetimes/public/…      │
└──────────────────────────────┘             └─────────────────────────────────────────┘
```

Три правила сохраняются во всем стеке:

1. **Одно дерево, два рендеринга.** Страница представляет собой дерево `страницы → разделы → элементы`, где каждый узел несет свои параметры как JSON blob `answers`. Одни и те же компоненты apphelper отображают редактор перетаскивания в B1Admin и сервер-отрендеренный публичный сайт в B1App — отдельного «формата публикации» нет.
2. **Контракт живет в `@churchapps/helpers`.** `ElementTypes.ts` — единственный каталог типов элементов; рендеринги разрешаются через реестр в apphelper; формы редактора находятся в B1Admin. Добавление типа элемента означает трогание всех трех в том порядке.
3. **Публичный сайт читает анонимные конечные точки.** Все, что нужно B1App — дерево страниц, параметры, сообщения блога, редиректы и конечные точки данных церкви в других модулях — публично. Аутентификация необязательна: JWT на анонимной конечной точке дерева разблокирует страницы только для членов, ничего больше не изменяется.

## Дерево содержимого

Модуль content (`Api/src/modules/content`) владеет данными конструктора:

| Таблица | Роль |
|---------|------|
| `pages` | Одна страница на URL: `url`, `title`, `layout`, плюс `visibility`/`groupIds` (контроль доступа) и `metaDescription` (SEO) |
| `sections` | Горизонтальные полосы на странице (или в блоке): фон, цвет текста и `answersJSON`, который содержит стиль плюс конфигурацию делителя формы `dividerTop`/`dividerBottom` |
| `elements` | Фрагменты контента внутри раздела: `elementType` + `answersJSON`, вложенные для типов макета (row/column, carousel) |
| `blocks` | Повторно используемые группы раздела/элемента (блоки нижнего колонтитула, блоки элемента), используемые на страницах |
| `posts` | Автономные сообщения блога (см. [Блог](#blog)) |
| `redirects` | Пары `fromPath → toPath` для каждой церкви, ограниченные 200 (см. [SEO](#seo-and-discoverability)) |
| `settings` | Параметры церкви ключ-значение; строки, отмеченные `public`, обслуживаются анонимно и содержат конфигурацию виджета/аналитики |

Все дерево для одного URL возвращается одним анонимным вызовом — `GET /content/pages/:churchId/tree?url=/about` — который B1App использует для рендеринга на сервере. Запросы редактора вывозят по id вместо и сохраняют внутренние id.

## Контракт элемента

### Каталог (`@churchapps/helpers`)

`Packages/helpers/src/ElementTypes.ts` определяет каждый тип элемента как `ElementTypeDefinition`: `elementType`, `label`, `category`, `schemaVersion`, `defaults` и JSON-schema-стиля `answersSchema` для его ответов. `validateElementAnswers()` намеренно снисходительна — неизвестные типы и дополнительные ключи проходят, поэтому старое содержимое никогда не ломается при обновлении каталога. **Сегодня поставляется 35 типов:**

| Категория | Типы элементов |
|----------|----------------|
| layout (6) | row, column, box, carousel, whiteSpace, block |
| content (11) | text, textWithPhoto, card, faq, iconFeature, testimonial, socialIcons, countdown, stats, table, buttonLink |
| media (4) | image, gallery, video, map |
| church (12) | logo, sermons, stream, donation, donateLink, form, calendar, groupList, groups, campaignProgress, staffGrid, serviceTimes |
| advanced (2) | rawHTML, iframe |

Элемент `sermons` — это наиболее настраиваемый из типов церкви: ответ `layout` выбирает `browse` (старый полный браузер), `grid`, `list` или `featuredLatest`, с `playlistId`, `itemCount`, `showTitles` и `showDates`, уточняющими макеты без browse.

### Рендеринги (`@churchapps/apphelper`)

Рендеринги находятся в `Packages/apphelper/src/website/components/elementTypes/`, один компонент на тип, разрешенный через `ElementRegistry.ts` — двухслойная карта, где `Element.tsx` регистрирует рендеринг по умолчанию для всех 35 типов (`registerDefaultElementRenderer`) и приложение-хозяин может переопределить любой из них во время выполнения (`registerElementRenderer`) без форка пакета.

### Формы редактора (B1Admin)

Формы настроек редактора для каждого типа находятся в `B1Admin/src/site/admin/elements/` — `ElementEdit.tsx` отправляет выделенный компонент (`GalleryEdit`, `TestimonialEdit`, `StatsEdit`, …) или встроенный построитель полей для каждого типа. Зеркало этого каталога, обращенное к AI, — это MCP инструмент API `describe_page_builder` (см. [MCP Server](../api/mcp)).

### Делители формы раздела

Разделы могут носить декоративные делители формы на обоих краях. Конфигурация находится в `answersJSON` раздела как объекты `dividerTop` / `dividerBottom` — `{ shape, color, height, flip }` с `shape`, являющимся одним из `wave, waves, slant, curve, triangle, peaks`. Apphelper отправляет компонент `SectionDivider` и помощник `parseDividerConfig()`; рендеринги раздела обоих приложений (`B1App/src/components/Section.tsx`, `B1Admin/src/site/admin/Section.tsx`) разбирают ответы и монтируют делитель, и `SectionEdit.tsx` в B1Admin предоставляет пользовательский интерфейс выбора. Пакеты доставляют только строительный блок — проводка на уровне раздела — это работа потребляющих приложений.

## Элементы данных церкви

Три типа элемента отображают живые данные церкви, а не созданное содержимое. Изоляция модуля по-прежнему применяется — каждый вызывает собственную открытую конечную точку модуля-владельца из браузера:

| Элемент | Конечная точка | Примечания |
|---------|----------|-------|
| `campaignProgress` | `GET /giving/funds/public/:churchId/:fundId/total` | Возвращает `{ fundId, totalAmount, donationCount }`, опциональное временное окно `?startDate=&endDate=`; элемент сравнивает его с ответом `goalAmount` |
| `staffGrid` | `GET /membership/groupmembers/public/:churchId/:groupId` | **Только по согласию**: группа должна иметь набор `publicRoster` (по умолчанию отключено). Проекция намеренно минимальна — `personId`, `displayName`, `leader`, photo — без контактных или демографических полей |
| `serviceTimes` | `GET /attendance/servicetimes/public/:churchId` | Возвращает дерево кампуса → сервис → время; рендеринг apphelper выполняет лучший результат schema.org `Event` JSON-LD (API возвращает простые данные) |

:::warning
`publicRoster` — это ворота конфиденциальности для `staffGrid`. Никогда не расширяйте открытую проекцию участников группы и не обходите флаг — конечная точка ростера анонимна по замыслу и минимальный список полей — это свойство безопасности.
:::

## Виджеты на уровне сайта

Два виджета отображаются на каждой открытой странице, а не внутри дерева: **AnnouncementBanner** (отклоняемая верхняя полоса страницы) и **Launcher** (плавающий центр действий для ссылок give/visit/watch-style). И компоненты, и их помощники `parse*Config()` отправляются в apphelper. Конфигурация представляет собой две открытые строки параметров — ключи `announcementBanner` и `launcher` — написанные `SiteWidgetsEdit` B1Admin (на странице Appearance) и читаемые открытым макетом B1App через `GET /content/settings/public/:churchId`. API рассматривает их как непрозрачные пары ключ-значение; имена ключей — это соглашение между двумя приложениями.

## Блог

Блог — это автономный тип контента, не слой над страницами конструктора. Строка `posts` содержит весь пост: `title`, `slug`, `excerpt`, `content` (markdown body), `authorId`, `photoUrl`, `publishDate`, `category`, `tags`. Открытая поверхность (все анонимно, `PostController`):

| Маршрут | Назначение |
|-------|---------|
| `GET /content/posts/public/:churchId` | Опубликованные сообщения, фильтруемые по `?category=&tag=`, разбитые на страницы |
| `GET /content/posts/public/:churchId/categories` | Отдельные категории в опубликованных сообщениях |
| `GET /content/posts/public/:churchId/slug/:slug` | Одно опубликованное сообщение |
| `GET /content/posts/rss/:churchId?siteUrl=` | RSS 2.0 фид, озаглавленный названием церкви, с категорией элемента и описанием выписки-или-содержимого |

Сообщение «опубликовано» один раз, когда `publishDate` установлена и прошла; будущая `publishDate` — это запланированное сообщение (скрыто публично, показано с чипом Scheduled в admin). Эндпойнты чтения обогащают каждое сообщение с `authorName`, разрешенным из `authorId` через шлюз модуля членства. Отсутствующие выписки возвращаются к содержимому с удаленным markdown (~160 символов) в картах списков, мета-описаниях и RSS. B1App обслуживает `/{sdSlug}/blog` — редакционный листинг (центрированный заголовок, который становится активным названием категории/тега при фильтрации, строка чипа фильтра категории, строки сообщения с миниатюрой слева с авторством и выписками) с RSS-фидом, объявленным как альтернативная ссылка — и `/{sdSlug}/blog/[postSlug]`, выделенный маршрут (не конвейер Zone/Section) с центрированным заголовком (категория kicker, название, авторство, правило акцента основного цвета), герой 16:9 на ширине контейнера, markdown body в читаемой колонке ~720px, теги чипа в нижнем колонтитуле статьи, полоса связанных сообщений `"More in {category}"` и JSON-LD `BlogPosting`, включая автора. Обе страницы стилизованы полностью из токенов темы, поэтому они наследуют палитру каждой церкви. URLs блога включены в карту сайта для каждой церкви. Пользовательский интерфейс авторства B1Admin (**Site → Blog**) редактирует сообщения в диалоговом окне: редактор markdown с переключателем предпросмотра, галерея изображений, обрезанная 16:9, выбор персоны автора (по умолчанию редактирующий пользователь), автозавершение категории в зависимости от существующих категорий, валидация дублирования слага и переключатель публикации; опубликованные строки ссылаются на живое сообщение, и страница подталкивает админов добавить ссылку навигации `/blog`.

## Страницы только для членов

`pages.visibility` переиспользует перечисление links навигации — `everyone` (по умолчанию), `visitors`, `members`, `staff`, `team`, `groups` (с `groupIds`) — но как **жесткие ворота доступа**, а не фильтр nav (`PageVisibilityHelper.canViewPage`). Поток:

1. Анонимная конечная точка дерева проверяет видимость для выборок на основе URL. Анонимные вызывающие страницы с воротами получают `{ restricted: true, visibility }` вместо контента — дерево никогда не пропускает.
2. Конечная точка все еще соблюдает JWT: `CustomAuthProvider` проверяет заголовок `Authorization` на *каждом* запросе, включая анонимные маршруты, поэтому выборка аутентифицированного члена одного URL разрешается нормально.
3. B1App отображает `RestrictedPage` на ответе `restricted`: она гидратизирует сеанс из сохраненных учетных данных, переполучает дерево с JWT и отображает его — или показывает вход с `returnUrl`, когда нет сеанса.

:::info
Гранулярность ворот варьируется по уровню: `groups` проверяет `groupIds` токена против списка страницы и `staff` проверяет `membershipStatus`, но `members` и `team` в настоящее время пропускают любого аутентифицированного пользователя церкви. Рассматривайте `groups` как строгий вариант.
:::

## SEO и обнаруживаемость

Все это B1App-side рендеринг над данными ContentApi — API хранит, приложение выполняет:

| Проблема | Как это работает |
|---------|------------|
| Мета-описания | `pages.metaDescription` (≤300 символов) проходит через `MetaHelper.getMetaData()` в Next.js `Metadata` (description + Open Graph) на каждом маршруте, отрендеренном конструктором. Параметры страницы B1Admin включают кнопку AI "Generate" (см. ниже) |
| Редиректы | Строки `redirects` для каждой церкви управляются в `/content/redirects` (`content.edit`, лимит 200 строк, нормализованные пути). На предполагаемый 404, маршрут страницы B1App разрешает путь против `GET /content/redirects/public/:churchId` и выполняет HTTP 308 через Next's `permanentRedirect`; несовпадающие пути проходят через `notFound()` |
| Брендированный 404 | `not-found.tsx` отображает `BrandedNotFound` с логотипом церкви, названием и темой вместо родовой ошибки |
| Структурированные данные | JSON-LD `BlogPosting` на сообщениях блога; `VideoObject` на страницах для каждой проповеди (`/{sdSlug}/sermons/[sermonId]`) и на страницах, содержащих элемент `sermons`; `Event` из элементов календаря/события на страницах конструктора; schema.org `Event` из элемента `serviceTimes` |
| Страницы проповедей | Каждая открытая проповедь получает понятную для краулинга страницу в `/sermons/[sermonId]` с полными метаданными — проповеди больше не заблокированы в элементе браузера на стороне клиента |
| Аналитика | Ключ параметров для общего пользования `ga4MeasurementId` (управляемый рядом с редиректами в B1Admin) вводит gtag GA4 для каждой церкви через `next/script` |
| Карта сайта и фиды | Маршрут `sitemap.xml` для каждой церкви включает страницы конструктора и URLs блога; листинг блога объявляет RSS фид |
| Доступность | Открытый chrome отображает ссылку пропуска, нацелив ориентир `<main id="main-content">` в каждом оборота макета |

## Генерация AI (AskApi)

Генерация страниц и сайтов работает в **AskApi**, отдельный сервис, под контроллером `/website`. Он аутентифицируется с тем же JWT `CustomAuthProvider`, что и все остальное, и является **без состояния в отношении контента**: каждая конечная точка возвращает JSON и вызывающая сторона (B1Admin) сохраняет результат через ContentApi (`POST /content/pages/importTree` создает страницу с полным вложенным деревом раздела/элемента одним вызовом; это всегда вставляется под церковью вызывающей стороны и игнорирует id в теле).

### Генерация страницы (`planPage` → `writePage`)

Шаблон страницы «AI» в `AddPageModal` B1Admin использует конвейер низкой стоимости (`AskApi/src/helpers/SiteGenHelper.ts`), построенный на одном правиле: **ни одна модель никогда не выполняет builder JSON**. Два модели разделяют работу через Vercel AI Gateway (простой HTTP, ключ SSM `/{env}/aiGatewayApiKey` или `AI_GATEWAY_API_KEY`):

- **JEV** (`typesafe-ai/jev`) — типизированная модель решений, которая возвращает выборы, баллы и булевы с вероятностями, но не может писать текст. Выбирает каждый раздел по очереди из фиксированной библиотеки шаблонов, оценивает макеты, проверяет фактичность копии и выбирает стоковые фотографии и иконки. Входная стоимость около $0,04 на миллион токенов и выходные данные бесплатны, поэтому ~90 вызовов на страницу стоят долю цента.
- **Небольшая модель чата (GPT-4.1 mini по умолчанию)** — заполняет названные, ограниченные по длине текстовые слоты выбранных шаблонов. Писатель — одна константа, переопределяемая переменной окружения `SITEGEN_COPY_MODEL` (любой id модели чата на шлюзе, например `anthropic/claude-haiku-4.5`). В слепом сравнении сбоку на трех церквях Claude Haiku 4.5 читал немного теплее, но GPT-4.1 mini был близким, примерно в 4 раза дешевле и быстрее, поэтому это вариант по умолчанию. Полная страница со всеми тремя макетами стоит около 1,3 цента, около 80% от нее писатель.

| Фаза | Конечная точка | Что происходит |
|-------|----------|--------------|
| 1 | `POST /website/planPage` | Классифицирует тип страницы (home, visit, about…), затем выбирает 10 кандидатов макета из вероятностей для каждого раунда JEV (герой + количество раздела → каждый раздел → ближе), дедупликирует, имеет JEV оценить каждого на соответствие/поток/промежутки и возвращает лучших 3 плюс голос письма и `suggestedStyle` (палитра + шрифты). Кандидаты, которые имеют одинаковые разделы до сих пор, задают JEV идентичный вопрос, поэтому раунды запоминаются по префиксу. Лучший балл ниже 6 регистрируется как `lowLayoutScore` — этот лог — это отставание шаблонов, стоящих добавления. ~2s |
| 2 | `POST /website/writePage` (один вызов на кандидата) | Писатель заполняет копию слота два раздела за вызов, параллельно, и возвращает пять заголовков героя, которых выбирает JEV; JEV проверяет фактичность каждого раздела; разделы, которые не пройдут, используют стоковую фразу или пересказывают предыдущий раздел (общие прогоны в 4 слова, проверяется в коде), переписываются параллельно с конкретной причиной; скраб кода удаляет предложения с фразами стокового сайта церкви (если не описание церкви использует их); JEV выбирает объекты фото, иконки и делитель формы героя и оценивает результат. Возвращает готовое к сохранению дерево раздела и оценку. ~6–9s |
| 3 | `POST /content/pages/importTree` | B1Admin пишет только лучший ранжированный макет (второй — резервная копия, если эта запись не пройдет), сохраняет его и открывает предпросмотр (~10s после сохранения) |

Каждая фаза — это собственный запрос, поэтому каждый вызов остается внутри лимита 29-секунд API Gateway. Шаблоны в `SiteGenHelper.buildTree` — это фиксированные деревья раздела + элемента из каталога (`text`, `row`/`column`, `card`, `iconFeature`, `faq`, `table`, `testimonial`, `textWithPhoto`, `box`, `map`, `sermons`) и ссылка токены темы (`var(--accent)`, `var(--lightAccent)`…), поэтому созданные страницы наследуют существующие параметры внешнего вида церкви. Добавление шаблона раздела означает добавление его списка слота к `SECTIONS` и его дереву к `buildTree`; модульный тест проходит каждый шаблон и проверяет дерево.

**Входы.** Копия может только излагать факты из двух источников: то, что ввел пользователь, и `churchContext.facts` — записи, которые B1Admin собирает перед планированием (открытые времена обслуживания и открытые имена групп, плюс название и адрес церкви). Те же флаги ворот шаблоны, поддерживаемые данными: `times` отображает живой элемент `serviceTimes`, когда церковь хранит времена обслуживания в B1 (типизированная таблица в противном случае), `groups` и `countdown` предлагаются только когда есть данные за ними. JEV вызовы хеджированы — дубликат срабатывает после 1,5s и первый ответ побеждает — потому что шлюз иногда заминает и вызовы почти бесплатны.

**Оставаться на тему.** Запрос пользователя — это *тема страницы*, а не фон о церкви. `planPage` классифицирует запрос (`home`, `visit`, `about`, `ministries`, `give`, `contact`, `event`, `topic`), а для страниц `event` и `topic` общие шаблоны церкви (примечание пастыря, проповеди, служения, группы, влияние сообщества, еженедельные времена и обратный отсчет, видеогерой) даже не предлагаются, в то время как `details` (когда / где / что принести) и дата `eventCountdown` предлагаются. Оба судьи оценивают релевантность на тему. B1Admin проходит `pageType` из плана в каждый вызов `writePage`.

**Полные страницы из коротких запросов.** Страницы имеют три-шесть средних раздела, щедрые длины слотов, вводную строку на разделах карт и FAQ из пяти вопросов, и проход восстановления расширяет любой раздел, который возвращается тонким. Генерация — это один клик: нет вопросов для последующих действий. Где запрос упускает обычную деталь, полная страница нуждается (время начала, комната, что принести, как зарегистрироваться), писатель заполняет его с правдоподобным, скромным выбором для редактирования церкви. Поскольку разделы написаны параллельно, эти пробелы решены **один раз**, в `planPage` (`assumedDetails`, один небольшой вызов писателя, который выполняется наряду с выборкой макета), и передаются обратно в каждый вызов `writePage` через `churchContext.assumedDetails`, поэтому один раздел не может сказать 5:00, в то время как другой говорит 5:30. JEV восстанавливает любой раздел, который противоречит запросу, записям церкви или тем решенным деталям. Решенные детали не появляются в пользовательском интерфейсе; церковь рассматривает и редактирует страницу как любую другую. Некоторые вещи никогда не придумываются: имена людей, номера телефонов, электронная почта и веб-адреса, цены, статистика, история церкви, цитаты, приписываемые людьми, и день недели для даты, которую запрос не дал одному для.

**Визуальные.** Шаблоны никогда не называют свои фотографии или иконки. Они оставляют слоты открытыми, и один универсальный проход (`visualSlots` → `pickVisuals` → `applyVisuals` в `SiteGenHelper`) проходит готовое дерево и заполняет каждый: фон раздела или запись галереи, отмеченная `auto:photo`, `auto:icon`, делитель формы героя и, без маркера вообще, любой элемент `textWithPhoto`, `card` или `image`, чья `photo` пуста. JEV выбирает каждый из текста рядом с ним (фото карты из названия карты и текста; фон из копии раздела), без повторяемого объекта на странице. Новый шаблон поэтому получает фотографии бесплатно. Фотографии — это объекты поиска Pexels, выпущенные как заполнители `pexels:<term>`, которые B1Admin разрешает через `POST /content/stock/search`; клиент, который не отправляет `resolvesPhotos`, получает встроенное изображение героя, плоские цветные полосы и карточки без фотографий. Намеренно нет портретных объектов и шаблон пастыря не несет фото: стоковый незнакомец никогда не должен стоять на месте реального человека. Для церкви без страниц еще B1Admin применяет `suggestedStyle` к глобальным стилям; существующие сайты сохраняют свой вид.

### Другие конечные точки

:::info
Кнопка переписывания `SectionToolbar` и кнопка "Generate Site" в списке страниц B1Admin остаются закомментированы на стороне клиента. Нижеуказанные конечные точки AskApi все еще отвечают; только этот пользовательский интерфейс скрыт.
:::

| Конечная точка | Назначение |
|----------|---------|
| `POST /website/generatePageOutline` → `generateSection` | Исходный двухэтапный поток страницы (план, затем один вызов LLM на раздел, выполняющий JSON элемента). Заменен в B1Admin на `planPage`/`writePage` из-за стоимости; сохранено для потребителей API |
| `POST /website/generateSite` | Генерация всего сайта. **Два-фаза по замыслу**: вызов `planOnly: true` возвращает только план многостраничный (один быстрый вызов модели), затем клиент запрашивает полный контент — сохраняя каждый запрос внутри Lambda/API-Gateway timeout |
| `POST /website/rewriteSection` | Переписывание, сохраняющее структуру: модель может только изменять ответы, содержащие текст. Сигнатура рекурсивной структуры (ids + types + order) сравнивается до и после; любое несовпадение возвращает исходный раздел с `fallback: true` вместо поврежденной структуры |
| `POST /website/generateAltText` | Вызов зрения по URL изображений до 20; возвращает краткий альтернативный текст (≤125 символов, префиксы "photo of" удалены) |
| `POST /website/generateMetaDescription` | Одно SEO мета-описание (≤155 символов) из текстового содержимого страницы — проводится на кнопку Generate на параметры страницы B1Admin |

Приглашения для этих конечных точек — это файлы markdown в `AskApi/config/instructions/`, включая каталог элемента, генерируемый моделью. Два дизайн-пункта сохраняют каталог честным: клиент передает `availableElementTypes` на каждом запросе (приглашение может использовать только типы из этого списка — сервер никогда не кодирует весь набор жестко), и MCP инструмент API `describe_page_builder` содержит то же руководство для AI агентов, работающих через [MCP](../api/mcp). Модели — это Anthropic Claude через OpenRouter — 3.5 Haiku для содержимого раздела (задержка), 3.5 Sonnet для контуров, планов сайтов и зрения — с резервной копией OpenAI, когда не настроен ключ OpenRouter.

## Диалоговые формы

Формы (модуль членства) получили диалоговый режим, направленный на страницы карточки подключения. Четыре столбца на `forms` управляют им: `displayMode` (`standard` | `conversational`), `autoCreatePerson`, `followUpSubject`, `followUpBody`.

- **Рендеринг** — apphelper's `FormSubmissionEdit` переходит на компонент `ConversationalForm` (по одному вопросу за раз), когда `displayMode` это `conversational`; страница формы B1App передает режим через. Одинаковый груз отправки в любом случае.
- **Автосоздание персоны** — при отправке с набором `autoCreatePerson`, `ConversationalFormHelper.findOrCreatePerson` дедупов по электронной почте (без учета регистра) и в противном случае создает домохозяйство + персону с `membershipStatus: "Guest"`, затем связывает отправку с этой персоной.
- **Электронная почта последующих действий** — когда установлены тема и тело, отправитель получает электронное письмо на основе шаблона (с токенами `{firstName}` / `{churchName}`) через существующий путь транзакционной электронной почты (`TransactionalEmailHelper`), никогда через дверь уведомления дайджеста. Оба побочных эффекта не опасны: отказ никогда не теряет отправку.

Четыре поля устанавливаются через API сегодня; редактор формы B1Admin их не выполняет.

## Кэш открытого сайта

Путь открытого рендеринга B1App кэширует выборки с тегом церкви (`next: { revalidate: 300, tags: [sdSlug] }` в производстве; `0` в разработке), поэтому живая страница может оставаться устаревшей до пяти минут после записи ContentApi. `POST /api/revalidate/{sdSlug}` на B1App вызывает `revalidateTag(sdSlug)` и является единственным способом сбросить кэш рано.

Два писателя ударяют по нему:

1. **B1Admin** — `clearSiteCache()` в `B1Admin/src/site/siteCache.ts` POST'S после сохранения редактора. Это предпочитает поддомен активного сайта (вторичный сайт должен ударить *этот* тег, не по умолчанию церкви).
2. **Api** — Мутации контента, которые никогда не проходят через B1Admin (ключи API, MCP, AI), срабатывают `SiteCacheHelper.bump(churchId)` из контроллеров контента. Помощник разрешает поддомен церкви через `SubDomainHelper` и POST'S `{b1AppRoot}/api/revalidate/{sd}`. Отказы проглатываются, поэтому недоступный B1App не может не пройти сохранение.

Контроллеры, которые удаляют: страницы (сохранение, удаление, дублирование, публикация, отказ, отмена публикации, AI temp), разделы, элементы, блоки, ссылки, глобальные стили, сообщения и редиректы. Dev `b1AppRoot` это `http://{subdomain}.localtest.me:3301`; demo/staging/prod использование `https://{subdomain}.b1.church`.
