# Архитектура конструктора сайтов

<div class="article-intro">

Каждый сайт церкви, который обслуживает B1App, отрисовывается из дерева контента — страниц, секций, элементов — которое хранится в ContentApi и редактируется визуально в B1Admin. Одна общая библиотека компонентов отрисовывает и предпросмотр редактора, и живой сайт, один каталог типов элементов определяет, что может появиться на странице, а отдельный сервис ИИ может создать или переписать это дерево. Эта страница описывает весь стек: контракт элемента в `@churchapps/helpers`, конвейер отрисовки, элементы с данными церкви, виджеты для всего сайта, слой блога, страницы с ограниченным доступом, SEO, генерацию с помощью ИИ и диалоговые формы.

</div>

## Обзор

```
┌──────────────────────────────┐             ┌─────────────────────────────────────────┐
│  B1Admin — editor            │             │  Api — /content module (ContentApi)     │
│  ContentEditor · SectionEdit │  POST /…    │                                         │
│  ElementEdit · PageLinkEdit  │ ──────────▶ │  pages ─ sections ─ elements   blocks   │
│  SiteWidgetsEdit · Blog      │             │  posts   redirects   settings   styles  │
└──────────┬───────────────────┘             └───────────────┬─────────────────────────┘
           │                                                 │ GET /content/pages/:churchId/tree?url=…
           │        shared render pipeline                   ▼            (anon, JWT honored)
           │   ┌───────────────────────────────┐   ┌─────────────────────────────────┐
           └──▶│  @churchapps/helpers          │◀──│  B1App — public site (Next.js)  │
               │    ElementTypes.ts (catalog)  │   │  Zone → Section → Element       │
               │  @churchapps/apphelper        │   │  + widgets, JSON-LD, sitemap,   │
               │    ElementRegistry, renderers │   │    redirects, branded 404       │
               │    SectionDivider, widgets    │   └───────────────┬─────────────────┘
               └───────────────────────────────┘                   │ church-data elements
┌──────────────────────────────┐                                   ▼
│  AskApi — /website/* (AI)    │             ┌─────────────────────────────────────────┐
│  generateSite · rewriteSection│            │  /giving/funds/public/…/total           │
│  generateAltText · metaDesc  │             │  /membership/groupmembers/public/…      │
│  returns JSON; B1Admin saves │             │  /attendance/servicetimes/public/…      │
└──────────────────────────────┘             └─────────────────────────────────────────┘
```

Три правила действуют во всём стеке:

1. **Одно дерево, два рендерера.** Страница — это дерево `pages → sections → elements`, где каждый узел хранит свои настройки в виде JSON-блоба `answers`. Одни и те же компоненты apphelper отрисовывают редактор с перетаскиванием в B1Admin и серверно отрисованный публичный сайт в B1App — отдельного «формата публикации» нет.
2. **Контракт находится в `@churchapps/helpers`.** `ElementTypes.ts` — единственный каталог типов элементов; рендереры выбираются через реестр в apphelper; формы редактора находятся в B1Admin. Добавление типа элемента требует изменений во всех трёх местах, именно в таком порядке.
3. **Публичный сайт читает анонимные конечные точки.** Всё, что нужно B1App — дерево страниц, настройки, посты блога, редиректы и конечные точки с данными церкви в других модулях — открыто. Аутентификация необязательна: JWT на анонимной конечной точке дерева открывает страницы только для участников, а больше ничего не меняется.

## Дерево контента

Модуль контента (`Api/src/modules/content`) владеет данными конструктора:

| Таблица | Назначение |
|---------|-----------|
| `pages` | Одна страница на URL: `url`, `title`, `layout`, а также `visibility`/`groupIds` (ограничение доступа) и `metaDescription` (SEO) |
| `sections` | Горизонтальные полосы на странице (или в блоке): фон, цвет текста и `answersJSON`, в котором хранятся стили и конфигурации фигурных разделителей `dividerTop`/`dividerBottom` |
| `elements` | Элементы контента внутри секции: `elementType` + `answersJSON`, могут вкладываться для типов макета (строка/колонка, карусель) |
| `blocks` | Переиспользуемые группы секций/элементов (блоки подвала, блоки элементов), общие для нескольких страниц |
| `posts` | Самостоятельные посты блога (см. [Блог](#blog)) |
| `redirects` | Пары `fromPath → toPath` для каждой церкви, ограничены 200 записями (см. [SEO](#seo-and-discoverability)) |
| `settings` | Настройки церкви в виде пар «ключ — значение»; строки с флагом `public` отдаются анонимно и содержат конфигурацию виджетов и аналитики |

Всё дерево для одного URL приходит одним анонимным запросом — `GET /content/pages/:churchId/tree?url=/about` — из него B1App выполняет серверную отрисовку. Запросы редактора получают данные по идентификатору и сохраняют внутренние идентификаторы.

## Контракт элемента

### Каталог (`@churchapps/helpers`)

`Packages/helpers/src/ElementTypes.ts` описывает каждый тип элемента как `ElementTypeDefinition`: `elementType`, `label`, `category`, `schemaVersion`, `defaults` и `answersSchema` в стиле JSON Schema для его ответов. `validateElementAnswers()` намеренно нестрога — неизвестные типы и лишние ключи проходят проверку, поэтому старый контент не ломается при обновлении каталога. **Сегодня поставляется 35 типов:**

| Категория | Типы элементов |
|-----------|----------------|
| макет (6) | row, column, box, carousel, whiteSpace, block |
| контент (11) | text, textWithPhoto, card, faq, iconFeature, testimonial, socialIcons, countdown, stats, table, buttonLink |
| медиа (4) | image, gallery, video, map |
| церковь (12) | logo, sermons, stream, donation, donateLink, form, calendar, groupList, groups, campaignProgress, staffGrid, serviceTimes |
| расширенные (2) | rawHTML, iframe |

Элемент `sermons` — самый настраиваемый из типов для церкви: ответ `layout` выбирает `browse` (старый полный обозреватель), `grid`, `list` или `featuredLatest`, а `playlistId`, `itemCount`, `showTitles` и `showDates` уточняют макеты, отличные от `browse`.

У элемента `rawHTML` два ответа: `rawHTML` (разметка) и `javascript`. Скрипты, вставленные через `innerHTML`, никогда не выполняются, поэтому `RawHTMLElement` пересоздаёт каждый узел `<script>` в разметке как новый элемент. Эти узлы, созданные не парсером, считаются доверенными по политике CSP `strict-dynamic`. Ответ `javascript`, который начинается с `<` (сниппет вендора, вставленный вместе с тегами `<script>`), разбирается как разметка и обрабатывается так же. В остальных случаях он выполняется как обычный встроенный скрипт. B1Admin отмечает голый URL в поле JavaScript, поскольку одинокий URL выполняется как пустой скрипт. Элемент `map` ничего не отрисовывает и не загружает скрипт Google Maps, если не настроен ключ API Maps.

### Рендереры (`@churchapps/apphelper`)

Рендереры находятся в `Packages/apphelper/src/website/components/elementTypes/`, по одному компоненту на тип, и выбираются через `ElementRegistry.ts` — двухслойную карту, в которой `Element.tsx` регистрирует рендерер по умолчанию для всех 35 типов (`registerDefaultElementRenderer`), а host-приложение может переопределить любой из них во время выполнения (`registerElementRenderer`) без форка пакета.

### Формы редактора (B1Admin)

Формы настроек каждого типа находятся в `B1Admin/src/site/admin/elements/`: `ElementEdit.tsx` передаёт управление отдельному компоненту (`GalleryEdit`, `TestimonialEdit`, `StatsEdit`, …) или встроенному построителю полей для каждого типа. Зеркало этого каталога, ориентированное на ИИ, — инструмент MCP `describe_page_builder` в API (см. [MCP-сервер](../api/mcp)).

Предпросмотр редактора подключает ту же `Theme`, что и живой сайт; она задаёт CSS-переменные `--headingFont` / `--bodyFont` из глобальных стилей церкви. B1App применяет эти переменные через `pages.css`, который B1Admin не может импортировать, поэтому `ContentEditor.tsx` внедряет `EDITOR_PAGE_FONT_CSS` (`src/site/admin/editorCss.ts`), чтобы применить их к тексту `.page` и заголовкам `h1`–`h6`. Без этого в предпросмотре заголовки отображались шрифтом админки.

### Декоративные разделители секций

Секции могут иметь декоративные фигурные разделители на любом крае. Конфигурация хранится в `answersJSON` секции в виде объектов `dividerTop` / `dividerBottom` — `{ shape, color, height, flip }`, где `shape` — один из `wave, waves, slant, curve, triangle, peaks`. Apphelper поставляет компонент `SectionDivider` и вспомогательную функцию `parseDividerConfig()`; рендереры секций обоих приложений (`B1App/src/components/Section.tsx`, `B1Admin/src/site/admin/Section.tsx`) разбирают ответы и подключают разделитель, а `SectionEdit.tsx` в B1Admin предоставляет интерфейс выбора. Пакеты поставляют только строительный блок — подключение на уровне секций возлагается на приложения-потребители.

## Элементы с данными церкви

Три типа элементов отображают живые данные церкви, а не авторский контент. Изоляция модулей при этом сохраняется — каждый из них вызывает публичную конечную точку владеющего модуля напрямую из браузера:

| Элемент | Конечная точка | Примечания |
|---------|---------------|-----------|
| `campaignProgress` | `GET /giving/funds/public/:churchId/:fundId/total` | Возвращает `{ fundId, totalAmount, donationCount }`, необязательное окно `?startDate=&endDate=`; элемент сравнивает результат с ответом `goalAmount` |
| `staffGrid` | `GET /membership/groupmembers/public/:churchId/:groupId` | **Только по выбору**: у группы должен быть установлен `publicRoster` (по умолчанию выключен). Проекция намеренно минимальна — `personId`, `displayName`, `leader`, фото — без контактов и демографических полей |
| `serviceTimes` | `GET /attendance/servicetimes/public/:churchId` | Возвращает дерево «кампус → служение → время»; рендерер apphelper на его основе генерирует JSON-LD `Event` из schema.org по принципу «по возможности» (API возвращает только данные) |

:::warning
`publicRoster` — это ворота приватности для `staffGrid`. Никогда не расширяйте публичную проекцию участников группы и не обходите этот флаг — конечная точка списка анонимна по замыслу, а минимальный набор полей — это свойство безопасности.
:::

## Элемент календаря и страницы событий

Ответы элемента `calendar` — это `calendarType` (`group` | `curated`), `calendarId`, `display` (`month`, по умолчанию, или `upcoming`) и `tag`. B1App переопределяет рендерер apphelper в `src/components/Element.tsx` через `registerElementRenderer("calendar", …)`:

- **`display: "upcoming"`** отрисовывает `UpcomingEventsElement` из B1App: он загружает `GET /content/events/public/group/:churchId/:groupId` или `GET /content/curatedEvents/public/calendar/:churchId/:curatedCalendarId`, разворачивает повторения с помощью `buildOccurrences()` (`src/helpers/EventOccurrences.ts`, одно вхождение на событие в пределах года) и показывает первые 12 в виде плиток с фото (`events.photoUrl`, а при его отсутствии — название на тёмном цвете темы), ведущих на `/events/{id}`, с меню Subscribe для ICS-ленты календаря.
- **`display: "month"`** отрисовывает `CalendarElement` из apphelper с колбэком `eventUrl`. `GroupCalendar` / `CuratedCalendar` → `EventCalendar` / `CuratedEventCalendar` при нажатии переходят по этому URL вместо открытия диалога с подробностями (B1Admin не передаёт `eventUrl`, поэтому административный календарь сохраняет диалог).
- **`tag`** фильтрует оба вида с помощью `EventHelper.hasTag()` (`@churchapps/helpers`): поиск без учёта регистра по строке `events.tags` с разделителями-запятыми; пустое значение показывает всё. Объединение курируемого календаря выбирает `e.tags`, чтобы курируемые события несли теги.

Курируемые события ссылаются по `realEventId` (`eventPageId()`), поэтому URL всегда указывает на базовое событие. `/{sdSlug}/events/[eventId]` — это выделенный маршрут (не конвейер конструктора): он загружает `GET /content/events/public/:churchId/:id` — который возвращает `null` для событий в ожидании или отклонённых и для приватных событий без регистрации, а также добавляет `roomNames` из неотклонённых бронирований помещений — отрисовывает `EventPageContent` (шапка с фото, описание в markdown, боковая панель When/Where, кнопка **Зарегистрироваться на это событие**, когда включён `registrationEnabled`, и ссылка **Добавить в мой календарь** на `GET /content/events/public/:churchId/:id/ical`), использует фото как изображение Open Graph и выводит JSON-LD `Event` для следующего вхождения через `EventPageJsonLd`. Неизвестное или скрытое событие возвращает настоящую ошибку 404.

## Виджеты для всего сайта

Два виджета отрисовываются на каждой публичной странице, а не внутри дерева: **AnnouncementBanner** (закрываемая полоса вверху страницы) и **Launcher** (плавающий центр действий для ссылок в стиле «пожертвовать / посетить / смотреть»). Оба компонента и их функции `parse*Config()` поставляются в apphelper. Конфигурация хранится в двух публичных строках настроек с ключами `announcementBanner` и `launcher`; их записывает `SiteWidgetsEdit` в B1Admin (на странице Appearance), а публичный макет B1App читает через `GET /content/settings/public/:churchId`. API воспринимает их как непрозрачные пары «ключ — значение»; имена ключей — договорённость между двумя приложениями.

## Блог {#blog}

Блог — это самостоятельный тип контента, а не надстройка над страницами конструктора. Строка `posts` хранит пост целиком: `title`, `slug`, `excerpt`, `content` (тело в markdown), `authorId`, `photoUrl`, `publishDate`, `category`, `tags`. Публичная поверхность (вся анонимная, `PostController`):

| Маршрут | Назначение |
|---------|-----------|
| `GET /content/posts/public/:churchId` | Опубликованные посты с фильтром `?category=&tag=` и постраничной разбивкой |
| `GET /content/posts/public/:churchId/categories` | Уникальные категории опубликованных постов |
| `GET /content/posts/public/:churchId/slug/:slug` | Один опубликованный пост |
| `GET /content/posts/rss/:churchId?siteUrl=` | Лента RSS 2.0 с названием церкви, с категорией и описанием каждого элемента (описание из excerpt или content) |

Пост считается «опубликованным», когда `publishDate` задан и уже наступил; будущая дата `publishDate` означает запланированный пост (скрыт публично и показывается с меткой Scheduled в админке). Эндпоинты чтения обогащают каждый пост полем `authorName`, которое определяется по `authorId` через шлюз модуля membership. При отсутствии excerpt в карточках списка, мета-описаниях и RSS используется содержимое без markdown (около 160 символов). B1App обслуживает `/{sdSlug}/blog` — редакционный список (центрированный заголовок, который при фильтрации превращается в название активной категории или тега; ряд фильтров-чипов по категориям; строки постов с миниатюрой слева, авторами и выдержками), с RSS-лентой, объявленной как альтернативная ссылка, — и `/{sdSlug}/blog/[postSlug]`, выделенный маршрут (не конвейер Zone/Section) с центрированным заголовком (надпись-категория, заголовок, автор и акцентная линия основного цвета), героическим изображением 16:9 во всю ширину контейнера, телом в markdown в колонке для чтения шириной около 720 px, чипами тегов в подвале статьи, полосой связанных постов `"More in {category}"` и JSON-LD `BlogPosting`, включая автора. Обе страницы оформляются исключительно токенами темы, поэтому наследуют палитру каждой церкви. URL блога включены в sitemap церкви. Интерфейс авторинга в B1Admin (**Сайт → Блог**) редактирует посты в диалоге: редактор markdown с переключателем предпросмотра, выбор изображения из галереи с обрезкой 16:9, выбор автора (по умолчанию редактирующий пользователь), автодополнение категорий на основе существующих, проверка дублирующихся slug и переключатель публикации; опубликованные строки ведут на живой пост, а страница напоминает администраторам добавить ссылку `/blog` в навигацию.

## Страницы только для участников

`pages.visibility` использует то же перечисление, что и ссылки навигации — `everyone` (по умолчанию), `visitors`, `members`, `staff`, `team`, `groups` (с `groupIds`), — но как **жёсткое ограничение доступа**, а не фильтр навигации (`PageVisibilityHelper.canViewPage`). Порядок работы:

1. Анонимная конечная точка дерева проверяет видимость при запросах по URL. Анонимные посетители ограниченной страницы получают `{ restricted: true, visibility }` вместо контента — дерево никогда не утекает.
2. Конечная точка всё равно учитывает JWT: `CustomAuthProvider` проверяет заголовок `Authorization` при *каждом* запросе, в том числе на анонимных маршрутах, поэтому запрос авторизованного участника к тому же URL проходит обычным образом.
3. B1App отрисовывает `RestrictedPage` при ответе `restricted`: он восстанавливает сеанс из сохранённых учётных данных, повторно запрашивает дерево с JWT и отрисовывает его — либо показывает экран входа с `returnUrl`, если сеанса нет.

:::info
Степень детализации ограничения различается по уровням: `groups` сверяет `groupIds` из токена со списком страницы, а `staff` проверяет `membershipStatus`, но `members` и `team` в настоящее время пропускают любого аутентифицированного пользователя церкви. Считайте `groups` строгим вариантом.
:::

## SEO и обнаруживаемость {#seo-and-discoverability}

Всё это — отрисовка на стороне B1App поверх данных ContentApi: API хранит, приложение выводит:

| Задача | Как это работает |
|--------|------------------|
| Мета-описания | `pages.metaDescription` (≤300 символов) через `MetaHelper.getMetaData()` попадает в `Metadata` Next.js (description + Open Graph) на каждом маршруте, отрисованном конструктором. В настройках страницы B1Admin есть кнопка AI «Generate» (см. ниже) |
| Редиректы | Записи `redirects` для каждой церкви, управляемые по адресу `/content/redirects` (`content.edit`, лимит 200 строк, нормализованные пути). При пути, который стал бы 404, маршрут страницы B1App сопоставляет путь с `GET /content/redirects/public/:churchId` и выдаёт HTTP 308 через `permanentRedirect` Next; непривязанные пути передаются в `notFound()` |
| Фирменная страница 404 | `not-found.tsx` отрисовывает `BrandedNotFound` с логотипом, названием и темой церкви вместо общей ошибки. Неизвестные пути `/register/[eventId]`, `/events/[eventId]`, `/stream/[pageSlug]` и `/volunteer/[planId]` возвращают настоящий 404, как и неизвестные поддомены и некорректные slug страниц (см. [Маршрутизация сайтов и мультисайтовость](./websites)) |
| Структурированные данные | `BlogPosting` JSON-LD для постов блога; `VideoObject` на страницах отдельных проповедей (`/{sdSlug}/sermons/[sermonId]`) и на страницах с элементом `sermons`; `Event` из элементов календаря/событий на страницах конструктора и на каждой странице `/{sdSlug}/events/[eventId]` (ближайшее вхождение, с фото события как `image`); schema.org `Event` из элемента `serviceTimes` |
| Страницы проповедей | Каждая публичная проповедь получает доступную для индексации страницу `/sermons/[sermonId]` с полными метаданными — проповеди больше не заперты внутри клиентского элемента-обозревателя |
| Аналитика | Публичный ключ настроек `ga4MeasurementId` (управляется рядом с редиректами в B1Admin) внедряет gtag GA4 для каждой церкви через `next/script`. Приложение B1 (`/{sdSlug}/mobile`) тоже отправляет на этот ID просмотры страниц вместе с собственным тегом ChurchApps, если это корректный ID вида `G-` (ID контейнеров GTM остаются только для сайта). В каждом вызове `gtag('config')` передаётся `display_mode` — `installed` или `browser` — в зависимости от `navigator.standalone` или медиазапроса `(display-mode: standalone)` (`B1App/src/helpers/mobileAnalytics.ts`) |
| Sitemap и ленты | Маршрут `sitemap.xml` для каждой церкви включает страницы конструктора, URL блога и 50 самых свежих страниц проповедей (с `<lastmod>` из даты публикации каждой проповеди). Также перечисляются встроенные страницы `/sermons`, `/groups` и `/volunteer`, когда у них есть содержимое (публичные группы, планы для записи), если только сохранённый редирект не заменяет этот путь. `/` исключается, если у церкви нет домашней страницы, поскольку тогда `/` перенаправляет на запрещённый `/mobile`. Список блога объявляет ленту RSS |
| Доступность | Публичный каркас отрисовывает ссылку «перейти к содержимому», ведущую на ориентир `<main id="main-content">`, в каждом макете |

## Генерация с ИИ (AskApi)

Генерация страниц и сайтов выполняется в **AskApi** — отдельном сервисе под контроллером `/website`. Он аутентифицируется тем же `CustomAuthProvider` JWT, что и всё остальное, и **не хранит контент**: каждый эндпоинт возвращает JSON, а вызывающая сторона (B1Admin) сохраняет результат через ContentApi (`POST /content/pages/importTree` создаёт страницу со всем вложенным деревом секций и элементов одним вызовом; он всегда вставляет под церковь вызывающего и игнорирует идентификаторы из тела запроса).

### Генерация страницы (`planPage` → `writePage`)

Шаблон «AI» в `AddPageModal` в B1Admin использует недорогой конвейер (`AskApi/src/helpers/SiteGenHelper.ts`), построенный на одном правиле: **ни одна модель не выдаёт JSON конструктора**. Две модели делят работу через Vercel AI Gateway (обычный HTTP, ключ SSM `/{env}/aiGatewayApiKey` или `AI_GATEWAY_API_KEY`):

- **JEV** (`typesafe-ai/jev`) — модель типизированных решений, которая возвращает выбор, оценки и логические значения с вероятностями, но не умеет писать текст. Она выбирает каждую секцию по очереди из фиксированной библиотеки шаблонов, оценивает макеты, проверяет факты в тексте и подбирает стоковые фото и иконки. Входные данные стоят около $0,04 за миллион токенов, выходные бесплатны, поэтому около 90 вызовов на страницу обходятся в долю цента.
- **Небольшая чат-модель (по умолчанию GPT-4.1 mini)** — заполняет именованные слоты текста с ограничением длины в выбранных шаблонах. Модель-писатель — это одна константа, переопределяемая переменной окружения `SITEGEN_COPY_MODEL` (любой id чат-модели на шлюзе, например `anthropic/claude-haiku-4.5`). В слепом сравнении на трёх церквях Claude Haiku 4.5 звучал немного теплее, но GPT-4.1 mini был близок, примерно в 4 раза дешевле и быстрее, поэтому он выбран по умолчанию. Полная страница со всеми тремя макетами стоит около 1,3 цента, примерно 80% из которых — писатель.

| Фаза | Эндпоинт | Что происходит |
|------|----------|----------------|
| 1 | `POST /website/planPage` | Классифицирует тип страницы (home, visit, about…), затем берёт выборку из 10 кандидатов макета по вероятностям JEV для каждого раунда (герой + число секций → каждая секция → завершение), удаляет дубликаты, просит JEV оценить каждый по соответствию, потоку и пробелам, и возвращает топ-3 вместе с голосом письма и `suggestedStyle` (палитра + шрифты). Кандидаты с одинаковыми секциями до этого момента задают JEV одинаковый вопрос, поэтому раунды мемоизируются по префиксу. Лучшая оценка ниже 6 логируется как `lowLayoutScore` — этот лог является списком шаблонов, которые стоит добавить. ~2 с |
| 2 | `POST /website/writePage` (один вызов на кандидата) | Писатель заполняет текст слотов по две секции за вызов, параллельно, и возвращает пять вариантов заголовка героя, из которых выбирает JEV; JEV проверяет факты в каждой секции; секции, которые не прошли проверку, используют шаблонную фразу или пересказывают более раннюю секцию (общие последовательности из 4 слов, проверяются кодом), переписываются параллельно с конкретной причиной; программная чистка удаляет предложения с типовыми фразами сайтов церквей (если только собственное описание церкви не использует их); JEV выбирает темы фото, иконки и фигурный разделитель героя и оценивает результат. Возвращает готовое к сохранению дерево секций и оценку. ~6–9 с |
| 3 | `POST /content/pages/importTree` | B1Admin записывает только лучший по рейтингу макет (запасной вариант — второй по рейтингу, если запись не удалась), сохраняет его и открывает предпросмотр (~10 с после Save) |

Каждая фаза — отдельный запрос, чтобы каждый вызов оставался в пределах 29-секундного лимита API Gateway. Шаблоны в `SiteGenHelper.buildTree` — это фиксированные деревья секций и элементов из каталога (`text`, `row`/`column`, `card`, `iconFeature`, `faq`, `table`, `testimonial`, `textWithPhoto`, `box`, `map`, `sermons`) и ссылаются на токены темы (`var(--accent)`, `var(--lightAccent)`…), поэтому сгенерированные страницы наследуют существующие настройки внешнего вида церкви. Чтобы добавить шаблон секции, нужно добавить его список слотов в `SECTIONS` и его дерево в `buildTree`; модульный тест проходит по каждому шаблону и проверяет дерево.

**Входные данные.** Текст может утверждать только факты из двух источников: того, что ввёл пользователь, и `churchContext.facts` — записей, которые B1Admin собирает до планирования (публичное время служений и названия публичных групп, а также название церкви и адрес). Те же флаги управляют шаблонами, опирающимися на данные: `times` отрисовывает живой элемент `serviceTimes`, когда церковь хранит время служений в B1 (иначе — набранную вручную таблицу), а `groups` и `countdown` предлагаются только тогда, когда за ними есть данные. Вызовы JEV дублируются: повторный запрос отправляется через 1,5 с, и побеждает первый ответ, потому что шлюз иногда зависает, а вызовы почти бесплатны.

**Оставаться в теме.** Запрос пользователя — это *тема страницы*, а не фон о церкви. `planPage` классифицирует запрос (`home`, `visit`, `about`, `ministries`, `give`, `contact`, `event`, `topic`), и для страниц `event` и `topic` шаблоны общего характера для церкви (заметка пастора, проповеди, служения, группы, общественное влияние, еженедельное время и обратный отсчёт, герой с видео) даже не предлагаются, зато предлагаются `details` (когда / где / что взять с собой) и `eventCountdown` с датой. Оба судьи оценивают соответствие теме. B1Admin передаёт `pageType` из плана в каждый вызов `writePage`.

**Полные страницы из коротких запросов.** Страницы имеют от трёх до шести средних секций, щедрую длину слотов, вводную строку в секциях-карточках и FAQ из пяти вопросов; проход исправления расширяет любую секцию, которая получилась слишком короткой. Генерация — это одно нажатие: уточняющих вопросов нет. Если запрос опускает обычную деталь, которая нужна полной странице (время начала, зал, что взять с собой, как записаться), писатель заполняет её правдоподобным и скромным выбором, который церковь может отредактировать. Поскольку секции пишутся параллельно, эти пробелы решаются **один раз** в `planPage` (`assumedDetails`, один небольшой вызов писателя, который идёт параллельно с выборкой макетов) и передаются обратно в каждый вызов `writePage` через `churchContext.assumedDetails`, поэтому одна секция не может сказать 5:00, а другая — 5:30. JEV исправляет любую секцию, которая противоречит запросу, записям церкви или принятым решениям. Принятые детали не показываются в интерфейсе; церковь проверяет и редактирует страницу как любую другую. Некоторые вещи никогда не выдумываются: имена людей, номера телефонов, адреса электронной почты и веб-сайтов, цены, статистика, история церкви, цитаты, приписанные людям, и день недели для даты, которой не было в запросе.

**Визуальные элементы.** Шаблоны никогда не называют свои фото или иконки. Они оставляют слоты открытыми, и один общий проход (`visualSlots` → `pickVisuals` → `applyVisuals` в `SiteGenHelper`) проходит по готовому дереву и заполняет каждый из них: фон секции или запись галереи с маркером `auto:photo`, `auto:icon`, фигурный разделитель героя `auto:divider`, а также любой элемент `textWithPhoto`, `card` или `image`, у которого поле `photo` пусто, даже без какого-либо маркера. JEV выбирает каждый из них по тексту рядом (фото карточки — по её заголовку и тексту, фон — по тексту секции), при этом ни одна тема не повторяется на странице. Поэтому новый шаблон получает фото бесплатно. Фото — это поисковые запросы Pexels, выведенные как заполнители `pexels:<term>`, которые B1Admin разрешает через `POST /content/stock/search`; клиент, который не передаёт `resolvesPhotos`, получает встроенное изображение героя, сплошные цветные полосы и карточки без фото. Намеренно не используются портретные темы, а шаблон пастора не содержит фото: случайный незнакомец никогда не должен заменять настоящего человека. Для церкви без страниц B1Admin применяет `suggestedStyle` к глобальным стилям; существующие сайты сохраняют свой вид.

### Другие эндпоинты

:::info
Кнопка переписывания `SectionToolbar` и кнопка **Сгенерировать сайт** на странице списка страниц в B1Admin остаются закомментированными на клиенте. Эндпоинты AskApi ниже по-прежнему отвечают; скрыт только этот интерфейс.
:::

| Эндпоинт | Назначение |
|----------|-----------|
| `POST /website/generatePageOutline` → `generateSection` | Исходный двухэтапный процесс страницы (схема, затем один вызов LLM на секцию, выдающий JSON элемента). В B1Admin заменён на `planPage`/`writePage` из-за стоимости; сохранён для потребителей API |
| `POST /website/generateSite` | Генерация всего сайта. **Двухфазный по замыслу**: вызов с `planOnly: true` возвращает только многостраничный план (один быстрый вызов модели), затем клиент запрашивает полное содержимое — так каждый запрос остаётся в пределах таймаута Lambda/API Gateway |
| `POST /website/rewriteSection` | Переписывание с сохранением структуры: модель может менять только ответы, содержащие текст. Рекурсивная сигнатура структуры (id + типы + порядок) сравнивается до и после; любое несовпадение возвращает исходную секцию с `fallback: true` вместо повреждённой структуры |
| `POST /website/generateAltText` | Визуальный вызов по списку до 20 URL изображений; возвращает краткий alt-текст (≤125 символов, без префиксов «photo of») |
| `POST /website/generateMetaDescription` | Одно SEO-мета-описание (≤155 символов) по текстовому содержимому страницы — подключено к кнопке Generate в настройках страницы B1Admin |

Промпты для этих эндпоинтов — это файлы markdown в `AskApi/config/instructions/`, включая каталог элементов, из которого генерирует модель. Два проектных решения сохраняют каталог честным: клиент передаёт `availableElementTypes` в каждом запросе (промпт может использовать только типы из этого списка — сервер никогда не зашивает полный набор), а инструмент MCP API `describe_page_builder` содержит то же руководство для ИИ-агентов, работающих через [MCP](../api/mcp). Модели — это Anthropic Claude через OpenRouter: 3.5 Haiku для содержимого секций (задержка), 3.5 Sonnet для схем, планов сайтов и визуальных задач, с запасным вариантом OpenAI, если ключ OpenRouter не настроен.

## Диалоговые формы

Формы (модуль membership) получили диалоговый режим, ориентированный на страницы в стиле connect-card. Четыре колонки таблицы `forms` управляют им: `displayMode` (`standard` | `conversational`), `autoCreatePerson`, `followUpSubject`, `followUpBody`.

- **Отрисовка** — `FormSubmissionEdit` из apphelper переключается на компонент `ConversationalForm` (по одному вопросу за раз), когда `displayMode` равен `conversational`; страница формы B1App передаёт режим дальше. Полезная нагрузка отправки в обоих случаях одинакова.
- **Автосоздание человека** — при отправке с установленным `autoCreatePerson` `ConversationalFormHelper.findOrCreatePerson` устраняет дубликаты по email (без учёта регистра), а иначе создаёт домохозяйство и человека со `membershipStatus: "Guest"` и связывает отправку с этим человеком.
- **Письмо с продолжением** — когда заданы тема и текст, отправитель получает письмо по шаблону (с токенами `{firstName}` / `{churchName}`) через существующий транзакционный путь (`TransactionalEmailHelper`), но никогда через дайджест уведомлений. Оба побочных эффекта не фатальны: сбой никогда не теряет отправку.

Четыре поля сегодня задаются через API; редактор форм B1Admin их пока не показывает.

## Кеш публичного сайта

Путь публичной отрисовки B1App кеширует выборки, помеченные тегом церкви (`next: { revalidate: 300, tags: [sdSlug] }` в продакшене; `0` в разработке), поэтому живая страница может оставаться устаревшей до пяти минут после записи в ContentApi. `POST /api/revalidate/{sdSlug}` в B1App вызывает `revalidateTag(sdSlug)` и является единственным способом сбросить этот кеш раньше.

Этот кеш сбрасывают два источника:

1. **B1Admin** — `clearSiteCache()` в `B1Admin/src/site/siteCache.ts` отправляет POST после сохранений в редакторе. Он предпочитает поддомен активного сайта (вторичный сайт должен сбросить *свой* тег, а не тег основной церкви).
2. **Api** — мутации контента, которые не проходят через B1Admin (ключи API, MCP, ИИ), вызывают `SiteCacheHelper.bump(churchId)` из контроллеров контента. Помощник определяет поддомен церкви через `SubDomainHelper` и отправляет POST на `{b1AppRoot}/api/revalidate/{sd}`. Ошибки проглатываются, чтобы недоступный B1App не мог провалить сохранение.

Контроллеры, которые вызывают сброс: страницы (сохранение, удаление, дублирование, публикация, отмена изменений, снятие с публикации, временный ИИ), секции, элементы, блоки, ссылки, глобальные стили, посты и редиректы. Базовый `b1AppRoot` в разработке — `http://{subdomain}.localtest.me:3301`; демо и продакшен используют `https://{subdomain}.b1.church`.
