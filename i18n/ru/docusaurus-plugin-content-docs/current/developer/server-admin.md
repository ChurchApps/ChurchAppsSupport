# Администрирование сервера

<div class="article-intro">

Функции администрирования сервера в ChurchApps доступны только пользователям с разрешением **Server.Admin**. Эти инструменты используются для операций платформы, поддержки и устранения неполадок во всех церквях в системе.

</div>

:::warning Доступ ограничен
Функции, описанные на этой странице, требуют разрешения **Server.Admin** и недоступны обычным администраторам церквей. Они предназначены только для операторов платформы и персонала поддержки.
:::

## Доступ к администрированию сервера

Пользователи с разрешением Server.Admin могут получить доступ к панели администратора сервера из B1 Admin:

1. Войдите в [admin.b1.church](https://admin.b1.church)
2. Откройте **Settings**, затем нажмите **Server Admin** в меню Settings. (Вы также можете перейти прямо на `admin.b1.church/admin`.)
3. Панель администратора сервера имеет разделы для Churches, Users, Impersonate User, Background Jobs, Commons, Usage Trends, Translation Lookups, Server Health и Database Migrations

## Олицетворение пользователя

Функция олицетворения позволяет администраторам сервера выполнить вход как другой пользователь в целях поддержки и устранения неполадок. Это полезно при расследовании проблем, сообщаемых пользователями, или помощи церквям в настройке их систем.

### Как олицетворить пользователя

1. Откройте раздел **Impersonate User** панели администратора сервера
2. Введите имя или адрес электронной почты пользователя в поле поиска
3. Нажмите **Search** или нажмите Enter
4. Из результатов поиска нажмите на пользователя, которого вы хотите олицетворить
5. Подтвердите олицетворение в появляющемся диалоге
6. Вы будете выполнены вход как этот пользователь и перенаправлены на его учетную запись

### Важные примечания

- Олицетворение создает новый сеанс с разрешениями целевого пользователя и доступом к церквям
- Ваш исходный сеанс администратора заканчивается, когда вы олицетворяете другого пользователя
- Все действия, предпринятые при олицетворении, записываются в журнал аудита
- Чтобы вернуться на свой аккаунт администратора, выйдите и войдите снова с вашими учетными данными
- Используйте олицетворение только при необходимости в целях поддержки и всегда информируйте пользователей при доступе к их учетным записям для поддержки

### Конечная точка API

Функция олицетворения поддерживается конечной точкой `/users/:userId/impersonate` в API членства. См. [Endpoints членства](/docs/developer/api/endpoints/membership#users) для технических деталей.

### Вопросы безопасности

- Олицетворение требует разрешения Server.Admin - это разрешение должно быть предоставлено скудно и только доверенным операторам платформы
- Все события олицетворения регистрируются с идентификатором администратора и идентификатором целевого пользователя
- Церкви не уведомляются, когда происходит олицетворение, поэтому установите четкие политики относительно того, когда и как эта функция должна использоваться
- Рассмотрите возможность документирования событий олицетворения в вашей системе билетов поддержки в целях отчетности

## Модерация Commons

Commons — это общая очередь модерации для содержимого, отправленного пользователями, в различные продукты — песни WorshipCommons, уроки Lessons.church, шаблоны FreeShow и шаблоны конструктора веб-сайтов B1 — все они проходят через ту же очередь вместо отдельных инструментов проверки для каждого продукта.

### Доступ к Commons

1. Перейдите на вкладку **Commons** в панели администратора сервера.
2. Вы увидите три подвкладки: **Queue**, **Reports** и **Assets**.

Ограниченная роль **music editor** также может видеть вкладку Queue, но ей запрещено одобрять отправки, которые изменяют права или лицензирование песни.

### Очередь

В очереди приведены все ожидающие отправки во всех продуктах, фильтруемые по продукту и типу активов. Каждая строка показывает, является ли отправка новым активом, редактированием его первоначального автора или редактированием третьей стороной, вместе с историей одобрения отправителя и тем, как долго отправка ждет (отмечается, когда она превышает 72 часа).

Нажмите **Review** для открытия ящика с различиями на уровне полей, предпросмотром файлов и встроенным предпросмотром только для чтения элемента. Используйте сочетания клавиш **a**/**r** для одобрения или отклонения, а **j**/**k** для перемещения на следующую или предыдущую отправку без закрытия ящика. Отклонение требует выбора причины (например, качество, дубликат, лицензирование, ccli, ai или off-topic) и примечания.

### Отчеты

На вкладке Отчеты обрабатываются отчеты об авторских правах и политике/качестве, поданные против уже опубликованных активов, разделенные на отдельные очереди авторских прав и политики и другие плюс историю разрешенных. Заявите отчет, чтобы начать его обработку, затем разрешите его с помощью разрешения (поддержано, отклонено или дубликат) и действия (нет, отмена публикации или удаление).

### Активы

Вкладка Активы — это доступный для поиска браузер опубликованного контента с действиями для **Feature** активом (выделяет его на домашней странице продукта), **Unpublish**/**Republish** его, или **Remove** его (с авторским правом или причиной политики).

Для песен в частности, это также место, где песня становится **Sunday-ready** и имеет право отображаться в поиске песен B1 Admin церкви: рецензент открывает актив и отмечает каждый опубликованный ключ как **Listened** один раз прослушав его и подтвердив, что оценка, аккорды и слайды все присутствуют. Песня становится Sunday-ready только после того, как все ключи отмечены.

:::info
Commons модерация только для персонала — отдельные церкви никогда не видят эту очередь. Единственное место, где администратор B1 отдельной церкви касается данных Commons — это раздел "WorshipCommons — free" в [поиске песен](/docs/b1-admin/serving/songs#free-songs-from-worshipcommons), который поверхностно показывает только те песни, которые уже прошли этот процесс проверки.
:::

См. страницу [архитектуры Content Commons](/docs/developer/architecture/commons) для базовой модели данных и жизненного цикла отправки.

## Одобрение электронной почты группы

Церкви не могут отправлять электронную почту, написанную церковью (групповую электронную почту, ответы на формы, рабочие процессы электронной почты и приглашения учетных записей), пока администратор сервера их не одобрит. Это предотвращает отправку спама из общего адреса ChurchApps при регистрации бота.

1. Откройте вкладку **Churches** в панели администратора сервера.
2. Каждая церковь показывает чип **Group Email**: **Approved** (зеленый) или **Not approved** (очерченный).
3. Нажмите чип и подтвердите для одобрения церкви, или отозвите одобрение.

Персонал церкви просит одобрение с помощью кнопки **Request review** в диалоговом окне Send Email в B1 Admin. Запрос отправляется по адресу поддержки и содержит название, идентификатор, дату регистрации, местоположение церкви и того, кто запросил. Церковь может отправить один запрос в неделю. Видеть [Пределы электронной почты, написанной церковью](/docs/developer/architecture/notifications#church-authored-email-limits) для ежедневного лимита и автоматической паузы при отскоках и жалобах.

## Миграции базы данных

Развертывания не изменяют базу данных. Размещенные базы данных принимают подключения только изнутри сети Api, поэтому после выпуска, который добавляет миграцию, администратор сервера применяет ее с вкладки **Database Migrations**. (Самостоятельно размещенные установки Docker по-прежнему запускают миграции автоматически при запуске контейнера Api.)

На вкладке отображается текущая среда и по одной строке для каждого модуля (членство, посещаемость, дающее и так далее) с его статусом, количеством примененных и ожидающих миграций и последней примененной.

- **Run Pending Migrations** применяет каждую ожидающую миграцию, по одному модулю за раз, по порядку. Она останавливается при первом отказе и показывает, что было применено для каждого модуля.
- Модуль, отмеченный **No history**, имеет базу данных, которая предшествует отслеживанию миграции. Он никогда не запускается автоматически, потому что это воспроизведет старые миграции данных через живые таблицы. Нажмите **Check Schema** на этом модуле вместо этого. Api сравнивает таблицы, столбцы и индексы, которые создает каждая миграция, с живой базой данных и отмечает каждую миграцию **Already applied**, **Missing**, **Partly applied** или **Data only**. Никаких изменений не производится при проверке.
- В результатах проверки, **Record as Already Applied** записывает обнаруженные миграции в историю миграции без их запуска. Отсутствующие остаются ожидающими и затем могут быть запущены нормально.
- **Partly applied** миграция блокирует запись. Если миграция безопасна для повторного запуска (сначала прочитайте ее), установите флажок **Re-run**, чтобы она осталась ожидающей и запустилась снова с начала.

Панель администратора сервера и CLI (`yarn migrate:up`) используют один и тот же миграторе Kysely и таблицу `kysely_migration`, поэтому они всегда согласны относительно того, что было применено. Резервные конечные точки — это `GET /membership/serverHealth/migrations`, `POST /membership/serverHealth/migrations/:module/run`, `GET .../:module/detect` и `POST .../:module/baseline`, все только Server.Admin.
