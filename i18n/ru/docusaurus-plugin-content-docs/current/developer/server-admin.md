# Администрирование сервера

<div class="article-intro">

Функции администрирования сервера в ChurchApps доступны только пользователям с разрешением **Server.Admin**. Эти инструменты используются для операций платформы, поддержки и устранения неполадок во всех церквях в системе.

</div>

:::warning Ограничение доступа
Функции, описанные на этой странице, требуют разрешения **Server.Admin** и недоступны обычным администраторам церкви. Они предназначены только для операторов платформы и персонала поддержки.
:::

## Доступ к Server Admin

Пользователи с разрешением Server.Admin могут получить доступ к панели администратора сервера из B1 Admin:

1. Войдите в [admin.b1.church](https://admin.b1.church)
2. Откройте [Jump меню](../b1-admin/introduction.md#getting-around-with-the-jump-menu), разверните **Settings** и нажмите **Server Admin**. (Вы также можете перейти непосредственно на `admin.b1.church/admin`.)
3. Панель Server Admin содержит разделы для Churches, Users, Impersonate User, Background Jobs, Commons, Usage Trends, Translation Lookups, Server Health и Database Migrations

## Импersonations пользователя

Функция импersonation позволяет администраторам сервера входить как другой пользователь для целей поддержки и устранения неполадок. Это полезно при расследовании проблем, о которых сообщают пользователи, или помощи церквям в настройке своих систем.

### Как выполнить импersonation пользователя

1. Откройте раздел **Impersonate User** панели Server Admin
2. Введите имя или адрес электронной почты пользователя в поле поиска
3. Нажмите **Search** или нажмите Enter
4. Из результатов поиска нажмите на пользователя, которого вы хотите импersonify
5. Подтвердите импersonation в появившемся диалоге
6. Вы будете входить как этот пользователь и перенаправлены на его аккаунт

### Важные примечания

- Импersonation создает новую сессию с разрешениями целевого пользователя и доступом к церкви
- Ваша исходная сессия админа заканчивается при импersonify другого пользователя
- Все действия, выполняемые во время импersonation, логируются в audit trail
- Чтобы вернуться на свой админ-аккаунт, выйдите и снова войдите со своими учетными данными
- Используйте импersonation только при необходимости для целей поддержки и всегда информируйте пользователей при доступе к их аккаунтам для поддержки

### API Endpoint

Функция импersonation поддерживается конечной точкой `/users/:userId/impersonate` в API Membership. См. [Membership Endpoints](/docs/developer/api/endpoints/membership#users) для технических деталей.

### Соображения безопасности

- Импersonation требует разрешения Server.Admin — это разрешение должно быть предоставлено только надежным операторам платформы
- Все события импersonation регистрируются с ID admin пользователя и целевой ID пользователя
- Церквям не уведомляются о том, когда происходит импersonation, поэтому установите четкие политики для того, когда и как эта функция должна использоваться
- Рассмотрите возможность документирования событий импersonation в вашей системе тикетов поддержки для подотчетности

## Модерирование Commons

Commons — это общая очередь модерирования для контента, представленного пользователями во всех продуктах — песни WorshipCommons, уроки Lessons.church, шаблоны FreeShow и шаблоны конструктора веб-сайтов B1 — все проходят через ту же очередь вместо отдельных инструментов проверки для каждого продукта.

### Доступ к Commons

1. Перейдите на вкладку **Commons** в панели Server Admin.
2. Вы увидите три подвкладки: **Queue**, **Reports** и **Assets**.

Ограниченная роль **music editor** также может видеть вкладку Queue, но заблокирована от утверждения представлений, которые изменяют права или лицензирование песни.

### Queue

Queue показывает каждое ожидающее представление во всех продуктах, фильтруемое по продукту и типу assets. Каждая строка показывает, является ли представление новым assets, редактированием его оригинального автора или редактированием третьей стороной, а также историю одобрения представителя и как долго представление ждет (отмечено, как только оно проходит 72 часа).

Нажмите **Review**, чтобы открыть drawer с различиями на уровне поля, предпросмотром файла и встроенным просмотром элемента только для чтения. Используйте сочетания клавиш **a**/**r** для утверждения или отклонения и **j**/**k** для переходов к следующему или предыдущему представлению без выхода из drawer. Отклонение требует выбора причины (например, качество, дублирование, лицензирование, ccli, ai или off-topic) и примечания.

### Reports

На вкладке Reports рассматриваются авторские права и жалобы на политику/качество, поданные в отношении уже опубликованных assets, разделенные на отдельные очереди Copyright и Policy & Other плюс историю Resolved. Требуйте отчет, чтобы начать работу с ним, затем разрешите его с разрешением (upheld, dismissed или duplicate) и действием (none, unpublish или remove).

### Assets

На вкладке Assets находится поисковая браузер опубликованного контента с действиями для **Feature** assets (выделяет его на главной странице продукта), **Unpublish**/**Republish** его или **Remove** его (с авторским правом или причиной политики).

Для песен в частности, это также где песня становится **Sunday-ready** и имеет право появляться в поиске песен B1 Admin церкви: рецензент открывает assets и отмечает каждый опубликованный ключ как **Listened**, как только они прослушивают его и подтверждают, что score, chords и slides все присутствуют. Песня становится Sunday-ready только после того, как каждый ключ отмечен.

:::info
Модерирование Commons — только для сотрудников — отдельные церкви никогда не видят эту очередь. Единственное место, где отдельная церковь B1 Admin касается данных Commons — это раздел "WorshipCommons — free" [поиска песен](/docs/b1-admin/serving/songs#free-songs-from-worshipcommons), который только представляет песни, которые уже прошли этот процесс рецензирования.
:::

См. страницу [архитектуры Content Commons](/docs/developer/architecture/commons) для базовой модели данных и жизненного цикла представления.

## Утверждение Group Email

Церкви не могут отправлять письма, написанные церковью (group email, последующие письма от формы, письма workflow и приглашения аккаунта), пока администратор сервера их не одобрит. Это предотвращает использование церквями, зарегистрированными ботом, общего адреса отправки ChurchApps для спама.

1. Откройте вкладку **Churches** в панели Server Admin.
2. Каждая церковь показывает **Group Email** chip: **Approved** (зеленый) или **Not approved** (outlined).
3. Нажмите chip и подтвердите, чтобы одобрить церковь, или отозвать одобрение.

Персонал церкви запрашивает одобрение с кнопкой **Request review** в диалоге Send Email B1Admin. Запрос отправляется на адрес поддержки и указывает имя церкви, ID, дату регистрации, местоположение и того, кто запросил. Церковь может отправить один запрос в неделю. См. [Ограничения на письма, составленные церковью](/docs/developer/architecture/notifications#church-authored-email-limits) для ежедневного пособия и автоматической паузы на отскоки и жалобы.

## Миграции базы данных

Deploy не изменяют базу данных. Размещенные базы данных принимают соединения только изнутри сети Api, поэтому после релиза, который добавляет миграцию, администратор сервера применяет ее на вкладке **Database Migrations**. (Самостоятельно размещенные Docker установки все еще автоматически запускают миграции при запуске контейнера Api.)

На вкладке отображается текущая среда и одна строка на модуль (membership, attendance, giving и т.д.) с его статусом, количество примененных и pending миграций и последняя примененная.

- **Run Pending Migrations** применяет каждую ожидающую миграцию, один модуль за раз, по порядку. Он останавливается при первой ошибке и показывает, что было применено для каждого модуля.
- Модуль, помеченный **No history**, имеет базу данных, которая предшествует отслеживанию миграции. Он никогда не запускается автоматически, потому что это переиграл бы старые миграции данных по live таблицам. Нажмите **Check Schema** на этом модуле вместо. Api сравнивает таблицы, столбцы и индексы, которые каждая миграция создает с live базой данных, и отмечает каждую миграцию **Already applied**, **Missing**, **Partly applied** или **Data only**. Ничего не изменяется посредством проверки.
- В результатах проверки, **Record as Already Applied** записывает обнаруженные миграции в историю миграции без их запуска (после подтверждения). Все до последней миграции **Already applied** записывается, включая **Data only** в этот диапазон; **Missing** остаются pending и затем могут быть запущены нормально с **Run Pending Migrations**.
- Миграция **Partly applied** блокирует запись. Если миграция безопасна для повторного запуска (прочитайте ее сначала), отметьте **Re-run**, чтобы она оставалась pending и запускалась снова с начала.

Панель Server Admin и CLI (`yarn migrate:up`) используют тот же миграtor Kysely и таблицу `kysely_migration`, поэтому они всегда согласны с тем, что было применено. Основные endpoints — это `GET /membership/serverHealth/migrations`, `POST /membership/serverHealth/migrations/:module/run`, `GET .../:module/detect` и `POST .../:module/baseline`, все Server.Admin only.
