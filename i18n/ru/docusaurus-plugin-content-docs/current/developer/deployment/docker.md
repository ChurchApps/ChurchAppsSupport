# Самостоятельное развёртывание через Docker

<div class="article-intro">

Запустите собственный приватный экземпляр B1 Admin, портала участников и сайта B1, API и базы данных MySQL на любой машине с Docker — домашнем сервере, небольшом VPS или локальном сервере. Одна команда устанавливает всё, одна команда обновляет, и каждое обновление сначала делает резервную копию. Если вы не хотите управлять сервером вообще, см. [Самостоятельное развёртывание на Railway](./railway-template) — управляемая альтернатива.

</div>

## Быстрый старт

<div class="prereqs">
<h4>Что понадобится</h4>

- Машина под Linux (или macOS / Windows с WSL или Git Bash — помощник `b1` представляет собой bash-скрипт) с [Docker Engine](https://docs.docker.com/engine/install/) и Compose v2 (входит в Docker Desktop)
- Около 2 ГБ оперативной памяти и 5 ГБ диска
- Для публичного сайта: доменное имя, направленное на машину, и доступные порты 80 и 443

</div>

```bash
curl -fsSL https://raw.githubusercontent.com/ChurchApps/B1Admin/main/deploy/install.sh | bash -s -- --domain church.example.org
```

Если не указывать `--domain`, установка будет работать на `http://localhost`. Установщик создаёт папку `b1church`, записывает `.env` со свежесгенерированными секретами, загружает готовые образы из GitHub Container Registry и ждёт, пока API не сообщит о нормальном состоянии. Ничего не собирается на вашей машине, поэтому первый запуск занимает минуту-две.

По завершении:

1. Откройте **https://church.example.org/admin** (или http://localhost/admin) и нажмите **Register**. Первая учётная запись автоматически становится администратором сервера.
2. Следуйте подсказкам в приложении, чтобы создать первую церковь. Её сайт и портал участников станут доступны по адресу **https://church.example.org/** сразу после создания.

Всё работает за одним доменом:

| Путь | Сервис |
|------|--------|
| `/` | B1App — сайт церкви и портал участников |
| `/admin` | B1Admin — панель сотрудников |
| `/api` | API, загружаемые файлы и вебсокет обновлений в реальном времени |

HTTPS настраивается автоматически: встроенный прокси [Caddy](https://caddyserver.com/) получает и продлевает сертификат Let's Encrypt для домена из `.env`. Наружу открыты только порты 80 и 443; база данных доступна только изнутри сети Docker.

## Команда `b1`

Установщик оставляет скрипт `deploy/b1` рядом с `docker-compose.yml`. Это единственное, что нужно для повседневной работы:

| Команда | Что делает |
|---------|--------------|
| `./deploy/b1 upgrade` | Загрузить текущий релиз, сделать резервную копию, перезапустить и проверить, что API работает нормально |
| `./deploy/b1 upgrade 2026.10.1` | То же, но с привязкой к конкретному релизу |
| `./deploy/b1 backup` | Сделать снимок базы данных, загруженных файлов и `.env` в `backups/<timestamp>/` |
| `./deploy/b1 restore backups/<timestamp>` | Вернуть снимок (API останавливается на время работы) |
| `./deploy/b1 rollback` | Восстановить самую свежую резервную копию, включая релиз, на котором она сделана |
| `./deploy/b1 status` | Установленная версия и состояние контейнеров |
| `./deploy/b1 logs api` | Следить за журналами сервиса |

Релизы публикуются одним версионным пакетом, поэтому три образа всегда совпадают. `B1_VERSION=stable` в `.env` отслеживает последний релиз; укажите конкретную версию, чтобы зафиксировать её. Примечания к релизам находятся в разделе [релизов B1Admin](https://github.com/ChurchApps/B1Admin/releases).

## Настройка

Все параметры находятся в `.env` рядом с `docker-compose.yml`. Установщик заполняет обязательные:

```bash
B1_VERSION=stable
DOMAIN=church.example.org
SITE_ADDRESS=church.example.org          # что обслуживает Caddy; http://localhost для локальной установки
PUBLIC_URL=https://church.example.org    # как браузеры и письма попадают на сайт
MYSQL_ROOT_PASSWORD=…                    # сгенерирован
JWT_SECRET=…                             # сгенерирован
ENCRYPTION_KEY=…                         # сгенерирован, ровно 32 символа — никогда не меняйте после сохранения учётных данных

# Email — настоятельно рекомендуется; без него участники не смогут сбросить пароль самостоятельно
MAIL_SYSTEM=SMTP
SMTP_HOST=smtp.resend.com
SMTP_USER=resend
SMTP_PASS=re_xxxxxxxxx
SMTP_SECURE=false
SUPPORT_EMAIL=noreply@church.example.org
```

После изменения `.env` примените его командой `docker compose up -d`. Веб-приложения определяют, с каким API работать, по адресу в браузере, поэтому при смене домена достаточно обновить `SITE_ADDRESS` и `PUBLIC_URL` и перезапустить — пересборка не нужна.

:::warning
Храните `.env` в безопасности. `ENCRYPTION_KEY` защищает сохранённые учётные данные платёжных шлюзов и хранилища файлов; резервная копия без него не сможет их расшифровать. `./deploy/b1 backup` по этой причине включает копию ключа.
:::

### Переход на домен позже

Если вы установили систему на `localhost` и позже хотите сделать её публичной: направьте DNS на машину, задайте в `.env` `DOMAIN`, `SITE_ADDRESS` (голый домен) и `PUBLIC_URL` (`https://` + домен), затем выполните `docker compose up -d`. Caddy получит сертификат при первом запросе.

## Email, пожертвования, несколько сайтов и интеграции

Всё это работает точно так же, как на Railway — те же переменные окружения, но заданные в `.env`, а не в панели Railway:

- **[Email / SMTP](./railway-template#1-email-highly-recommended)** — инструкции по провайдерам Resend, Brevo и Gmail
- **[Несколько сайтов](./railway-template#3-multi-site-multiple-churches-on-one-instance)** — неограниченное число церквей на одном экземпляре. `/` обслуживает церковь, чей slug совпадает с `DEFAULT_CHURCH_SLUG` (первая церковь — `church`); направьте дополнительные домены на машину и сопоставьте их в **Settings → Domains** в B1Admin
- **[Онлайн-пожертвования](./railway-template#4-online-giving-stripe--paypal)** — настраиваются для каждой церкви в административном интерфейсе
- **[Дополнительные интеграции](./railway-template#6-optional-feature-integrations)** — `OPENAI_API_KEY`, `YOUTUBE_API_KEY`, `PEXELS_KEY`, `VIMEO_TOKEN`, `API_BIBLE_KEY`, `GOOGLE_RECAPTCHA_SECRET_KEY`
- **[Push-уведомления](#push-notifications)** — `WEB_PUSH_*`; установщик оставляет их пустыми, поэтому push выключен, пока вы их не добавите

Приглашения и другие письма, которые отправляет церковь, на самостоятельно развёрнутом экземпляре включаются автоматически (размещённый сервис ограничивает их ручной проверкой, чтобы защитить репутацию отправителя).

## Push-уведомления {#push-notifications}

Push-уведомления в браузере и мобильной веб-версии остаются выключенными, пока на сервере нет пары ключей VAPID. Установщик её не создаёт. Пока вы её не добавите, страница уведомлений в мобильной веб-версии сообщает, что push для сайта не включён.

1. Сгенерируйте пару ключей. Для этого нужен только Docker:

   ```bash
   docker run --rm node:lts-alpine npx --yes web-push generate-vapid-keys
   ```

2. Добавьте два значения в `.env`. `WEB_PUSH_SUBJECT` необязателен — это контактный адрес, который видят push-сервисы:

   ```bash
   WEB_PUSH_PUBLIC_KEY=…
   WEB_PUSH_PRIVATE_KEY=…
   WEB_PUSH_SUBJECT=mailto:admin@example.org
   ```

3. Примените их:

   ```bash
   docker compose up -d
   ```

4. Для проверки откройте в B1Admin **Server Admin → Server Health**. Оба ключа Web Push должны отображаться как настроенные. После этого участники могут включить уведомления в мобильной веб-версии.

:::warning
Как только участники подключились, не меняйте ключи. Их смена делает недействительными все существующие подписки, и каждому устройству придётся зарегистрироваться заново.
:::

## Данные, резервные копии и хранение файлов

Все данные хранятся в трёх именованных томах Docker:

| Том | Содержимое |
|--------|----------|
| `b1church_mysql-data` | Все схемы базы данных |
| `b1church_api-content` | Загруженные файлы — фото, документы, изображения сайта |
| `b1church_caddy-data` | TLS-сертификаты |

`./deploy/b1 backup` записывает согласованный снимок первых двух томов и `.env` в `backups/<timestamp>/`. Запланируйте его через cron и копируйте папку за пределы машины:

```
0 3 * * * cd /opt/b1church && ./deploy/b1 backup >> backups/backup.log 2>&1
```

Для больших медиатек можно перевести хранение файлов на S3 — задайте `FILE_STORE=S3` и переменные `AWS_*`, описанные в разделе [Хранение файлов](./railway-template#5-file-storage) руководства по Railway. Резервные копии базы данных не включают объекты S3; включите версионирование для этого бакета.

## Обновление

```bash
./deploy/b1 upgrade
```

Порядок действий: загрузка релиза, резервная копия, пересоздание контейнеров, применение ожидающих миграций базы данных при запуске API и ожидание проверки работоспособности API. Если что-то не удалось, команда остановится и предложит выполнить `./deploy/b1 rollback`, который восстанавливает эту резервную копию и предыдущий релиз. Миграции работают только вперёд; откат всегда означает восстановление снимка.

Обновление с beta-файла compose (того, который собирал образы из исходников) работает так же, как только у вас есть `.env`: там по умолчанию было `MYSQL_ROOT_PASSWORD=churchapps`, поэтому укажите это значение в `.env` вместе с `PUBLIC_URL` и `SITE_ADDRESS`, замените `docker-compose.yml` и `deploy/` актуальными файлами и выполните `./deploy/b1 upgrade`.

## Сборка из исходного кода

Разработчики могут собирать образы локально, а не загружать их:

```bash
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

`API_CONTEXT` и `B1APP_CONTEXT` в `.env` указывают сборкам на локальные копии (например, `../Api`) или на git-ref.

## Устранение неполадок

| Симптом | Вероятная причина | Решение |
|---------|--------------|---------|
| Контейнер `api` постоянно перезапускается | Сбой миграции или неверный пароль базы данных | `./deploy/b1 logs api` — миграция покажет, какой модуль не сработал |
| `api` пишет "ENCRYPTION_KEY must be exactly 32 characters" | Ключ в `.env` отредактирован вручную или обрезан | Восстановите исходный 32-символьный ключ (генерируйте новый, только если учётные данные ещё не сохранены) |
| Браузер показывает предупреждение о сертификате | DNS ещё не направлен сюда или порты 80/443 заблокированы | Исправьте DNS / брандмауэр; Caddy повторит попытку сам |
| `/` показывает панель вместо сайта церкви | Церкви ещё нет или `DEFAULT_CHURCH_SLUG` не совпадает | Создайте церковь или задайте slug в **Settings → Church** |
| «Check your email», но письмо не приходит | `MAIL_SYSTEM=SMTP` с неверными учётными данными | Исправьте учётные данные или уберите `MAIL_SYSTEM`, чтобы отключить email |
| Мобильная веб-версия пишет, что push-уведомления не включены | На сервере нет ключей VAPID | Добавьте их, как описано в [Push-уведомлениях](#push-notifications) |
| Чат / живые функции молчат | Вебсокет блокируется другим прокси перед системой | Сокет работает по `/api/` через тот же порт; разрешите заголовки `Upgrade` |
| `install` отказывается: "database volume already exists" | Остатки от предыдущей установки | `docker compose down -v`, чтобы очистить, или напишите `.env` и используйте `upgrade` |

Всё ещё не работает? Откройте задачу на [github.com/ChurchApps/ChurchAppsSupport/issues](https://github.com/ChurchApps/ChurchAppsSupport/issues) и приложите вывод `./deploy/b1 logs`.
