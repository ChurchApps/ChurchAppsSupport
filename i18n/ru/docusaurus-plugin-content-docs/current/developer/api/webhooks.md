# Вебхуки

<div class="article-intro">

Вебхуки позволяют церкви отправлять уведомления в реальном времени сторонним инструментам — платформам автоматизации (Zapier, Make, n8n), CRM, бухгалтерским системам или чему угодно, что принимает HTTP POST. Когда человек, группа или домохозяйство меняются в B1, B1 отправляет подписанную JSON-нагрузку на каждый URL, подписанный на это событие.

</div>

<div class="prereqs">
<h4>Перед началом</h4>

- Администратор церкви с правом **Редактировать настройки церкви** регистрирует вебхуки и управляет ими
- Ваша принимающая конечная точка должна быть доступна по **HTTPS** на публичном адресе
- Имейте способ безопасно хранить секрет подписи — он показывается только один раз

</div>

## Обзор

Вебхуки работают только **исходящим** образом: B1 вызывает вашу конечную точку, а не наоборот. Каждый вебхук — это подписка отдельной церкви, состоящая из URL назначения, секрета подписи и списка событий, на которые оформлена подписка.

Доставка использует **надёжный outbox**: когда происходит событие с подпиской, B1 записывает строку доставки, а фоновый воркер отправляет POST-запрос в течение примерно минуты. Неудачные доставки повторяются с экспоненциальной задержкой. Ничего не теряется, если доставка задерживается или ваша конечная точка кратковременно недоступна.

## Регистрация вебхука

### В B1Admin

Перейдите в **Настройки → Разработчикам → Вебхуки → Новый вебхук**. Введите имя, URL полезной нагрузки и выберите события, на которые нужно подписаться. При сохранении **секрет подписи показывается один раз** — скопируйте его немедленно и сохраните вместе с вашей интеграцией. Больше он не показывается (вы можете позже его сменить, но получить исходный секрет заново нельзя).

### Через API

Все конечные точки находятся под базовым путём модуля Membership `/membership/webhooks` и требуют либо JWT администратора церкви с правом `Settings / Edit`, **либо [ключ API](./api-keys), выпущенный с областью `settings:write`**. Одни и те же маршруты принимают оба варианта. Именно это позволяет Zapier и Make регистрировать вебхуки от имени церкви при включении Zap или сценария.

```http
POST /membership/webhooks
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "name": "Zapier — новые участники",
  "url": "https://hooks.zapier.com/hooks/catch/123/abc",
  "events": ["person.created", "person.updated", "group.member.added"]
}
```

Ответ на создание — и **только** ответ на создание — включает `secret`:

```json
{
  "id": "a1b2c3d4e5f",
  "name": "Zapier — новые участники",
  "url": "https://hooks.zapier.com/hooks/catch/123/abc",
  "events": ["person.created", "person.updated", "group.member.added"],
  "active": true,
  "secret": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822c"
}
```

| Метод и путь | Назначение |
|---|---|
| `GET /membership/webhooks` | Список вебхуков церкви (секрет не включён) |
| `GET /membership/webhooks/events` | Каталог допустимых названий событий |
| `GET /membership/webhooks/:id` | Загрузить один вебхук |
| `POST /membership/webhooks` | Создать (без `id`) или обновить (с `id`) |
| `POST /membership/webhooks/:id/regenerate-secret` | Сменить секрет подписи; возвращает новое значение один раз |
| `DELETE /membership/webhooks/:id` | Удалить вебхук |
| `GET /membership/webhooks/:id/deliveries` | Последние попытки доставки для вебхука |
| `GET /membership/webhooks/deliveries/:deliveryId` | Полная полезная нагрузка и ответ для одной доставки |
| `POST /membership/webhooks/deliveries/:deliveryId/redeliver` | Повторно поставить доставку в очередь |

## Каталог событий

Названия событий следуют шаблону `{сущность}.{действие}`. Получите актуальный список из `GET /membership/webhooks/events`.

| Событие | Срабатывает, когда |
|---|---|
| `person.created` | Добавлен человек |
| `person.updated` | Изменена запись о человеке |
| `person.destroyed` | Человек удалён |
| `household.created` | Добавлено домохозяйство |
| `household.updated` | Домохозяйство изменено |
| `household.destroyed` | Домохозяйство удалено |
| `group.created` | Добавлена группа |
| `group.updated` | Группа изменена |
| `group.destroyed` | Группа удалена |
| `group.member.added` | Человек добавлен в группу |
| `group.member.removed` | Человек удалён из группы |
| `donation.created` | Записано пожертвование — ручной ввод, онлайн или переход из состояния «в ожидании» в «завершено» |
| `donation.updated` | Запись о пожертвовании отредактирована |
| `attendance.recorded` | Зафиксировано посещение (ручной ввод или регистрация) |
| `session.created` | Создана новая сессия посещаемости (вручную или автоматически при первой регистрации) |
| `form.submission.created` | Отправлена форма |
| `event.created` | Добавлено событие в календаре |
| `event.updated` | Событие в календаре отредактировано |
| `event.destroyed` | Событие в календаре удалено |

## Формат полезной нагрузки

Каждая доставка — это HTTP `POST` с телом JSON и следующими заголовками:

| Заголовок | Описание |
|---|---|
| `Content-Type` | Всегда `application/json` |
| `X-B1-Event` | Название события, например `person.created` |
| `X-B1-Delivery-Id` | Уникальный id этой попытки доставки — используйте для дедупликации |
| `X-B1-Signature` | Подпись HMAC-SHA256 сырого тела запроса (см. ниже) |
| `X-B1-Timestamp` | Unix-время в секундах, когда запрос был отправлен |
| `User-Agent` | `B1-Webhooks/1.0` |

Тело оборачивает изменённый ресурс в небольшой конверт:

```json
{
  "event": "person.created",
  "churchId": "AbC123XyZ90",
  "occurredAt": "2026-05-17T14:32:08.114Z",
  "data": {
    "id": "Pq7Rs2Tu4Vw",
    "churchId": "AbC123XyZ90",
    "name": { "display": "Jordan Rivera", "first": "Jordan", "last": "Rivera" },
    "contactInfo": { "email": "jordan@example.com" }
  }
}
```

Для событий `*.destroyed` `data` содержит только `id` и `churchId` удалённой записи.

События, чьи полезные нагрузки ссылаются на другие записи по id, также несут читаемые человеком имена, разрешённые во время доставки: `personName` и `groupName` для событий членства в группе, `personName` для событий посещаемости, пожертвований и членства в списках, `groupName` для `session.created`, и `formName` (а также `personName`, когда отправка формы связана с человеком) для `form.submission.created`.

## Типы коннекторов

Формат доставки по умолчанию — это описанный выше JSON-конверт — `connectorType: "standard"`. Для [Slack и Discord](/docs/b1-admin/integrations/slack-discord) тот же движок вебхуков вместо этого публикует сообщение в формате чата, которое эти сервисы принимают напрямую:

| `connectorType` | Отправляемое тело | Когда использовать |
|---|---|---|
| `"standard"` (по умолчанию) | Подписанный конверт `{event, churchId, occurredAt, data}` | Вы пишете собственную интеграцию или указываете на Zapier / Make / собственный сервер |
| `"slack"` | `{ "text": "💝 New donation: $50.00" }` | Вы отправляете напрямую на URL входящего вебхука Slack |
| `"discord"` | `{ "content": "💝 New donation: $50.00" }` | Вы отправляете напрямую на URL вебхука канала Discord |

Тип коннектора задаётся в выпадающем списке **Connector Type** в редакторе вебхука или через `connectorType` в теле `POST /membership/webhooks`. Подписанный заголовок `X-B1-Signature` по-прежнему отправляется для доставок в Slack/Discord (они безобидно его игнорируют), поэтому переключение вебхука обратно на `standard` позже не требует повторной подписи.

## Тестовые доставки

У каждого редактора вебхука есть кнопка **Send Test Event** — соответствующий вызов API — `POST /membership/webhooks/:id/test`. Тестовый маршрут строит синтетическую полезную нагрузку для первого подписанного события, отправляет её синхронно через реальный путь подписанной доставки (и через `formatForConnector` для Slack/Discord) и возвращает получившуюся строку доставки, включая `responseStatus` и `responseBody`. Используйте её, чтобы подтвердить связность и обработку подписи, прежде чем включать интеграцию по-настоящему.

## Проверка подписей

Всегда проверяйте `X-B1-Signature`, прежде чем доверять полезной нагрузке. Подпись — это `sha256=`, за которым следует шестнадцатеричный HMAC-SHA256 **сырого тела запроса**, подписанный вашим секретом подписи. Вычисляйте её по байтам, которые вы получили — не сериализуйте разобранный JSON заново.

**Node.js**

```js
const crypto = require("crypto");

function isValid(rawBody, signatureHeader, secret) {
  const expected = "sha256=" + crypto.createHmac("sha256", secret).update(rawBody, "utf8").digest("hex");
  const a = Buffer.from(expected);
  const b = Buffer.from(signatureHeader || "");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

**Python**

```python
import hashlib, hmac

def is_valid(raw_body: bytes, signature_header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature_header or "")
```

**PHP**

```php
function isValid(string $rawBody, string $signatureHeader, string $secret): bool {
    $expected = "sha256=" . hash_hmac("sha256", $rawBody, $secret);
    return hash_equals($expected, $signatureHeader ?? "");
}
```

Отклоняйте любой запрос, чья подпись не совпадает. При желании также отклоняйте запросы, у которых `X-B1-Timestamp` старше нескольких минут, чтобы ограничить окно повторных атак.

## Поддержка SDK

Для Node.js пакет `@churchapps/integration-sdk` поставляется с типизированным верификатором и middleware для Express, который берёт на себя захват сырого тела, проверку подписи и разбор конверта за вас:

```ts
import express from "express";
import { b1WebhookMiddleware } from "@churchapps/integration-sdk";

const app = express();
// Захватить сырое тело до разбора JSON — необходимо, чтобы подпись по-прежнему проверялась.
app.use(express.json({ verify: (req, _res, buf) => { (req as any).rawBody = buf; } }));

app.post("/webhooks/b1", b1WebhookMiddleware({ secret: process.env.B1_WEBHOOK_SECRET! }), (req, res) => {
  const env = req.b1Webhook!;
  switch (env.event) {
    case "donation.created": console.log("new gift", env.data.amount); break;
  }
  res.sendStatus(200);
});
```

SDK также предоставляет `WebhookVerifier.verify(secret, rawBody, signatureHeader)` для сред без Express (serverless-функции, Fastify и т. д.). Смотрите пакет на npm.

## Доставка и повторы

Ваша конечная точка должна отвечать статусом `2xx` как можно быстрее — в идеале сразу после постановки работы в очередь, а не после её обработки. Любой ответ, отличный от `2xx`, сбой соединения или ответ медленнее **10 секунд** считаются неудачной доставкой.

Неудачные доставки повторяются с экспоненциальной задержкой — **16 попыток примерно за 5 дней**. Интервал растёт с 1 минуты через часы вплоть до промежутков в 3 дня для последних попыток. После 16-й неудачной попытки доставка помечается как `exhausted` и отменяется.

Доставка происходит **минимум один раз**: доставка может прийти более одного раза (например, если ваша конечная точка отвечает успешно, но ответ теряется). Используйте заголовок `X-B1-Delivery-Id` для дедупликации — обрабатывайте каждый id только один раз, а повторы считайте отсутствием действия.

### Автоотключение

Если вебхук выдаёт **три подряд исчерпанные доставки**, B1 автоматически его отключает. Исправьте вашу конечную точку, затем снова включите вебхук в B1Admin (или через `POST /membership/webhooks` с `"active": true`).

## Просмотр и повторная доставка

Редактор вебхука в B1Admin показывает таблицу **Recent Deliveries** — событие, статус, число попыток, код ответа и время. Выбор строки открывает полную отправленную полезную нагрузку и полученный ответ.

Используйте **Redeliver**, чтобы повторно поставить в очередь любую прошлую доставку с её исходной полезной нагрузкой — полезно после исправления бага в вашей конечной точке или для восстановления событий, которые ваша конечная точка пропустила, пока была недоступна.

## Требования к URL

Поскольку URL вебхуков задаются церковью, B1 применяет защиту от подделки серверных запросов (SSRF). URL вебхука отклоняется — при регистрации и повторно проверяется перед каждой доставкой — если он:

- не использует **`https`**
- указывает на `localhost`, имя хоста `.local` / `.internal`, или
- разрешается в **приватный, loopback, link-local или облачный метаданный** IP-адрес

Ваша конечная точка должна быть публично доступным HTTPS-сервисом.
