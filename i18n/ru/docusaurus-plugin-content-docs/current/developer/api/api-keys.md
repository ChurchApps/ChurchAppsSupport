# Ключи API

<div class="article-intro">

Ключи API (персональные токены доступа) — самый простой способ аутентификации в API B1 из серверного скрипта, стороннего коннектора (Zapier, Make, Google Sheets) или в любом случае, где полный поток OAuth избыточен. Ключ привязан к конкретному человеку в конкретной церкви и наследует его права, при необходимости ограниченные набором областей доступа (scopes).

</div>

<div class="prereqs">
<h4>Прежде чем начать</h4>

- Ключи создаёт и управляет ими администратор церкви с правом **Edit Settings** (Редактирование настроек)
- Полный ключ показывается **один раз** при создании — сразу сохраните его в надёжном месте
- Все API-запросы должны использовать **HTTPS**

</div>

## Формат ключа

Ключ API B1 выглядит так:

```
cak_<prefix>.<secret>
```

- `cak_` — фиксированный идентификатор (префикс ключа API, по которому его распознаёт уровень аутентификации)
- `<prefix>` — 8-символьный публичный сегмент для поиска
- `<secret>` — 48-символьный секрет; на сервере хранится только его хеш SHA-256

Полный ключ передаётся серверу в стандартном заголовке Bearer:

```http
Authorization: Bearer cak_a1b2c3d4.f0e1d2c3b4a5968778695a4b3c2d1e0f1a2b3c4d5e6f7
```

Уровень аутентификации API направляет любой токен, начинающийся с `cak_`, в путь для ключей API, хеширует секрет, находит ключ по префиксу и определяет текущие права человека, которому принадлежит ключ. Поэтому отзыв права в B1Admin вступает в силу уже при следующем запросе, и ключ никогда не расходится с ролью.

## Создание ключа (B1Admin)

1. Войдите в B1Admin под пользователем с правом **Edit Settings**.
2. Откройте **Settings → Developer → API Keys** (Настройки → Разработчик → Ключи API).
3. Нажмите **New API Key** (Новый ключ API), дайте ему узнаваемое имя (например, «Zapier — синхронизация пожертвований»), выберите области, которые должен иметь ключ, и нажмите **Save**.
4. Полный ключ `cak_…` показывается **один раз** в диалоге. Скопируйте его в конфигурацию интеграции до закрытия — получить его позже невозможно. Вы всегда можете создать новый ключ.

## Области доступа {#scopes}

Область доступа **ограничивает** то, что может делать ключ: она никогда не может дать право, которого нет у лежащего в основе человека. Пустой набор областей означает, что ключ получает полный набор прав человека.

| Область | Разрешает |
|---|---|
| `people:read` / `people:write` | Просмотр / редактирование людей, домохозяйств, участников групп |
| `groups:read` / `groups:write` | Просмотр / редактирование групп и их состава |
| `donations:read` / `donations:write` | Просмотр / запись пожертвований |
| `attendance:read` / `attendance:write` | Просмотр / запись посещаемости, сессий, отметок прихода |
| `forms:write` | Управление формами (чтение подразумевается записью) |
| `content:read` / `content:write` | Просмотр / редактирование контента сайта, регистраций, трансляций |
| `messaging:read` / `messaging:write` | Чтение сообщений; запись также разрешает отправку SMS |
| `roles:read` / `roles:write` | Просмотр / редактирование определений ролей |
| `settings:read` / `settings:write` | Просмотр / редактирование настроек церкви (**обязательно** для программной регистрации вебхуков) |
| `workflows:read` / `workflows:write` | Просмотр рабочих процессов и задач / запуск и редактирование рабочих процессов. Запуск рабочего процесса может отправлять email и SMS, вызывать вебхуки и менять состав групп |
| `offline_access` | Разрешает долгоживущие refresh-токены (только для потоков OAuth — на ключи API не влияет) |

Области `write` неявно включают соответствующую `read`. Права администратора сервера и домена намеренно не выведены в виде областей: ограниченные учётные данные никогда не смогут получить права администрирования сайта.

:::tip
Если вы будете использовать ключ для регистрации вебхуков (например, для интеграции Zapier или Make), ключу нужна область `settings:write`. Ключ только с `people:read` молча получает 403 на `POST /membership/webhooks`.
:::

## Использование ключа

Так же, как любой Bearer-токен: каждая аутентифицированная конечная точка принимает ключи API точно так же, как JWT:

```bash
curl https://api.churchapps.org/membership/people \
  -H "Authorization: Bearer cak_a1b2c3d4.f0e1d2c3b4a5968778695a4b3c2d1e0f1a2b3c4d5e6f7"
```

Запрос, у ключа которого недостаточно областей, возвращает **403 Forbidden** с той же структурой, что и любая ошибка отказа в доступе.

## Управление ключами через API

Все конечные точки находятся по пути `/membership/apiKeys` модуля Membership и требуют JWT (а не ключ API) от администратора церкви с правом **Edit Settings**.

| Метод и путь | Назначение |
|---|---|
| `GET /membership/apiKeys` | Список ключей церкви (без секрета — только `id`, `name`, `prefix`, `scopes`, `lastUsedAt`, `expiresAt`, `createdAt`) |
| `GET /membership/apiKeys/scopes` | Список всех доступных имён областей — для интерфейса создания ключа |
| `POST /membership/apiKeys` | Создать новый ключ. Тело: `{ "name": "...", "scopes": ["people:read"] }`. Ответ содержит исходный ключ `cak_…` **один раз**. |
| `DELETE /membership/apiKeys/:id` | Отозвать ключ — вступает в силу при следующем запросе |

Отозванный ключ перестаёт работать сразу — льготного периода нет.

## Рекомендации

- **Один ключ на интеграцию.** Если что-то скомпрометировано, вы отзываете один ключ, не ломая остальные.
- **Выпускайте самые узкие области, которые подходят.** Экспорту в Google Sheets нужен только `people:read`, а не `settings:write`.
- **Привязывайте ключ к сервисной учётной записи, а не к реальному сотруднику.** Если сотрудник уйдёт, его доступ к B1 прекратится — и вместе с ним все ключи, выпущенные от его имени.
- **Храните ключи в менеджере секретов** (переменные окружения вашего хостинг-провайдера, AWS Secrets Manager и т. п.), но никогда не в системе контроля версий.
- **Меняйте ключи** при подозрении на утечку: создайте новый ключ, обновите интеграцию, затем удалите старый.

## Чем это отличается от OAuth

Ключи API подходят, когда **ваша церковь — единственный пользователь интеграции**. Для коннектора, которому нужен доступ к многим церквям с явного согласия каждой, — например, SaaS-приложение, используемое сообществом B1, — используйте вместо этого [OAuth и подключённые приложения](./connected-apps).

| | Ключ API | OAuth |
|---|---|---|
| Кто устанавливает | Один администратор церкви | Каждый администратор церкви авторизует приложение |
| Заголовок авторизации | `Authorization: Bearer cak_…` | `Authorization: Bearer <jwt>` |
| Срок действия токена | До отзыва | Доступ ≈ 7 дней, обновление ≈ 90 дней |
| Лучше всего для | Внутренние скрипты, коннекторы Zapier/Make/Sheets | Многопользовательские сторонние приложения |
