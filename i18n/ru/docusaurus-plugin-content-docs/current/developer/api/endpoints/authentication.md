# Аутентификация и разрешения

<div class="article-intro">

API ChurchApps использует аутентификацию на основе JWT. Пользователи входят в систему и получают токен, который содержит их идентификатор, принадлежность к церкви и разрешения. На этой странице описаны процесс аутентификации, модель разрешений и поддержка OAuth.

</div>

## Процесс входа

### Стандартный вход

```
POST /membership/users/login
```

**Авторизация:** Публичный

Принимает один из трёх типов учётных данных:

| Поле | Описание |
|-------|-------------|
| `email` + `password` | Стандартный вход по email и паролю |
| `jwt` | Повторная аутентификация с существующим JWT |
| `authGuid` | Одноразовая ссылка для аутентификации (используется в письмах с приветствием и сбросом пароля) |

**Ответ:**

```json
{
  "user": {
    "id": "abc-123",
    "firstName": "Jane",
    "lastName": "Doe",
    "email": "jane@example.com"
  },
  "churches": [
    {
      "church": { "id": "church-1", "name": "First Church", "subDomain": "firstchurch" },
      "person": { "id": "person-1", "membershipStatus": "Member" },
      "groups": [{ "id": "group-1", "name": "Choir", "leader": false }],
      "apis": [
        {
          "keyName": "MembershipApi",
          "permissions": [
            { "contentType": "People", "action": "View" },
            { "contentType": "People", "action": "Edit" }
          ]
        }
      ]
    }
  ],
  "token": "<jwt-token>"
}
```

Поле `token` является JWT, который следует отправлять в заголовке `Authorization: Bearer <token>` при последующих запросах.

### Содержимое токена

JWT содержит:
- `id` — ID пользователя
- `churchId` — текущая выбранная церковь
- `personId` — запись о человеке для выбранной церкви
- Массивы разрешений для каждого API

### Выбор церкви

Пользователи могут состоять в нескольких церквях. Ответ на вход содержит все церкви с их разрешениями. Чтобы переключиться на другую церковь, клиент формирует новый JWT, привязанный к другой церкви из данных ответа на вход.

## Регистрация пользователей

### Регистрация нового пользователя

```
POST /membership/users/register
```

**Авторизация:** Публичный

```json
{
  "email": "jane@example.com",
  "firstName": "Jane",
  "lastName": "Doe",
  "appName": "B1 Admin",
  "appUrl": "https://app.b1.church"
}
```

Создаёт пользователя с временным паролем и отправляет письмо с приветствием и ссылкой для аутентификации. Первый пользователь, зарегистрированный на новом экземпляре, автоматически получает доступ администратора сервера.

Принимаются два необязательных поля-ловушки для ботов: `website` (скрытое поле-приманка, которое реальные пользователи оставляют пустым) и `fillMs` (сколько миллисекунд форма была открыта). Если поле `website` заполнено или `fillMs` меньше 2000, учётная запись не создаётся, но эндпоинт всё равно возвращает обычный ответ `200`, чтобы боты не могли понять, что их отклонили. Клиенты, которые не передают оба поля, регистрируются как обычно.

### Регистрация новой церкви

```
POST /membership/churches/add
```

**Авторизация:** JWT

После регистрации пользователя вызовите этот эндпоинт, чтобы создать церковь и связать с ней пользователя.

## Управление паролями

| Метод | Путь | Авторизация | Описание |
|--------|------|------|-------------|
| POST | `/membership/users/forgot` | Публичный | Отправить письмо для сброса пароля. Тело: `{ "userEmail": "...", "appName": "...", "appUrl": "..." }` |
| POST | `/membership/users/setPasswordGuid` | Публичный | Установить новый пароль с помощью GUID авторизации из письма для сброса. Тело: `{ "authGuid": "...", "newPassword": "..." }` |
| POST | `/membership/users/updatePassword` | JWT | Сменить пароль текущего пользователя. Тело: `{ "newPassword": "..." }` |

## Модель разрешений

Разрешения организованы по модулям и назначаются пользователям через роли. Каждое разрешение имеет **тип содержимого** и **действие**.

### Справочник разрешений

| Раздел в интерфейсе | Тип содержимого | Действие | Описание |
|----------------|--------------|--------|-------------|
| **Attendance** | Attendance | Checkin | Регистрация участников на богослужениях |
| | Attendance | Edit | Редактирование записей посещаемости |

| | Attendance | View | Просмотр записей посещаемости |
| | Attendance | View Summary | Просмотр сводок и отчётов о посещаемости |
| **Donations** | Donations | Edit | Создание и редактирование записей о пожертвованиях |
| | Settings | Edit | Редактирование настроек приёма пожертвований и платежей |
| | Donations | View Summary | Просмотр сводных отчётов о пожертвованиях |
| | Donations | View | Просмотр отдельных записей о пожертвованиях |
| **People and Groups** | Forms | Admin | Полное администрирование форм |
| | Forms | Edit | Редактирование определений форм |

### Как проверяются разрешения

В контроллерах разрешения проверяются с помощью метода `au.checkAccess()`:

```typescript
// Требуется конкретное разрешение
if (!au.checkAccess(Permissions.people.edit)) return this.json({}, 401);

// Или внутри actionWrapper — система CRUD проверяет автоматически
crudSettings: {
  permissions: {
    view: Permissions.people.view,
    edit: Permissions.people.edit
  }
}
```

### Администратор сервера

Разрешение `Server.Admin` предоставляет полный доступ ко всем церквям. Оно назначается первому зарегистрированному пользователю и может быть выдано другим через роль администратора сервера.

## OAuth 2.0

API поддерживает OAuth 2.0 для сторонних интеграций. Доступны два типа грантов.

### Поток с кодом авторизации

1. **Авторизация:** `POST /membership/oauth/authorize` (требуется JWT)
   - Тело: `{ "client_id": "...", "redirect_uri": "...", "response_type": "code", "scope": "...", "state": "...", "code_challenge": "...", "code_challenge_method": "S256" }`
   - `code_challenge` / `code_challenge_method` (PKCE, только `S256`) обязательны для публичных клиентов без секрета
   - Возвращает: `{ "code": "...", "state": "..." }`

2. **Обмен кода на токен:** `POST /membership/oauth/token` (Публичный)
   - Тело: `{ "grant_type": "authorization_code", "code": "...", "client_id": "...", "client_secret": "...", "redirect_uri": "...", "code_verifier": "..." }`
   - Передавайте `code_verifier`, если на шаге авторизации использовался `code_challenge`; публичные клиенты не передают `client_secret`. Принимаются тела в формате JSON или form-encoded
   - Возвращает: `{ "access_token": "...", "token_type": "Bearer", "expires_in": 43200, "refresh_token": "...", "scope": "..." }`

3. **Обновление токена:** `POST /membership/oauth/token` (Публичный)
   - Тело: `{ "grant_type": "refresh_token", "refresh_token": "...", "client_id": "...", "client_secret": "..." }`

Срок действия токенов доступа составляет **12 часов**.

### Поток с кодом устройства (RFC 8628)

Для устройств без браузера (ТВ-приложения, киоски):

1. **Запрос кода устройства:** `POST /membership/oauth/device/authorize` (Публичный)
   - Тело: `{ "client_id": "...", "scope": "..." }`
   - Возвращает: `{ "device_code": "...", "user_code": "ABCD-1234", "verification_uri": "https://app.b1.church/device", "expires_in": 900, "interval": 5 }`

2. **Пользователь вводит код** по адресу проверки и подтверждает или отклоняет запрос

3. **Опрос для получения токена:** `POST /membership/oauth/token` (Публичный)
   - Тело: `{ "grant_type": "urn:ietf:params:oauth:grant-type:device_code", "device_code": "...", "client_id": "..." }`
   - Возвращает `authorization_pending`, пока запрос не подтверждён, после чего возвращает токен доступа

### Управление клиентами OAuth

| Метод | Путь | Авторизация | Разрешение | Описание |
|--------|------|------|------------|-------------|
| GET | `/membership/oauth/clients` | JWT | Server.Admin | Получить всех клиентов OAuth |
| GET | `/membership/oauth/clients/:id` | JWT | Server.Admin | Получить клиента по ID |
| GET | `/membership/oauth/clients/clientId/:clientId` | JWT | — | Получить клиента по client ID (секрет скрыт) |
| POST | `/membership/oauth/clients` | JWT | Server.Admin | Создать или обновить клиента |
| DELETE | `/membership/oauth/clients/:id` | JWT | Server.Admin | Удалить клиента |
| POST | `/membership/oauth/register` | Публичный | — | Динамическая регистрация клиента (RFC 7591) для публичных клиентов, таких как коннекторы MCP. См. [Подключённые приложения](../connected-apps#dynamic-client-registration) |

### Эндпоинты подтверждения устройства

| Метод | Путь | Авторизация | Описание |
|--------|------|------|-------------|
| GET | `/membership/oauth/device/pending/:userCode` | JWT | Получить информацию об ожидающем коде устройства для интерфейса подтверждения |
| POST | `/membership/oauth/device/approve` | JWT | Подтвердить авторизацию устройства. Тело: `{ "user_code": "...", "church_id": "..." }` |
| POST | `/membership/oauth/device/deny` | JWT | Отклонить авторизацию устройства. Тело: `{ "user_code": "..." }` |

## Публичные и аутентифицированные эндпоинты

API использует две функции-обёртки, которые определяют требования к аутентификации:

- **`actionWrapper`** — требует действительный JWT. Объект аутентифицированного пользователя (`au`) доступен и содержит `churchId`, `userId` и проверки разрешений.
- **`actionWrapperAnon`** — аутентификация не требуется. Используется для входа, регистрации, публичных запросов содержимого и приёмников вебхуков.

В таблицах эндпоинтов этой документации они обозначены в колонке «Авторизация» как **JWT** и **Публичный** соответственно.
