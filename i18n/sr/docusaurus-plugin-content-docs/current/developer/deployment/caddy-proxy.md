# Caddy прокси за прилагођене домене

<div class="article-intro">

Прилагођени домени цркава (`mychurch.org` → сајт цркве у B1) завршавају се на једној Windows EC2 машини на којој ради Caddy. Машина поседује TLS сертификате, преводи сваки домен на његов `{sub}.b1.church` сајт и прослеђује захтеве реверзним проксијем уз преписано Host заглавље. Цела њена конфигурација састоји се од две датотеке, статичког `Caddyfile`-а и `hosts.map`-а који се освежава из Membership API-ја, тако да преживљава поновна покретања без икаквог стања у време извршавања. Ова страница описује како се машина гради од нуле, како ради и које су замке, проверене у пракси, на које ће наићи свако ко је поново поставља.

</div>

За то како се захтев преводи на цркву и сајт када стигне до B1App-а, погледајте [Рутирање веб-сајтова и више сајтова](../architecture/websites.md).

## Компоненте

| Део | Шта је |
|---|---|
| EC2 инстанца | Windows Server; Elastic IP **`3.23.251.61`** (уграђена у DNS цркава широм света. IP је трајна, а инстанце су привремене) |
| `C:\caddy\caddy.exe` | **Прилагођена** Caddy верзија са модулом за складиштење `techknowlogick/certmagic-s3`. Стандардни Caddy не може да чита складиште сертификата |
| `C:\caddy\Caddyfile` | Цела конфигурација проксија: TLS на захтев, `map` од хоста до упстрима, преусмеравања са www на апекс, `:80` → https |
| `C:\caddy\hosts.map` | По један ред `{domain} {sub}.b1.church` за сваки домен који може да се рутира, уметнут у `map` блок Caddyfile-а |
| `sync-hostmap.ps1` + задатак `CaddyHostmapSync` | Заказани задатак (сваких 5 минута и при покретању, као SYSTEM) освежава `hosts.map` из API-ја и поново учитава Caddy елегантно, само при промени |
| Windows услуга `caddy` (WinSW омотач) | Покреће `caddy.exe run --config C:\caddy\Caddyfile --adapter caddyfile`; аутоматски се поново покреће при грешци. Caddy не подржава SCM, па је омотач обавезан |
| S3 кофа `churchapps-caddy-certs` | Заједничко складиште сертификата (`region us-east-2`, префикс `certs`). Сертификати опстају при поновној изградњи инстанце |
| IAM улога `CaddyRole` | Даје инстанци S3 приступ. Caddy користи подразумевани AWS ланац акредитива (без кључева у конфигурацији) |

## Две API крајње тачке од којих машина зависи

Обе су на Membership API-ју. `authorize` је анониман. `hostmap` од Api PR #67 (2026-08-16) захтева заглавље `x-internal-key: <INTERNAL_API_KEY>`. `sync-hostmap.ps1` га чита из `C:\caddy\internal-key.txt`:

| Крајња тачка | Улога |
|---|---|
| `GET /membership/domains/authorize?domain={host}` | **Капија `ask` за TLS на захтев** за Caddy: `200 {"authorized":true}` када је хост (или, за хост са `www.`, његов апекс) ред у табели `domains`; у супротном `404`. Ово је контрола злоупотребе. Caddy неће издати сертификат за хост који ова крајња тачка одбије |
| `GET /membership/domains/hostmap` | Захтева `x-internal-key` (или JWT администратора сервера). `text/plain`, сортирани редови без дупликата `{domain} {sub}.b1.church` (свесни сајта: домен додељен секундарном сајту бира поддомен тог сајта). Извор за `map` |

## Ток захтева

1. Прегледач преводи `mychurch.org` → `3.23.251.61` (апекс `A` запис или `CNAME proxy.b1.church`).
2. Caddy завршава TLS. Ако се сертификат налази у S3, послужује га. За непознат SNI пита се `authorize`: 200 → издаје се на захтев преко Let's Encrypt-а; 404 → **рукопожимање је одбијено** (нема сертификата, нема одговора). Непознат хост добија TLS одбијање, а не HTTP грешку.
3. `map` преводи Host на `{sub}.b1.church`. `www.{apex}` добија 302 на апекс. Хост који је ауторизован, али није мапиран (потпуно нов домен у прозору синхронизације од ≤5 минута), добија чисту 404 грешку.
4. `reverse_proxy` се повезује на `{sub}.b1.church:443` са SNI-јем и Host-ом преписаним на упстрим, тако да Vercel-ова ивица послужује B1App сајт.
   Caddy такође шаље оригинални домен посетиоца као `X-Church-Host` (Vercel преписује `X-Forwarded-Host` преписаним Host-ом). B1App middleware га прихвата само када `/domains/public/lookup/{host}` мапира тај домен на исти `{sub}` као хост захтева. Затим га излаже као `x-public-host` за канонично `Link` заглавље, `robots.txt` и `sitemap.xml`. `x-public-host` које шаље клијент се увек уклања. Schema.org `ChurchJsonLd` и даље користи `b1.church` URL (читање заглавља тамо би учинило странице динамичним).
5. Порт 80 прослеђује ACME HTTP-01 изазове, а све остало 308 преусмерава на https.

Ново ширење: домен сачуван у B1Admin-у постаје рутибилан у року од ~5 минута (задатак синхронизације). Његов сертификат се издаје при првом HTTPS приступу.

## Изградња машине од нуле

Ово је сажетак процедуре проверене у пракси. Комплетан корак по корак, са командама за копирање, налази се у радном простору за операције, а не у овом репозиторијуму. Прво предуслови, јер без њих изградња не функционише:

1. **IAM**: прикачите `CaddyRole` (S3 приступ кофи сертификата) инстанци. Проверите преко IMDSv2 са саме машине. Имајте на уму да обичан IMDS GET који враћа 401 значи само да је IMDSv2 наметнут, а не да „нема улоге".
2. **Исправност API-ја**: `authorize` мора да врати 404 за лажни домен, а `hostmap` (са заглављем `x-internal-key`) мора да врати 200 пре свега осталог.

Затим:

3. **Бинарна датотека**: преузмите прилагођену верзију са Caddy-јевог сервиса за изградњу: `https://caddyserver.com/api/download?os=windows&arch=amd64&p=github.com/techknowlogick/certmagic-s3` (~57 MB наспрам ~45 MB стандардне; v2.11.4 у време писања). Избор модула је важан. `techknowlogick/certmagic-s3` користи кључеве `bucket`/`region`/`prefix` који одговарају постојећем распореду сертификата. `ss098` форк користи `host`/`endpoint` и **неће пронаћи постојеће сертификате**.
4. **Датотеке**: `Caddyfile`, `sync-hostmap.ps1` и `internal-key.txt` (продукциони `INTERNAL_API_KEY`, једна линија) у `C:\caddy\`. Једном попуните мапу помоћу `sync-hostmap.ps1 -NoReload`.
5. **Капије пре првог покретања**: `caddy list-modules` мора да прикаже модул за S3 складиште. `caddy adapt` мора да испише `"module":"s3","bucket":"churchapps-caddy-certs","region":"us-east-2","prefix":"certs"` у свом блоку storage. `caddy validate` мора да прође.
6. **Услуга**: инсталирајте је преко WinSW-а (ид услуге `caddy`, аутоматско поновно покретање при грешци, ротирајући логови). Покреће се као LocalSystem, који приступа IMDS-у ради акредитива улоге.
7. **Задатак синхронизације**: региструјте `CaddyHostmapSync` (SYSTEM, сваких 5 минута и при покретању, ограничење извршавања од 4 минута).
8. **Провера пре пребацивања**: проверите тако што ћете принудно разрешити домене на `127.0.0.1` помоћу `curl --resolve`, јер машина нема стварни саобраћај док се EIP не пребаци. Постојећи домен мора да послужује са исправним пренесеним сертификатом. `www.` мора да добије 302. Непознат хост мора да добије TLS одбијање. `Restart-Service caddy` мора да се врати и да послужује **без ручног поновног прајмовања**. Тај тест поновног покретања је суштина статичког дизајна.
9. **Пуштање у рад**: поново повежите Elastic IP `3.23.251.61` са новом инстанцом. DNS цркава се никада не мења.

## Замке проверене у пракси (научене тешким путем, не враћајте их)

| Замка | Симптом | Решење |
|---|---|---|
| `tls_server_name {vars.upstream}` у транспорту reverse_proxy | Сваки проксиран домен добија 502. Placeholder-и мапе се разрешавају **празно у време TLS повезивања** („either ServerName or InsecureSkipVerify must be specified") | Користите placeholder нативан за транспорт: `tls_server_name {http.reverse_proxy.upstream.host}` |
| Дупли кључеви или неисправне линије у `hosts.map` | Caddy-јев `map` handler **прекида рад при дупликату улазног кључа**. Једна лоша линија може срушити целу конфигурацију | Скрипта за синхронизацију нормализује размаке, одбацује неисправне линије (одбија све само ако је >20% лоших), уклања дупликате по принципу првог побеђује и уписује UTF-8 **без BOM-а** (BOM квари први кључ мапе). API такође на извору филтрира редове домена који су празни или садрже размаке |
| `Register-ScheduledTask -RepetitionDuration ([TimeSpan]::MaxValue)` | Регистрација задатка **тихо не успева** (XML ван опсега, грешка која не прекида рад) | Изградите понављање као CIM инстанцу `MSFT_TaskRepetitionPattern` са `Interval = "PT5M"` и без трајања. Додајте `ExecutionTimeLimit` од 4 минута, јер први SYSTEM пролаз може да се заглави на хладном TLS/CRL упиту |

:::warning
Административни API се везује само за `localhost:2019`. Наслеђени режим рада је удаљено излагао API да би Membership API могао да гура конфигурације рута. Статички дизајн не захтева удаљена слања, а мањи простор излагања је намеран. `caddy reload` (локално га покреће скрипта за синхронизацију) је једини потрошач административног API-ја.
:::

:::info Наслеђено гурање при раду
`CaddyHelper` у API-ју (и крајње тачке `/membership/domains/caddy` + `/caddy/init`) и даље постоје као путања за повратак на стари режим са конфигурацијом при раду. Заказано је брисање након што статична машина буде стабилна неколико недеља. После тога су `authorize` и `hostmap` једине тачке интеграције.
:::

## Рад

- **Логови**: WinSW ротирајући логови у `C:\caddy\` (stdout/err услуге; грешке реверзног проксија се бележе у `caddy-service.err.log`). Историја синхронизације је у `C:\caddy\sync-hostmap.log`.
- **Принудно освежавање мапе**: `Start-ScheduledTask -TaskName CaddyHostmapSync`.
- **Измена конфигурације**: уредите `C:\caddy\Caddyfile`, затим покрените `caddy validate` и `caddy reload` (или `Restart-Service caddy`, јер су поновна покретања безбедна по дизајну).
- **Масовно брисање домена** по дизајну активира заштитни механизам скрипте за синхронизацију против смањења. Премести­те стари `hosts.map` на страну и поново покрените задатак да бисте прихватили намерно велико смањење.
- **Упутства за DNS за цркве се никада не мењају**: апекс `A 3.23.251.61` или `CNAME proxy.b1.church`.
