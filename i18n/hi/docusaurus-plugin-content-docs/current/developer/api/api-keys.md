# API कुंजियाँ {#api-keys}

<div class="article-intro">

API कुंजियाँ (पर्सनल एक्सेस टोकन) किसी सर्वर-साइड स्क्रिप्ट, किसी तृतीय-पक्ष कनेक्टर (Zapier, Make, Google Sheets), या ऐसी किसी भी जगह से B1 API पर प्रमाणित होने का सबसे सरल तरीका हैं जहाँ पूरा OAuth फ़्लो अनावश्यक हो। एक कुंजी किसी चर्च में एक विशेष व्यक्ति से जुड़ी होती है और उस व्यक्ति की अनुमतियाँ विरासत में लेती है, जिन्हें वैकल्पिक स्कोप के एक समूह द्वारा सीमित किया जा सकता है।

</div>

<div class="prereqs">
<h4>शुरू करने से पहले</h4>

- किसी चर्च एडमिन के पास **Edit Settings** अनुमति होनी चाहिए, वही कुंजियाँ बनाता और प्रबंधित करता है
- कच्ची कुंजी बनाते समय **एक बार** दिखाई जाती है -- इसे तुरंत किसी सुरक्षित जगह पर सहेज लें
- सभी API अनुरोध **HTTPS** का उपयोग करने चाहिए

</div>

## कुंजी प्रारूप {#key-format}

B1 API कुंजी इस तरह दिखती है:

```
cak_<prefix>.<secret>
```

- `cak_` -- स्थिर पहचानकर्ता (API कुंजी का उपसर्ग जिससे ऑथ लेयर मिलान करती है)
- `<prefix>` -- 8-अक्षर का सार्वजनिक लुकअप खंड
- `<secret>` -- 48-अक्षर का गुप्त खंड; सर्वर पर केवल SHA-256 हैश संग्रहीत होता है

पूरी कुंजी सर्वर को मानक bearer हेडर में भेजी जाती है:

```http
Authorization: Bearer cak_a1b2c3d4.f0e1d2c3b4a5968778695a4b3c2d1e0f1a2b3c4d5e6f7
```

API ऑथ लेयर `cak_` से शुरू होने वाले किसी भी टोकन को API-कुंजी पथ पर भेजती है, गुप्त खंड का हैश बनाती है, उसे उपसर्ग से खोजती है, और कुंजी के व्यक्ति की वर्तमान अनुमतियाँ हल करती है -- इसलिए B1Admin में किसी अनुमति को रद्द करने का असर ठीक अगले अनुरोध पर होता है, और कुंजी कभी भूमिका से बेमेल नहीं होती।

## कुंजी बनाना (B1Admin) {#creating-a-key-b1admin}

1. **Edit Settings** अनुमति वाले उपयोगकर्ता के रूप में B1Admin में साइन इन करें।
2. **Settings → Developer → API Keys** खोलें।
3. **New API Key** पर क्लिक करें, उसे पहचानने योग्य नाम दें (जैसे "Zapier — donations sync"), कुंजी के लिए आवश्यक स्कोप चुनें, और **Save** करें।
4. पूरी `cak_…` कुंजी एक डायलॉग में **एक बार** दिखाई जाती है। बंद करने से पहले उसे अपने इंटीग्रेशन की कॉन्फ़िगरेशन में कॉपी करें -- इसे बाद में दोबारा प्राप्त नहीं किया जा सकता। आप हमेशा नई कुंजी बना सकते हैं।

## स्कोप {#scopes}

स्कोप किसी कुंजी के कर सकने वाले कार्यों को **सीमित** करता है -- यह ऐसी कोई अनुमति कभी नहीं दे सकता जो अंतर्निहित व्यक्ति के पास न हो। खाली / कोई स्कोप नहीं का अर्थ है कि कुंजी के पास व्यक्ति का पूरा अनुमति सेट होता है।

| स्कोप | क्या करने देता है |
|---|---|
| `people:read` / `people:write` | लोगों, परिवारों, समूह सदस्यों को देखना / संपादित करना |
| `groups:read` / `groups:write` | समूहों और उनकी सदस्यता को देखना / संपादित करना |
| `donations:read` / `donations:write` | दान देखना / रिकॉर्ड करना |
| `attendance:read` / `attendance:write` | उपस्थिति, सत्र, चेक-इन देखना / रिकॉर्ड करना |
| `forms:write` | फ़ॉर्म प्रबंधित करना (पढ़ने की पहुँच write में निहित है) |
| `content:read` / `content:write` | वेबसाइट कंटेंट, रजिस्ट्रेशन, स्ट्रीमिंग देखना / संपादित करना |
| `messaging:read` / `messaging:write` | मैसेजिंग पढ़ना; write में SMS भेजना भी शामिल है |
| `roles:read` / `roles:write` | भूमिका परिभाषाएँ देखना / संपादित करना |
| `settings:read` / `settings:write` | चर्च सेटिंग्स देखना / संपादित करना (प्रोग्रामेटिक रूप से वेबहुक पंजीकृत करने के लिए **आवश्यक**) |
| `workflows:read` / `workflows:write` | वर्कफ़्लो और टास्क देखना / वर्कफ़्लो चलाना और संपादित करना। वर्कफ़्लो चलाने से ईमेल और टेक्स्ट भेजे जा सकते हैं, वेबहुक चालू हो सकते हैं, और समूह सदस्यता बदल सकती है |
| `offline_access` | लंबी अवधि के रिफ़्रेश टोकन की अनुमति (केवल OAuth फ़्लो के लिए -- API कुंजियों पर इसका कोई प्रभाव नहीं) |

`write` स्कोप में मिलान करने वाला `read` स्वतः शामिल होता है। सर्वर- और डोमेन-एडमिन अनुमतियाँ जानबूझकर स्कोप के रूप में उजागर नहीं की गई हैं -- सीमित क्रेडेंशियल कभी साइट एडमिनिस्ट्रेशन तक नहीं पहुँच सकता।

:::tip
यदि आप कुंजी का उपयोग वेबहुक पंजीकृत करने के लिए करेंगे (जैसे Zapier या Make इंटीग्रेशन के लिए), तो कुंजी में `settings:write` होना चाहिए। केवल `people:read` वाली कुंजी `POST /membership/webhooks` पर चुपचाप 403 देगी।
:::

## कुंजी का उपयोग {#using-a-key}

किसी भी bearer टोकन जैसा ही -- हर प्रमाणित एंडपॉइंट API कुंजियाँ ठीक वैसे ही स्वीकार करता है जैसे JWT स्वीकार करता है:

```bash
curl https://api.churchapps.org/membership/people \
  -H "Authorization: Bearer cak_a1b2c3d4.f0e1d2c3b4a5968778695a4b3c2d1e0f1a2b3c4d5e6f7"
```

जिस अनुरोध की कुंजी में पर्याप्त स्कोप नहीं हैं, उसे उसी आकार की **403 Forbidden** प्रतिक्रिया मिलती है जो किसी भी अनुमति-अस्वीकृत त्रुटि में होती है।

## API के माध्यम से कुंजियाँ प्रबंधित करना {#managing-keys-via-the-api}

सभी एंडपॉइंट Membership मॉड्यूल के `/membership/apiKeys` पथ के अंतर्गत हैं और उन्हें **Edit Settings** वाले चर्च एडमिन से JWT (API कुंजी नहीं) चाहिए।

| विधि और पथ | उद्देश्य |
|---|---|
| `GET /membership/apiKeys` | चर्च की कुंजियों की सूची (कोई गुप्त मान नहीं -- केवल `id`, `name`, `prefix`, `scopes`, `lastUsedAt`, `expiresAt`, `createdAt`) |
| `GET /membership/apiKeys/scopes` | सभी उपलब्ध स्कोप नामों की सूची -- कुंजी-निर्माण UI के लिए |
| `POST /membership/apiKeys` | नई कुंजी बनाएँ। बॉडी: `{ "name": "...", "scopes": ["people:read"] }`। प्रतिक्रिया में कच्ची `cak_…` कुंजी **एक बार** शामिल होती है। |
| `DELETE /membership/apiKeys/:id` | कुंजी रद्द करें -- अगले अनुरोध पर प्रभावी |

रद्द की गई कुंजी तुरंत बेकार हो जाती है -- कोई ग्रेस पीरियड नहीं है।

## सर्वोत्तम प्रथाएँ {#best-practices}

- **एक इंटीग्रेशन के लिए एक कुंजी।** यदि कुछ से समझौता हो जाए, तो आप बाकी को तोड़े बिना केवल एक कुंजी रद्द कर सकते हैं।
- **काम करने वाले सबसे संकीर्ण स्कोप बनाएँ।** Google Sheets एक्सपोर्ट को केवल `people:read` चाहिए, `settings:write` नहीं।
- **कुंजी को किसी सेवा खाते से बाँधें, किसी वास्तविक स्टाफ सदस्य से नहीं।** यदि कोई स्टाफ सदस्य छोड़ता है, तो उसकी B1 पहुँच समाप्त हो जाती है -- और उसकी पहचान के तहत बनाई गई सभी कुंजियाँ भी।
- **कुंजियाँ किसी सीक्रेट मैनेजर में संग्रहीत करें** (आपके होस्टिंग प्रदाता के environment variables, AWS Secrets Manager, आदि) -- कभी सोर्स कंट्रोल में नहीं।
- **संदेह होने पर कुंजियाँ रोटेट करें:** नई कुंजी बनाएँ, इंटीग्रेशन अपडेट करें, फिर पुरानी कुंजी हटाएँ।

## OAuth से अंतर {#how-it-differs-from-oauth}

API कुंजियाँ तब उपयुक्त हैं जब **आपका चर्च ही इंटीग्रेशन का एकमात्र उपयोगकर्ता है**। ऐसे कनेक्टर के लिए जिसे हर चर्च की स्पष्ट सहमति से कई चर्चों तक पहुँचना है -- जैसे B1 समुदाय में साझा SaaS ऐप -- इसके बजाय [OAuth और Connected Apps](./connected-apps) का उपयोग करें।

| | API कुंजी | OAuth |
|---|---|---|
| कौन इंस्टॉल करता है | एक चर्च एडमिन | हर चर्च एडमिन ऐप को अधिकृत करता है |
| ऑथ हेडर | `Authorization: Bearer cak_…` | `Authorization: Bearer <jwt>` |
| टोकन की अवधि | रद्द होने तक | एक्सेस ≈ 7 दिन, रिफ़्रेश ≈ 90 दिन |
| सर्वोत्तम उपयोग | आंतरिक स्क्रिप्ट, Zapier/Make/Sheets कनेक्टर | बहु-किरायेदार (multi-tenant) तृतीय-पक्ष ऐप |
