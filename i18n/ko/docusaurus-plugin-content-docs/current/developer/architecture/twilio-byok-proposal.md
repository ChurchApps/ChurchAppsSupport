# Twilio BYOK 연동 제안

:::caution 제안 — 제공 중인 연동이 아님
이 문서는 유지관리자 검토를 위한 설계안이며, 2026년 10월 22일에 검토한 공개 소스와 Twilio 문서를 바탕으로 합니다. 그 이후 기본 Twilio 제공업체가 출시되었습니다(`@churchapps/texting` 0.6.0과 B1 Admin **Settings > Texting**). 교회는 Account SID, Auth Token, From 번호를 입력합니다(제공업체는 `MG`로 시작하는 Messaging Service SID도 받지만, `fromNumber` 열은 여전히 `varchar(20)`이라 34자 SID를 저장하기에는 짧습니다). 문자는 수신자마다 한 번의 요청으로 Twilio Messages API를 통해 발송되며, STOP 응답은 기존 수신 웹훅을 통해 B1에 전달됩니다. 자세한 내용은 [교회 설정: 문자 메시지](../../b1-admin/settings/church-settings.md#texting)를 참고하세요. 아래의 동의 모델, Advanced Opt-Out 처리, 전달 상태, 설정 준비 상태 점검은 여전히 제안 단계이며, 출시된 동작이 아닙니다. 설정 제안과 교회별 예시가 담긴 [교회 온보딩 초안](./twilio-byok-onboarding-draft)도 함께 참고하세요.
:::

## 권장 방향

B1의 기존 문자 제공업체 체계에 Twilio를 추가하되, **교회가 소유한 Twilio 계정, API 자격 증명, Messaging Service, SMS 발송이 가능한 전화번호**를 사용합니다. 교회는 자체 법인과 메시징 캠페인을 등록하고, Twilio에 직접 비용을 지불하며, 수신자 동의를 관리하고, Twilio Console에서 승인 절차를 진행합니다. ChurchApps는 연동과 문서를 제공합니다.

교회마다 하나의 메시징 프로그램, 하나의 Messaging Service, 하나의 미국 로컬 10DLC 발신 번호로 시작합니다. 기존 B1 화면을 통해 개별 문자, 그룹 문자, 워크플로 문자, 참여 알림을 지원합니다. 교회의 동의 내용과 승인된 캠페인에 세 가지가 모두 명시되어 있다면, 예배 변경, 행사 알림, 봉사 일정 안내로 구성된 프로그램이 합리적인 첫 번째 범위입니다. 모금이나 홍보 메시지는 별도의 범위 검토와 동의가 필요하므로, 이 프로그램에 몰래 추가하지 마십시오.

| 책임 | 교회 | B1 / ChurchApps |
|---|---|---|
| Twilio 계정, 청구, 번호 소유 | 소유하고 직접 관리합니다 | 플랫폼 계정을 준비하지 않으며, 크레딧을 재판매하지 않습니다 |
| 브랜드, 캠페인, 번호 등록 | 정확한 교회 정보를 제출하고, 검토와 정정을 처리합니다 | 필요한 사전 조건을 설명하고, 제공되는 준비 상태 정보를 읽습니다 |
| 가입 페이지, 정책, 메시지 목적 | 게시하고 유지 관리합니다 | 호환되는 양식 컨트롤, 예시, 동의 기록을 제공합니다 |
| 수신자 자격과 STOP 처리 | 동의 증거를 검토하고, SMS 외부에서 받은 요청을 확인합니다 | 동의, 수신 차단, 권한, 서명된 웹훅을 강제합니다 |
| 전달과 지원 | Twilio 오류, 계정 상태, 수신된 답장을 모니터링합니다 | 제출 및 전달 상태를 보여주며, 승인을 보장한다고 주장하지 않습니다 |

ChurchApps가 소유하는 Twilio 상위 계정, 고객 하위 계정, 번호 구매, Trust Hub 제출, 청구, 대화 수신함, MMS/WhatsApp, 국제 발송, 무료 전화(toll-free) 온보딩은 이번 범위에서 제외합니다. 무료 전화는 등록을 우회하는 경로가 아니라 별도의 검증된 발신자 경로입니다. 이러한 경계는 첫 출시를 B1의 기존 "직접 가져오는 제공업체(bring-your-own-provider)" 모델에 맞추기 위한 것입니다.

## 설정 및 자격 증명 설계

`fromNumber`에 과도한 의미를 부여하거나 API 키 문자열에 구조화된 데이터를 저장하지 말고, 명시적이고 추가적인 설정 필드를 사용합니다.

| 필드 | 제안 용도 |
|---|---|
| `accountSid` | 교회 소유 Twilio 계정/프로젝트 식별자(`AC…`) |
| `apiKey`, `apiSecret` | 발신 API 접근을 위한 전용 Twilio API Key SID(`SK…`)와 비밀 값. 암호화 및 마스킹 |
| `webhookAuthToken` | Twilio SDK가 수신 서명을 검증할 때 쓰는 계정 Auth Token. 별도로 암호화 및 마스킹 |
| `messagingServiceSid` | 교회의 Messaging Service(`MG…`, 34자) |
| `fromNumber` | 선택된 SMS 발송 가능 번호(E.164 형식), 해당 계정/서비스에서 발신자로 검증된 번호 |
| 프로그램 설정 | 안정적인 프로그램 ID, 이름, 허용된 목적, 가입/정책 URL, 고지 버전 |

Twilio는 [REST 인증에 API 키를 권장](https://www.twilio.com/docs/iam/api-keys)합니다. 발송과 필요한 읽기 전용 설정 점검을 포괄하면서, 테스트를 거친 가장 좁은 키 권한을 사용하십시오. 계정 Auth Token은 여전히 [표준 Twilio 웹훅 서명 검사](https://www.twilio.com/docs/usage/security)에 필요합니다. 이 차이는 UI에서 설명해야 합니다. API 비밀 값은 웹훅 Auth Token이 아닙니다. 자격 증명은 서버 측 설정 저장소에만 두며, 공개 페이지, 양식 답변, 브라우저 발송 요청, 지원 이슈에는 절대 넣지 않습니다.

교회는 Console에서 이러한 리소스를 생성하고 관리합니다. B1의 검증 동작은 설정된 서비스, 발신자, 등록 정보를 읽기만 해야 합니다. 번호를 구매하거나, 캠페인을 만들거나, Twilio 설정을 바꾸거나, 부수 효과로 테스트 메시지를 보내서는 안 됩니다. 대신 동의한 적격 수신자에게만 허용되는 별도의 명시적 테스트 발송 동작을 제공합니다.

마스킹된 자격 증명은 같은 저장된 제공업체를 편집할 때만 유지합니다. Twilio로 전환할 때는 별도의 자격 증명을 요구하고, 오래된 제공업체 전용 값을 지워야 합니다. 마스킹된 Clearstream이나 Nalo 키를 Twilio 설정으로 가져가면 안 됩니다.

모든 로드와 업데이트는 인증된 B1 교회 범위로 제한합니다. 콜백은 저장된 연동과 예상되는 Twilio 계정/서비스/발신자에 묶고, 교회 간 충돌하는 할당은 거부합니다. 자격 증명 교체와 제공업체 연결 해제는 준비 상태를 무효화하고 대기 중인 발송을 일시 정지해야 하지만, 동의 기록이나 과거 전달 기록을 지워서는 안 됩니다.

## 동의와 수신 차단은 출시 필수 작업입니다

Twilio 프로그램을 위한 전화번호 기반 구독 기록과, 추가만 가능한(append-only) 동의/차단 이벤트를 도입합니다. 최소한의 증거로는 교회 ID, 프로그램 ID, 정규화된 전화번호, 선택적인 검증된 사람 연결, 적극적 행동, 출처 양식/제출 ID 또는 검토된 외부 증빙, 서버 타임스탬프, 고지 문구와 버전, 출처 URL, 정책 URL, 철회/재시작 이벤트를 권장합니다. 접근과 보관 기간은 기존 교회 데이터 보안 정책에 따라 제한합니다.

`unknown`, `pending`, `active`, `suppressed` 같은 상태를 사용합니다. 기존 휴대전화 번호, 가져온 연락처, 출석, 헌금, 그룹 구성원 자격, `person.optedOut = false`, `allowSms`는 적극적인 프로그램 동의가 아닙니다. 문서화된 동의를 가져오는 작업은 권한이 있는 사용자가 출처를 기록하며 수행하는 감사 가능한 작업이어야 하며, 마이그레이션이 모든 사람을 자동으로 등록해서는 안 됩니다.

초기 웹 흐름에는 B1의 표준 공개 양식 모드를 사용합니다. 기본 상태가 선택되지 않은(unchecked) 상태이고 선택 사항이며, 클릭 가능한 정책 링크를 표시하고, 하나의 프로그램과 휴대전화 필드에 대응하는, 명시적으로 설정된 SMS 동의 질문을 추가합니다. 서버에서 이 대응 관계를 검증하고, 적극적인 응답을 저장할 때 화면에 표시된 고지 내용을 스냅샷으로 남깁니다. 임의의 질문 레이블, 대화형 AI, 워크플로 구성원 자격에서 동의를 유추하지 마십시오. 대화형 방식은 명시적인 적극적 상호작용과 증거 기록이 테스트된 뒤에만 활성화합니다.

체크되지 않은 제출은 구독을 만들지 않으며, 다른 사람이 기존에 가진 동의를 철회해서도 안 됩니다. 동의는 제출된 전화번호에 묶습니다. 직원은 가구 기록을 병합하지 않고도 모호한 사람 연결을 해결할 수 있습니다. 바뀐 휴대전화 번호에는 별도의 동의가 필요합니다. 익명 양식에는 남용 방지 조치를 적용하고, 번호 소유권 검증이나 이중 확인(double opt-in) 단계는 명시적으로 만듭니다. 체크박스 하나만으로는 누가 그 전화를 소유하는지 증명할 수 없습니다. 확인 절차를 사용한다면, 완료될 때까지 구독을 보류 상태로 두고, 그 정확한 절차를 등록 자료에 설명합니다.

Twilio의 경우 SMS 수신 차단과 디렉터리 공개 여부를 분리합니다. 기존의 수신 거부 항목은 보수적으로 수신 차단 기록으로 옮기고, 나머지 기존 수신자는 `unknown` 상태로 둡니다. 문서화된 새 등록은 디렉터리 공개 설정을 바꾸지 않으면서 SMS 동의를 설정할 수 있습니다. 다른 제공업체의 동작은 각자의 마이그레이션이 별도로 검토될 때까지 그대로 유지합니다.

실제로 발송할 때마다 다음을 요구합니다. 교회 연동이 활성화되어 있고 준비 상태여야 하며, 정확한 전화번호에 대해 현재 프로그램 동의가 있어야 하고, 전화번호 수준의 차단이 없어야 하며, 기존 호출자 권한이 있어야 합니다. 알림은 추가로 `allowSms`, 카테고리 설정, 방해 금지 시간(quiet hours)을 따릅니다. 큐에 넣은 후 다시 확인하고, 병합 필드를 해석하고, 번호를 정규화 및 검증하고, 전화번호 기준으로 중복을 제거합니다. STOP은 수동 발송과 워크플로를 포함해 해당 서비스/프로그램의 모든 발송을 막아야 하며, 같은 전화번호를 공유하는 모든 사람에게도 적용되어야 합니다.

교회 식별 정보와 STOP 안내는 공통 Twilio 발송 경로에서 일관되게 표시하고, 최종 SMS/세그먼트 수를 미리 보여줍니다. 병합 필드 확장과 길이 처리는 이러한 요소를 보존해야 하며, 수신 거부 안내를 조용히 잘라내서는 안 됩니다. 예시와 실제 알림/워크플로 템플릿은 서로 맞춰 둡니다.

## Twilio 발송, 응답, 전달 상태

`TwilioProvider.sendMessage`를 선택된 Messaging Service와 발신자를 사용해 Messages API로 구현합니다. Twilio 메시지 SID와 접수/제출 결과를 반환합니다. HTTP 접수는 단말기 전달을 뜻하지 않습니다. 그룹 발송은 입력 순서대로 수신자별 결과를 반환합니다.

**`sendBulk`와 개별 발송 모두**의 아웃바운드 동시성을 제한합니다. 현재 병합 필드 분기는 `sendMessage` 호출을 펼쳐서 실행합니다. 요청 예산에 맞출 수 없는 그룹은 발송 의도와 가져갈 수 있는 작업을 내구성 있게 저장합니다. 교회에 별도 서비스를 실행하도록 요구하지 말고, 기존 배포 모델을 재사용합니다. 알려진 일시적 오류나 속도 제한 오류는 백오프와 함께 재시도합니다. 모호한 시간 초과는 맹목적으로 재발송할 대상이 아니라, 대조해서 확인해야 할 "결과 불명" 상태로 취급합니다. 그렇지 않으면 중복 문자와 중복 요금이 발생할 수 있습니다.

교회별 수신 및 상태 콜백 URL을 설정합니다. SDK, 정확히 설정된 외부 URL, 원래의 양식 매개변수, 일치하는 계정 Auth Token을 사용해 `X-Twilio-Signature`를 검증합니다. 비밀 URL만으로는 충분하지 않습니다. 콜백은 저장된 교회/계정/메시지 기록과 매칭하고, 중복 이벤트와 발송 결과가 커밋되기 전에 도착한 콜백을 처리하며, 오래된 이벤트가 종료 상태를 덮어쓰지 못하게 합니다. 수신 확인에는 빈 TwiML을, 상태 이벤트에는 적절한 성공 응답을 반환합니다. [Twilio 보안](https://www.twilio.com/docs/usage/security), [상태 콜백](https://www.twilio.com/docs/messaging/guides/track-outbound-message-status)을 참고하십시오.

Messaging Service의 **Advanced Opt-Out**을 권장합니다. STOP/START/HELP 확인 메시지는 Twilio가 담당하고, B1은 인증된 `OptOutType` 이벤트를 소비하며 중복 확인 메시지는 보내지 않습니다. STOP은 즉시 수신 차단을 기록합니다. START는 이미 알려진 구독을 같은 고지 프로그램에 대해서만 복원하며, 새 재시작 이벤트를 남깁니다. START가 새 전화번호를 관련 없는 메시지에 가입시키거나 알림 설정을 켜서는 안 됩니다. HELP는 누구도 등록하지 않습니다. 그 밖의 수신 답장은 B1 수신함 범위 밖에 있으며, 교회가 Twilio에서 이를 모니터링할 수 있도록 문서화된 방법을 제공해야 합니다. [Advanced Opt-Out](https://www.twilio.com/docs/messaging/tutorials/advanced-opt-out)

Twilio 메시지 SID, 계정/서비스 연결 정보, 제출 시각, 최종 상태/오류 코드, 콜백 시각을 전달 로그와 함께 저장합니다. 대기/접수, 전달됨, 실패, 미전달, 알 수 없음을 정확히 표시합니다. 다른 제공업체의 기존 응답 계약은 유지하고, 집계된 성공 수가 제출을 의미하는지 전달을 의미하는지도 정의합니다.

## 설정 준비 상태와 승인 검증

자격 증명, 서비스/발신자 소유권, 캠페인 검증, 번호 등록, 웹훅 점검, 전달된 스모크 테스트에 대해 각각 구분된 확인 단계를 보여줍니다. 자격 증명이 작동한다는 이유만으로 "승인됨"이라는 단일 녹색 배지를 표시하지 마십시오.

미국 로컬 번호의 경우, 서비스의 [Usa2p 캠페인 리소스](https://www.twilio.com/docs/messaging/api/usapptoperson-resource)를 읽고 관련 캠페인이 `VERIFIED` 상태인지 확인해야 합니다. 또한 선택된 번호가 해당 서비스와 연결되어 있고 번호 등록을 마쳤는지 별도로 검증합니다. 승인된 캠페인이라도 번호 등록은 대기 중일 수 있습니다. 지원되는 읽기 API가 필요한 신호를 제공하지 않으면 **수동 Console 검증 필요**로 표시하고, 교회 관리자가 날짜와 함께 남긴 확인을 그대로 기록합니다. 이를 API로 검증된 것으로 표시하지 마십시오. 자동 번호 등록 이벤트는 후속 작업으로 둘 수 있습니다. [번호 등록 오류](https://www.twilio.com/docs/api/errors/30035), [A2P 등록 이벤트](https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/event-streams-setup)

발송을 활성화하기 전에 최신 점검을 요구하고, 점검한 시각과 방법을 기록하며, 오래된 점검은 만료시킵니다. 자격 증명이 취소되거나, 발신자가 바뀌거나, 등록이 실패하거나, 계정 오류가 계속되면 일시 정지합니다. 스모크 테스트의 전달 성공은 테스트한 경로가 작동한다는 뜻일 뿐, 보편적인 이동통신사 승인이나 수신자 동의를 의미하지 않습니다. 동반 문서는 교회의 사전 제출, 출시 전, 운영 중 점검 항목을 명시합니다.

## 저장소 및 출시 계획

[조직 기여 가이드](https://github.com/ChurchApps/.github/blob/main/CONTRIBUTING.md)는 B1 기능 요청을 ChurchAppsSupport로, 구현 PR을 해당 저장소로 보내도록 안내합니다. 중앙 기능 요청 하나를 만들고, 집중된 구현 PR을 그 요청과 연결합니다.

1. **ChurchAppsSupport:** Twilio를 사용 가능한 사용자 기능으로 제시하기 전에 이 설계안과 온보딩 초안을 검토합니다.
2. **Packages:** Twilio 어댑터, 명시적인 공유 설정/인터페이스, B1Admin/B1App이 공유하는 SMS 동의 양식 렌더링을 추가합니다. 소비자 업데이트 전에 changeset을 포함하고 기존 릴리스 워크플로로 배포합니다.
3. **Api:** 연동 메타데이터, 동의/차단, 전달 상태를 위한 추가형 마이그레이션을 추가합니다. 설정 검증, 공유 발송 게이트, 양식 증거 저장, 웹훅 처리, 발송 영속화를 구현합니다.
4. **B1Admin:** Twilio 설정/준비 상태 UI, 프로그램/동의 관리, 제공업체를 인식하는 발신자 저장, 정확한 전달 보고를 추가합니다. 일반 사람 편집을 통해서는 SMS 동의를 무시하는 기능을 제공하지 않습니다.
5. **B1App:** 익명 방문자와 모바일 방문자를 포함해, 공개 양식/페이지와 정책 링크 경험이 공유 컨트롤과 일치하는지 검증합니다. 별도의 Twilio 브라우저 클라이언트는 필요하지 않습니다.
6. **ChurchAppsSupport:** 출시 후 온보딩 초안을 지원되는 설정/도움말 페이지로 바꾸고, 실제 스크린샷을 추가하며, 문자 설정에서 링크하고, 번역을 준비합니다.

스키마와 공유 패키지를 소비자보다 먼저 배포합니다. Twilio는 소규모 옵트인 파일럿을 위해 기능 플래그로 제한합니다. 기존 제공업체는 계속 작동해야 합니다. 롤백은 Twilio 발송을 비활성화하고 제출되지 않은 작업을 취소하되, 수신 거부 기록과 증거는 보존해야 합니다. 수신자를 다른 제공업체나 다른 발신자로 자동 전환해서는 안 됩니다.

## 작업량 평가

이 평가는 에코시스템에 익숙한 기여자를 기준으로 한 계획 추정치입니다. 이 평가에서는 운영 자격 증명이나 실제 SMS를 사용하지 않았습니다.

| 작업 | 개발자 일수 |
|---|---|
| 어댑터, 설정/스키마 확장, 설정 UI | 2–3 |
| 전화번호/프로그램 동의, 독립적인 차단, 공통 발송 게이트, 공개 양식 연동 | 3–5 |
| 서명된 콜백, 전달 영속화, 제한되고 내구성 있는 작업 큐 | 2–3 |
| 준비 상태 UI, 교회 가이드, 통합/회귀 테스트, 파일럿 수정 | 3–4 |
| **권장 출시 범위** | **총 10–15** |

기본 어댑터/설정 개념 증명은 약 1–2일입니다. 발신자만 추정한 값에는 이 권장 사항에 필요한 동의와 온보딩 작업이 포함되지 않습니다. 외부 Twilio/이동통신사 검토 시간은 별도이며 가변적입니다. 프로젝트는 승인 날짜나 승인 결과를 약속해서는 안 됩니다.

## 완료 기준

- [ ] 교회가 계정, 서비스, 등록된 발신자, 캠페인을 소유하고 비용을 지불합니다. ChurchApps가 관리하는 Twilio 계정은 필요하지 않습니다.
- [ ] 자격 증명은 암호화 및 마스킹되고, 테넌트 범위로 제한되며, 교체 가능하고, 로그나 공개 콘텐츠에 없습니다. 검증은 읽기 전용입니다.
- [ ] 선택되지 않은 선택형 동의는 실제 정책 링크를 표시하고, 프로그램/전화번호/고지 증거를 서버 측에 저장합니다. 동의를 거부해도 기본 양식 동작은 계속 가능합니다.
- [ ] 수동, 그룹, 병합 필드, 워크플로, 알림 경로가 모두 같은 Twilio 적격성 게이트를 적용합니다. 알 수 없음, 동의 없음, 전화번호 변경, 차단된 수신자는 유용한 사유와 함께 건너뜁니다. 확장과 길이 처리 후에도 교회 식별 정보와 STOP 안내가 유지됩니다.
- [ ] 기존 디렉터리 공개 설정은 수신자를 등록하지 않습니다. STOP/START는 디렉터리 공개 여부나 관련 없는 설정을 바꾸지 않습니다. 공유 전화번호와 교회 간 사례를 테스트합니다.
- [ ] 서명된 STOP/START/HELP, 잘못된 서명, 잘못된 계정/서비스, 중복 이벤트, 재전송된 양식 제출, 위조된 동의 대응 관계를 다룹니다.
- [ ] 그룹 크기/시간 초과, 요청 빈도 제한, 부분 실패, 모호한 결과, 콜백 경합, 순서가 뒤바뀐 전달 이벤트를 테스트하며, 중복 발송이 없어야 합니다.
- [ ] 캠페인 승인과 번호 등록 완료는 자격 증명 검증과 구분됩니다. 수동 증거는 명확히 표시되며, 오래되었거나 취소된 준비 상태는 발송을 차단합니다.
- [ ] 파일럿 교회가 가입 페이지, 거절 및 수락 양식 경로, 정확한 정책 URL, 동의한 테스트 수신자를 확인합니다. 제출, 전달, STOP 차단, 허용된 재구독까지 모두 검증합니다.
- [ ] 기존 Clearstream, Text In Church, Nalo 설정과 발송 동작이 회귀 테스트를 통과합니다. 도움말 문구는 제안과 출시된 기능을 구분합니다.
