# قاعدة البيانات

<div class="article-intro">

تعتمد واجهة برمجة تطبيقات ChurchApps على بنية **قاعدة بيانات لكل وحدة**. لكل وحدة من وحدات البيانات الست قاعدة بيانات MySQL خاصة بها مع مجمع اتصالات مستقل، مما يوفر حدودًا واضحة للبيانات مع الحفاظ على كل شيء ضمن نشر واحد.

</div>

<div class="prereqs">
<h4>قبل أن تبدأ</h4>

- ثبّت **MySQL 8.0+** -- راجع [المتطلبات الأساسية](../setup/prerequisites.md)
- اضبط سلاسل اتصال قواعد البيانات في ملف `.env` الخاص بك -- راجع [متغيرات البيئة](../setup/environment-variables.md)

</div>

## نظرة عامة على البنية

```
Api
├── membership_db   ← الأشخاص والمجموعات والصلاحيات
├── attendance_db   ← الخدمات والجلسات والسجلات
├── content_db      ← الصفحات والأقسام والعناصر
├── giving_db       ← التبرعات والصناديق والمدفوعات
├── messaging_db    ← المحادثات والإشعارات
└── doing_db        ← المهام والخطط والتكليفات
```

### قرارات التصميم الرئيسية

- **قاعدة بيانات واحدة لكل وحدة** -- تحتفظ كل وحدة بقاعدة بيانات MySQL خاصة بها مع مجمع اتصالات مخصص (تديره `KyselyPool`). يحافظ هذا على استقلال الوحدات ويتيح تطوير المخطط بشكل مستقل.
- **الملكية الحصرية** -- تُقرأ جداول الوحدة وتُكتب فقط بواسطة الشيفرة البرمجية الخاصة بتلك الوحدة. عندما تحتاج وحدة أخرى إلى هذه البيانات، فإنها تستدعي بوابة الوحدة المالكة بدلًا من الاستعلام عن الجداول مباشرةً -- راجع [التواصل بين الوحدات](./module-structure.md#cross-module-communication).
- **نمط المستودع دون ORM** -- تمر جميع عمليات الوصول إلى البيانات عبر فئات مستودعات تبني استعلامات SQL مُنمَّطة باستخدام منشئ الاستعلامات Kysely على مخطط الوحدة. وهذا يمنح تحكمًا كاملًا في أداء الاستعلامات وسلوكها.
- **متعددة المستأجرين بالتصميم** -- يتم تحديد نطاق كل استعلام بواسطة `churchId`. تتضمن جميع الجداول عمود `churchId`، وتفرض طبقة المستودعات عزل المستأجرين تلقائيًا.

## سلاسل الاتصال

يتم ضبط اتصال قاعدة بيانات كل وحدة في ملف `.env` باستخدام تنسيق سلسلة اتصال MySQL القياسي:

```
mysql://user:password@host:port/database
```

على سبيل المثال، قد تبدو إعدادات التطوير المحلي كما يلي:

تقرأ كل وحدة اتصالها من متغير بيئة يُسمى `<MODULE>_CONNECTION_STRING`:

```env
MEMBERSHIP_CONNECTION_STRING=mysql://root:password@localhost:3306/churchapps_membership
ATTENDANCE_CONNECTION_STRING=mysql://root:password@localhost:3306/churchapps_attendance
CONTENT_CONNECTION_STRING=mysql://root:password@localhost:3306/churchapps_content
GIVING_CONNECTION_STRING=mysql://root:password@localhost:3306/churchapps_giving
MESSAGING_CONNECTION_STRING=mysql://root:password@localhost:3306/churchapps_messaging
DOING_CONNECTION_STRING=mysql://root:password@localhost:3306/churchapps_doing
```

:::info
في بيئة الإنتاج، تُخزَّن سلاسل الاتصال في AWS SSM Parameter Store وتقرأها فئة `Environment` عند بدء التشغيل.
:::

## نصوص المخطط

تُعرَّف مخططات الجداول كعمليات ترحيل Kysely في دليل `tools/migrations/`، منظمةً حسب الوحدة:

```
tools/migrations/
├── membership/
├── attendance/
├── content/
├── giving/
├── messaging/
└── doing/
```

تحدد عمليات الترحيل إنشاء الجداول والفهارس وتغييرات المخطط. يحتوي دليل `tools/dbScripts/` على بيانات تجريبية وبيانات أولية يمكن تحميلها فوق المخطط.

## تهيئة قاعدة البيانات

### تهيئة جميع قواعد البيانات

```bash
npm run initdb
```

ينشئ هذا الأمر قواعد البيانات الست جميعها ويشغّل عمليات الترحيل لكل منها.

### تهيئة وحدة واحدة

```bash
npm run initdb -- --module=membership
```

:::tip
عند العمل على وحدة محددة، يمكنك إعادة تهيئة قاعدة بيانات تلك الوحدة فقط دون التأثير على الوحدات الأخرى.
:::

## نمط الوصول إلى البيانات

تبني المستودعات الاستعلامات باستخدام منشئ استعلامات Kysely على المخطط المُنمَّط لقاعدة بيانات الوحدة، والذي يُحصل عليه عبر دالة `getDb()` الخاصة بالوحدة. تبدو طريقة المستودع النموذجية كما يلي:

```typescript
public async loadAll(churchId: string) {
  return getDb().selectFrom("people").selectAll()
    .where("churchId", "=", churchId)
    .execute();
}
```

يتم الحصول على المستودعات عبر `RepoManager`:

```typescript
const repos = await RepoManager.getRepos<Repos>("membership");
const people = await repos.person.loadAll(churchId);
```

:::warning
قم دائمًا بتضمين `churchId` في استعلاماتك للحفاظ على عزل المستأجرين. لا تستعلم عبر المستأجرين أبدًا إلا إذا كان لديك سبب محدد ومصرّح به لذلك.
:::

## المراجع بين الوحدات

نظرًا لأن بيانات كل وحدة موجودة في قاعدة بيانات منفصلة، فلا توجد مفاتيح أجنبية أو عمليات ربط SQL عبر حدود الوحدات. يخزّن السجل المرتبط ببيانات وحدة أخرى معرّف ذلك السجل -- على سبيل المثال، يحمل التبرع في قاعدة بيانات giving المعرّف `personId` لشخص موجود في قاعدة بيانات membership -- ويتم أي تركيب للبيانات عبر الوحدات في شيفرة التطبيق.

هذا القيد هو ما يجعل حدود الوحدات حقيقية: يمكن لكل مخطط أن يتطور بشكل مستقل، ويمكن نقل قاعدة بيانات الوحدة إلى خادم خاص بها، بل ويمكن استخراج الوحدة كخدمة مستقلة دون فك تشابك الجداول المشتركة أو الاستعلامات عبر قواعد البيانات.
