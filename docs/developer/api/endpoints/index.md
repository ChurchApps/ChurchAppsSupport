# Endpoint Reference

<div class="article-intro">

This section documents all REST endpoints exposed by the ChurchApps API. Each module page lists every route with its HTTP method, path, authentication requirements, and required permissions.

</div>

## Base URL

| Environment | URL |
|-------------|-----|
| Local development | `http://localhost:8084` |
| Production | `https://api.churchapps.org` |

The [Lessons API](./lessons.md) is a separate service with its own base URL (`https://api.lessons.church`); it accepts the same JWT.

## Request Conventions

- **Content-Type:** All request and response bodies use `application/json`
- **Multi-tenant:** Every authenticated request is scoped to a `churchId` extracted from the JWT token — you do not pass `churchId` in the URL
- **Batch saves:** Most `POST` endpoints accept an **array of objects**. The API will insert new records (no `id` field) and update existing ones (with `id` field) in a single call
- **IDs:** Entity IDs are 11-character strings generated by the API (letters, digits, `-` and `_`). Leave `id` out to create a record; send it to update one

### Example: Batch Save

```json
POST /membership/people
Authorization: Bearer <token>

[
  { "firstName": "Jane", "lastName": "Doe" },
  { "id": "abc-123", "firstName": "John", "lastName": "Smith" }
]
```

The first object is created (new); the second is updated (has `id`).

## Response Format

Successful responses return JSON — either a single object or an array. Error responses use standard HTTP status codes:

| Code | Meaning |
|------|---------|
| `200` | Success |
| `400` | Bad request (validation errors) |
| `401` | Unauthorized (missing/invalid token or insufficient permissions) |
| `404` | Not found |
| `500` | Server error |

Validation errors return:

```json
{
  "errors": [
    { "msg": "enter a valid email address", "param": "email", "location": "body" }
  ]
}
```

## How to Read Endpoint Tables

Each module page organizes endpoints by controller. The tables use these columns:

| Column | Description |
|--------|-------------|
| **Method** | HTTP method (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) |
| **Path** | Route path relative to the controller's base path |
| **Auth** | **JWT** = requires a bearer token in the `Authorization` header (a login JWT, an OAuth access token, or an [API key](../api-keys.md)), **Public** = no auth required, **Internal** = server-to-server route guarded by a shared key instead of a user token |
| **Permission** | Required permission (e.g. `People.Edit`). `—` means any authenticated user |
| **Description** | What the endpoint does |

Most resources follow the same four-route shape: `GET /` (list all), `GET /:id` (get by ID), `POST /` (create or update, as a batch), and `DELETE /:id` (delete). Each route is declared in its own controller, so the permission can differ from one resource to the next; the module pages list every route with the check it enforces.

## Reporting Module

The Reporting module works differently from the other modules. Instead of database-backed resources, it loads report definitions from JSON files shipped with the API and runs their parameterized SQL queries.

| Method | Path | Auth | Permission | Description |
|--------|------|------|------------|-------------|
| GET | `/reporting/reports/:keyName` | JWT | — | Load a report definition (display name, parameters, queries, outputs) by key name. `keyName` may contain only letters, digits, `_` and `-` (400 otherwise). 404 when no report has that key |
| GET | `/reporting/reports/:keyName/run` | JWT | Set by the report | Run a report and return `{ displayName, description, outputs, table }`, where `table` is the result rows. 401 when the caller lacks the report's permission, 404 when no report has that key |
| GET | `/reporting/reports/groupAttendanceDownload/run` | JWT | Attendance.View | Run the group attendance download. Same response shape, but `table` holds one row per group member (`displayName`, `groupName`, `personId`, `groupId`) with one `present` / `absent` column per dated session |

Report parameters are passed as query string values (e.g. `?startDate=2024-01-01&endDate=2024-12-31`); a parameter that is left out is sent to the query as an empty string. The `churchId` parameter is injected automatically from the JWT token.

## Platform Endpoints

These routes sit outside the module prefixes. They report on the service itself and support the MCP server.

| Method | Path | Auth | Permission | Description |
|--------|------|------|------------|-------------|
| GET | `/` | Public | — | Service descriptor: `{ name, version, description, modules }` |
| GET | `/modules` | Public | — | Module list: `{ modules: [{ name, prefix, status }], total, timestamp }` |
| GET | `/health` | Public | — | Liveness check: `{ status, timestamp, environment, node, modules }` |
| GET | `/health/environment` | Public | — | `{ environment, stage, timestamp }` |
| GET | `/health/database-connections` | Public | — | Reports whether each module's database configuration is loaded: `{ status, timestamp, environment, summary: { total, loaded, missing }, modules: { loaded, missing }, connections }`. `status` is `healthy` with a 200, or `degraded` with a 503 when any module is missing its configuration |
| POST | `/mcp` | JWT | Caller's own permissions and scopes | [MCP server](../mcp.md) endpoint (JSON responses, no session state). The bearer token may be a JWT or a `cak_` API key. Without a valid token it returns 401 with a `WWW-Authenticate` header pointing at the protected-resource metadata below |
| GET | `/.well-known/oauth-protected-resource` | Public | — | OAuth protected-resource metadata for the MCP server: `{ resource, authorization_servers, scopes_supported, bearer_methods_supported, resource_name }` |
| GET | `/.well-known/oauth-protected-resource/mcp` | Public | — | Same document as above, at the path-suffixed URL that MCP clients try first |
| GET | `/.well-known/oauth-authorization-server` | Public | — | OAuth authorization-server metadata: issuer, authorization, token and registration endpoints, supported scopes, grant types and PKCE method. See [OAuth discovery](../mcp.md#oauth-discovery) |
| GET | `/favicon.ico` | Public | — | The ChurchApps icon, cached for a day. MCP connector screens show the host's favicon next to its tools |
